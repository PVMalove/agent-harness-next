## [Unreleased]

### Added

- **[Пошаговая проверка тест-автора]:** `harness health` выводит отдельную строку на каждое условие тест-автора — блок `test_author`, корень проекта по Git, доверие Claude Code, guard, runner и probe изоляции (`hooks.test_author_*`), и для каждого отказа печатает шаг исправления: фрагмент конфигурации, путь для диалога доверия или команду. `harness health --fix` добавляет отсутствующий блок `test_author` в `.harness/project.json` из плана developer в `.harness/orchestration.json` и не меняет существующий. Руководство «Как включить тест-автора» добавлено в документацию проекта и шаблон целевого проекта (#1122).
- **[Перенос отчёта architect без last_accepted]:** `batch create --supersedes` переносит отчёт architect закрытого batch, который не был принят, если человек подтвердил именно этот отчёт: `--carry-architect <dispatch>`, `--architect-report-sha256`, `--architect-confirmed-by` и `--architect-confirmed-at`. Ссылка `supersedes.architect` хранит id dispatch, `report_sha256` и подтверждение; batch начинает с developer без нового architect. Отказ без подтверждения человека, при другом SHA-256, другом Definition of Done и при `commit_plan` вне `allowed_paths` нового batch (#1052).
- **[Журнал worker под runtime]:** Новая команда `dispatch logs --dispatch <id> [--offset N] [--follow]` показывает события worker под надзором runtime из его журнала запуска `executions/<operation_id>/stdout.log`; с `--follow` она печатает каждое событие строкой JSON, пока worker работает, и не держит замок ledger. Тот же журнал читают `dispatch observe` и экран worker в веб-консоли, пока worker работает (#1124).
- **[Проверки адаптеров и PATH serve]:** `harness health` сверяет `.harness/adapters/claude_worker.py` и `codex_worker.py` с версией harness (`orchestration.adapters`) и ищет `claude` и `codex` в PATH окружения `harness-runtime serve` (`orchestration.worker_binaries`), который runtime теперь сообщает в ответе `status` как `search_path`. Отсутствие двоичного файла, нужного роли с транспортом `external`, — `fail` с командой запуска serve (#1124).

- **[Кэш cargo для QA-контейнеров]:** Элемент `cache` в `access_policy.*.filesystem` принимает необязательное поле `variable`: контейнерный исполнитель сам передаёт `--env <variable>=<путь кэша>`, поэтому путь кэша не требует настройки окружения `harness-runtime serve`. Имя уникально среди кэшей, не совпадает с `environment` и с именами, которые задаёт runtime; кэш без `variable` сохраняет прежний digest плана. Каждый QA-прогон задаёт `CARGO_TARGET_DIR=<run root>/cargo-target`: cargo-этапы одного прогона переиспользуют собранные зависимости, а каталог удаляется вместе с прогоном, поэтому собранный код кандидата не переходит в прогон другого. Решение — ADR 0032; настройка и процедура измерения — раздел «Caches» в `.harness/docs/container-executor.md` (#1097).

### Fixed

- **[Задержка ответа serve]:** `harness-runtime serve` принимал соединение только на следующем такте опроса (до 25 мс), а клиент открывает соединение на каждый запрос, поэтому каждая команда coordinator ждала. Цикл accept теперь ждёт соединение через `poll(2)`: `state.read` на пустом store — около 3,4 мс вместо 25 мс; флаг остановки проверяется не реже, чем раньше (#1146).
- **[Retry проверки на store]:** `batch decide --decision retry` по маршруту `verification` в эпохе runtime store падал с `NotADirectoryError`: хеш отчёта считался чтением файла, которого в store нет. Регистрация кандидата берёт `report_sha256` записи, который ledger сверяет с отчётом в обеих эпохах (#1146).
- **[Контейнерный worker без ложного blocked]:** Контейнерный worker, который записал отчёт и вышел раньше, чем coordinator его наблюдал, больше не попадает в `blocked` с `worker-exited-without-report`: `dispatch wait`, `dispatch status --dispatch` и `report submit` подтверждают модель по сохранённому stdout вышедшего контейнера, а `report submit` делает это до проверки self-report. Событие `init` ищется в полных строках первых 4 МиБ потока, а не в первых 64 КиБ. `.py`-адаптер контейнерного плана запускается через `python3` образа; `claude_worker.py` под `HARNESS_EXECUTOR=docker` просит только записать отчёт, без команд coordinator, и руководство `container-executor.md` описывает его вместо нерабочего shell-примера. Runtime заменяет значения переменных `environment` на `[redacted:<имя>]` в логах контейнерного worker. `harness health` (`orchestration.worker_binaries`) для роли в контейнере проверяет движок в PATH serve и образы в хранилище движка вместо `claude` на хосте и ищет `claude` также в `~/.local/bin`. Решения — раздел #1125 ADR 0025; hooks проекта в контейнере зависят от #1122 (#1125).
- **[Тест-автор в worktree developer]:** `test-author-preflight.sh` берёт корень проекта из `git rev-parse --show-toplevel` и больше не требует `CLAUDE_PROJECT_DIR`: переданная переменная, которая указывает на другой каталог, даёт отдельный отказ `project_dir_mismatch`. Linked worktree доверен, если в Claude Code доверен основной checkout его репозитория, поэтому новый worktree не требует своего диалога доверия. In-process developer `/implement` вызывает автора через `.harness/health/test_author.py run --repo <worktree> --brief <brief>`, и автор работает с guard и runner этого worktree. Решение записано в ADR 0033 (#1122).
- **[Право записи в worktree задачи]:** `batch create`, а для пишущей роли `dispatch preflight` и `dispatch send`, создают и удаляют временный файл в worktree задачи и в его каталоге git-метаданных (`git rev-parse --absolute-git-dir`) и отказывают, если сессия не может туда писать: ошибка называет каталог, remedy — сессия в основном checkout с правом записи в worktree и его git-метаданные или маршрут одной сессии. Раньше coordinator узнавал об этом только из отчёта `blocked` developer, когда `git commit` не мог создать `index.lock`. Skill `implement` до смены метки `status::*` проверяет, что сессия открыта в основном checkout и может писать в `.git/worktrees`, worktree задачи и `.harness/.sandboxes/scratch/inbox/`; требование описано в `docs/agents/worktrees.md` (#1126).
- **[Адаптер живёт вместе с worker]:** Под надзором runtime стандартные адаптеры `claude_worker.py` и `codex_worker.py` больше не завершаются раньше worker, поэтому dispatch работающего worker не попадает в `blocked` с `worker-exited-without-report`. Адаптер держит worker в своей группе процессов, не читает свой stdin и возвращает код выхода worker (`128 + N` при сигнале N), который `runtime_failure.exit_code` показывает при выходе без отчёта; это правило обязательно для любого нового адаптера. Без `execution` в brief (файловый ledger или runtime без `execution.launch`) адаптеры запускают worker отсоединённо, как раньше (#1124).
- **[Отчёт read-only роли через адаптер Claude]:** `claude_worker.py` даёт read-only роли (не `developer` и без `Edit`/`Write`, например `architect` и `code-review`) право `Edit(//<report_staging_path>)`: под `dontAsk` она записывает свой отчёт и не может писать в другие файлы. `--claude-bin`, заданный именем, ищется в `PATH`, затем в `~/.local/bin`, поэтому адаптер находит `claude` и тогда, когда `~/.local/bin` нет в PATH окружения `harness-runtime serve` (#1123).
- **[Hooks и старый конверт]:** `runtime-autostart.sh` при `.claude/hooks/hook_response.py`, который не регистрирует `runtime-autostart`, больше не блокирует каждый вызов `Bash` и не зацикливает `Stop`: он печатает предупреждение `[runtime-autostart-failed]` с командой исправления и завершается кодом `0`. `harness update` не подключает hook, чей `hook_id` не знает установленный конверт, и печатает `harness update <repo> --force-seed-file .claude/hooks/hook_response.py`, которая за один запуск заменяет конверт и подключает hook. Проверка `hooks.policy` в `harness health` сообщает такой рассинхрон (`fail`, если hook подключён) и даёт ту же команду. Блокировка критичных hooks не меняется (#1100).
- **[QA при отсутствующем исполняемом файле гейта]:** Runner и валидатор отчёта QA решают исход одним правилом `qa_report_outcome`: упавшая стадия, окончание которой runtime отнёс к домену (`tooling` при выходе 126/127, `timeout`), даёт записанный отчёт `blocked` вместо отказа валидатора. Retry такого отчёта повторяет QA на том же кандидате без траты попытки разработчика, `batch auto-decide` останавливается с `qa-environment-failure` и remedy про образ QA. При объявленном `qa_preparation` brief контейнерного QA закрепляет проверку `command -v` каждого исполняемого файла гейта после подготовки и как environment probe: образ без `cargo` останавливает QA до первой команды гейта. При объявленных `qa_environment_probes` и `qa_project_file_checks` (все проверки файлов проекта прошли) это новая попытка без отчёта с названной причиной и remedy про образ; без проб или без проверок файлов проекта диагноз `unknown`, и `qa run` записывает отчёт `blocked` с упавшей стадией `preparation` и блокером `coordinator triage required; no automatic retry`, без remedy про образ. Шаблон получил образ QA `.harness/container/Dockerfile.qa` с тулчейном Rust; сборка и выбранное поведение описаны в `.harness/docs/container-executor.md` (#1096).

## [2.0.0]

### Breaking Changes

- **[Обязательный Rust runtime]:** Operational state оркестрации хранит runtime store `state/runtime.db`, а пишет в него только `harness-runtime serve`. Недоступный runtime даёт `runtime_unavailable` и код 2 (#792, #801, #807).
- **[Ledger версии 4]:** `harness-runtime migrate` переводит ledger версии 3 в runtime store и пишет `ledger.json` с `version: 4`, после чего установка 1.x отказывает с кодом 2 (#797).
- **[Coordinator требует store]:** Coordinator 2.0.0 на `ledger.json` версий 1–3 завершается с кодом 2 и называет в remedy `harness-runtime migrate` (#814).
- **[Новый проект на runtime store]:** Проект без состояния оркестрации получает store командой `harness-runtime init --repo <repo> --approved-by <человек> --approved-at <время RFC 3339> --reason <текст>`, без файлового ledger и без `migrate`. Команду выполняет человек: approval проверяется как у `migrate`, approver `policy:` отклоняется. Повтор отвечает `already_initialized: true` без записи, а ledger версий 1–3 и записи 1.x команда отклоняет кодом 2 с remedy `harness-runtime migrate`. Coordinator больше не создаёт файловый ledger: `batch create`, `batch plan` и `ledger reset` на проекте без состояния завершаются с кодом 2, ничего не пишут и называют в remedy `harness-runtime init`. `harness health` показывает для такого проекта `warn` с этой командой, `migrate` на пустом состоянии (`nothing_to_migrate`) ведёт к ней же. `serve` store не создаёт. ADR 0036 (#1146).
- **[Migrate по approval]:** `harness-runtime migrate` и `rollback --to-legacy` требуют `--approved-by`, `--approved-at` и `--reason` и выполняются только человеком. Порядок перехода и отката — в [руководстве миграции на 2.0](https://pvmalove.github.io/agent-harness-next/guides/upgrade-2-0/) (#803, #826).

### Added

- **[Видимость harness-runtime serve]:** Быстрый старт (ru и en) получил раздел «Runtime»: однократный `migrate`, постоянный `serve`, проверка `coordinator.py runtime status`, команды, которые без runtime отказывают, и пример сервиса `systemd --user` с оговоркой про `PATH` и `XDG_RUNTIME_DIR`. `harness health` получил проверку `orchestration.runtime`: `ok` с pid, версией и протоколом; `fail` с командой `harness-runtime serve --repo <repo>` в «Как исправить», если runtime не отвечает; `fail` с remedy клиента при отказе runtime; на файловом ledger проверка пропускается. Отказ `orchestration.ledger_summary` при неотвечающем runtime получил ту же команду. Веб-консоль показывает в шапке «Runtime: работает / не отвечает», а на Главной, в Оркестрации, Восстановлении и Контейнерном запуске — копируемую команду запуска; снимок store получил поле `start_command`. `harness cleanup` и `harness worktree-remove` при неотвечающем runtime называют причиной «runtime does not answer: start `harness-runtime serve --repo <repo>`» вместо «Git or ledger state unavailable» (#1081).
- **[Ход работы in-process воркера]:** Вкладка «Ход работы» веб-консоли для in-process dispatch, у которого нет потока событий, показывает причину, время heartbeat, self-report модели с отметкой совпадения и последние 20 чекпоинтов из ledger с их общим числом — и пока воркер работает, и после его остановки. Запись roster живой ленты `steps.subscribe` получила поле `observation` (код причины `in_process`, `heartbeat_at`, `self_report`, `checkpoints`, `checkpoint_count`); у других dispatch оно `null` (#1051).

- **[Автозапуск harness-runtime serve]:** В Claude Code hook `runtime-autostart` перед командой coordinator вызывает `harness-runtime ensure`: работающий serve переиспользуется, иначе запускается свой serve вне песочницы агента, и QA docker executor работает с ним. `Stop` и `SubagentStop` вызывают `harness-runtime release`; свой serve завершается сам, когда владельцев нет и store простаивает (нет живого dispatch, lease и очереди QA, незавершённого исполнения). Ручной serve не останавливается. Отказ serve, устаревшая сборка, отсутствие бинарника и песочница дают предупреждение с причиной и журналом `<repo-id>.serve.log`. Codex и Windows остаются на ручном запуске. ADR 0031. Чтобы получить hook, выполните `harness update` и соберите release-бинарник (#1088).

- **[Остановка и перезапуск runtime]:** `harness-runtime stop --repo <repo>` останавливает runtime репозитория тем же путём, что SIGTERM, через новую IPC-операцию `shutdown` и ждёт освобождения lock; без runtime отвечает `not_running`, повтор безопасен. `harness-runtime restart --repo <repo>` заменяет живой runtime без поиска pid. Коды выхода описаны в `site/docs/architecture/runtime.md`; контракт одинаков на Unix-сокете и Windows named pipe (#1053).
- **[Этапы и аннотации CI]:** Полный путь `verify.yml` идёт этапами: быстрый гейт `lint` (ruff, mypy, `cargo fmt`, Clippy, метаданные) и `docs` до тяжёлых наборов Linux и Windows, которые без него не запускаются; Linux-наборы берут одну debug-сборку `harness-runtime` из задания `rust`. Ошибки Clippy, ruff и mypy, упавшие тесты, непокрытые изменённые строки и находки проверок метаданных и терминов видны аннотациями на своих строках во вкладке «Files changed», а сводка показывает диаграмму итогов, свёрнутые traceback и команду повтора (#1059).
- **[Консоль: страницы веб-консоли выверены по макету после замечаний владельца]:** Каждая страница и вкладка веб-консоли сверена с макетом при ширине 1440 и 390 px. Блок «Здоровье» на Главной не выходит за рамку, полоса прогресса уже. На странице обновления diff показывает одну строку на файл, добавлены панели «Миграция runtime-store» (`update_harness.snapshot` получил аддитивные поля `store` и `store_target_schema`) и «Результат последнего запуска». Проект, Ход работы (5 последних сессий, 10 шагов и событий, таймлайн с осью времени), Оркестрация (анимация только живого шага, три карточки batch, Dispatch, «Все тикеты», один набор вкладок), Отчёты, Публикация, Диагностика, Доска задач, Harness (подблоки «Images» и «Networks / volumes»), Repo Map (подписи KPI, индекс с пилюлей свежести, стек-бар покрытия), Настройки (четыре KPI, панели «Конфигурация» и «Политики», редактор с панелью Schema) и Справка (README, карточки быстрых ссылок, частые вопросы ru/en) перестроены по блокам, порядку и плотности макета; в шапке у ветки иконка. Playwright обходит все вкладки каждой страницы на 1440 и 390 px: панели не выходят за рамки, axe-core не находит нарушений; проверяется только DOM (ADR 0029). Поля без источника показывают «нет данных» с причиной. Таблица аудита и пункты на приёмку владельца — `docs/design/web-console-mockups/parity-1066.md`.

- **[Консоль: веб-страницы приведены к принятому макету]:** Оболочка и десять страниц веб-консоли (Главная, Диагностика, Harness, Repo Map, Ход работы, Оркестрация, Отчёты, Публикация, Восстановление, Контейнерный запуск) повторяют блоки, порядок, заголовки, вкладки, фильтры, плитки и кнопки макета `docs/design/web-console-mockups/execution-console-prototype.html`. Шапка показывает «Harness next», реальную версию harness, репозиторий и ветку; бейдж pre-release появляется только при semver-суффиксе версии; счётчики меню берутся из снимка Главной. Kernel и протокол получили поля проекта, установки harness, runtime store, drift, областей здоровья, последних сессий, KPI и аналитики ledger, тайминги живых шагов и представление публикации; поля покрыты тестами Python. Поле без источника данных показывает явное «нет данных», демонстрационные значения макета в консоль не попадают. Таймлайн собирается на клиенте из заголовков отчётов и времени начала этапов; матрицу evidence строит kernel с одним определением устаревшего QA-запуска на batch, и KPI stale evidence считает устаревшие ячейки этой же матрицы. Пустое состояние соединения показывают только страницы данных Главной; остальные страницы показывают пустоту своих данных. Блоки без места в макете (решения, Lock ledger, обслуживание, этапы контейнерного маршрута, действия восстановления) идут после блоков макета, подтверждения необратимых действий сохранены. Playwright проверяет структуру DOM каждой страницы при ширине 1440 и 390 px без горизонтальной прокрутки и состояния соединения на каждой странице, без сравнения снимков экрана (ADR 0029). Вместо «нет данных» kernel теперь отдаёт: «Почему важно» для каждой проверки `harness health`, вид символа и покрытие source/docs/tests/excluded в Repo Map, инвентарь движка контейнеров (только чтение, с причиной сбоя каждой пробы), почасовой тренд latency гейтов за сутки и вердикт Release Gate ready/blocked/unknown на Публикации и вкладке «Готовность». Таблица паритета — `docs/design/web-console-mockups/parity-1039.md`.

- **[Консоль: смена статуса тикета на доске задач]:** Карточку доски задач можно перенести в другую колонку перетаскиванием или выбрать статус в модальном окне тикета. Во время перетаскивания колонки подсвечиваются как допустимые или запрещённые, запрещённый перенос показывает причину: открытые блокеры, активный batch, колонки «Review / QA» и «Готово», закрытый тикет, переход только через «Готово к работе». Разрешённый перенос требует подтверждения и выполняется как мутирующий job сервера `board-status` (класс «внешнее изменение»); при другой активной мутирующей команде он получает отказ «занято», после ответа команды доска перечитывается с `force`. - **[Удержание batch до `recovery resume`]:** Удержанный batch отказывает в `dispatch propose`/`create`, `send`, `self-report`, `checkpoint`, `report submit`, `qa run`, `dispatch publish`, `batch decide`, `batch resume`, `resume-stop`, `rewind` и в реакции на завершённое исполнение (`reaction_error` в `dispatch status`) кодом 2 без записи. `batch auto-decide` записывает остановку `integrity-failure`/`operational-hold` и никогда не делает abandon, attention получает причину `operational-hold`, а decision packet — пустые `options` и маршрут восстановления. - **[Супервизор процессов runtime]:** На Linux `harness-runtime` сам запускает внешний worker dispatch, созданного на runtime store, из сохранённого brief: `dispatch send` больше не вызывает адаптер, а повтор возвращает тот же receipt без второго запуска. После SIGKILL runtime новый runtime усыновляет процесс по меткам или записывает исполнение `lost`, останавливает worker по сроку `worker_execution_timeout_seconds` (SIGTERM, затем SIGKILL группе), доводит до конца остановку, начатую до рестарта, и освобождает аренду только после доказанного выхода всей группы процессов, в том числе усыновлённой; `dispatch status` показывает исполнение, а отчёт, присланный до выхода worker, принимается после выхода, при потере исполнения остаётся в статусе как `held_report`, а при отказе записи после выхода — ожидающим с причиной в `reaction_error` (#805).
- **[Супервизор процессов runtime на Windows]:** На Windows `harness-runtime` запускает внешний worker в именованном Job Object `Global\harness-runtime-execution-<operation_id>` без `KILL_ON_JOB_CLOSE`, поэтому исполнение переживает runtime. Процесс стартует подвешенным, в своей группе процессов и со своей скрытой консолью, попадает в job и только потом возобновляется; receipt записывает pid, время создания процесса и имя job, а процесс с тем же pid и другим временем создания исполнением не считается. Runtime после рестарта находит job по имени: усыновляет лидера незавершённого запуска, которого запустил runtime из аренды intent, записывает код выхода лидера, которого держит открытым handle, и доводит до конца остановку, начатую до рестарта. По сроку исполнение получает `CTRL_BREAK` через helper `harness-runtime ctrl-break`, затем `TerminateJobObject`, а аренда освобождается, только когда в job не осталось живых участников исполнения; хост скрытой консоли участником исполнения не считается. `hello` на Windows перечисляет `execution.launch` и `execution.observe`; контейнеры и QA-прогоны остаются только на Linux. Контрактные тесты Job Object идут в CI-задании `runtime-ipc-windows`; решения записаны в ADR 0022, раздел «Решения реализации #806» (#806).
- **[Параллельные batch и снимки чтения store]:** Coordinator-ы разных batch пишут в runtime store параллельно. Команда читает store из одного снимка (`state.read` с `snapshot`: `open`, id снимка и `close`; простой 30 с, жизнь 120 с, предел числа снимков; истёкший снимок — повторяемый `store_busy`), поэтому коммит другого batch между её чтениями не даёт `ledger_busy`, а `dispatch status`, `batch auto-report`, `batch decision-packet` и `qa status` не ждут писателя и видят состояние до незавершённой транзакции. Схема store 3 добавляет singleton-строку `generation`: запрос, который создаёт batch или меняет его состояние, повышает её ревизию, а решения по всем batch (`concurrency_budget` в `dispatch create`, дубль работы в `batch create`) передают `expected_generation_revision`, и из двух команд с одним решением коммитит одна (`revision_conflict` по `generation`). `harness-runtime serve` переводит store версий 1 и 2 на версию 3 при старте (#804).
- **[Lease QA-lane с fencing и снятием мёртвого владельца]:** QA-lane в store — singleton lease с монотонным `fencing_token`, который строка lane хранит и после освобождения. Типизированные операции `state.write` (`lease_acquire`, `lease_release`, `lease_heartbeat`, `lease_reap`, `lease_clear`) и чтение `qa.lane.inspect` заменяют общие мутации `qa-lane/lease.json`, которые runtime теперь отклоняет. Runtime записывает идентичность владельца из ядра (`SO_PEERCRED`, `GetNamedPipeClientProcessId`): host, boot, PID-namespace, pid и время старта процесса. После `expires_at` lease снимается только вердиктом `owner-dead`; `owner-alive`, `owner-pid-reused`, `owner-in-other-environment`, `owner-on-another-host` и `owner-unknown` его сохраняют, а запрос получает `lease_held` со `stale_heartbeat`. Следующий `qa run`, `integration local-qa` или `ledger release-lock` снимает lease мёртвого владельца без `--force` с записью audit (владелец, идентичность, наблюдение, вердикт, время) и восстановлением его QA dispatch. Владелец продлевает lease heartbeat каждую треть нового ключа `lease_ttl_seconds` (по умолчанию 300 с). `qa status` получил `stale_heartbeat`, `dispatch status` — объект `qa_lane`, `ledger lock-status` — объект `qa_lease` с вердиктом и `release_available` (#804).
- **[Запуск `harness console --web`]:** Команда запускает Сервер консоли проекта, печатает URL с токеном, открывает браузер (`--no-open` отключает) и завершается; уже работающий сервер переиспользуется (#865).
- **[Запись lifecycle через runtime store]:** При `ledger.json` версии 4 каждая мутация batch и dispatch идёт в Rust runtime операцией `state.write` (протокол 1.1): блок `_ledger_lock` команды стал единицей записи, примитивы ledger накапливают мутации, чистый выход отправляет по одной транзакции `BEGIN IMMEDIATE` на batch с CAS по `revision` каждой прочитанной строки, порядком строк `batch` → `qa_lane` → `generation`, записью `operations` (повтор с тем же `operation_id` возвращает сохранённый результат, тот же id с другим запросом — `idempotency_conflict`) и одной записью audit на мутацию. Python не открывает `runtime.db`, не берёт `.coordinator.lock` и не имеет запасного пути записи; `revision_conflict`, `store_busy` и `runtime_unavailable` — разные ошибки с кодом выхода 2 и кодом в скобках первой строки REMEDY. Каждый внешний блок `_ledger_lock` читает свежий снимок store (опрос `dispatch wait` видит новый `reported` и heartbeat), отказ `qa run` по доступу и отказ `dispatch create` по `needs_attention` сохраняют свои записи, недостающий checkpoint audit строится до транзакции записи, а ошибка чтения store при проверке даёт `store_busy` или `internal`, а не `invariant_violation`. Схема store версии 2 добавляет таблицу `operations`, `revision` строк `dispatch_status`, `qa_queue` и `record`, столбец `execution_state` с CHECK терминального состояния dispatch и singleton `audit_checkpoint`; `harness-runtime serve` переводит store версии 1 на версию 2 при старте, а store более новой версии отказывает без записи. Реестр `systemFields.v1` получил `runtime.operation_state` и `runtime.execution_state` (#801).
- **[Checkpoint audit-цепочки и `ledger validate --full`]:** Обычная команда проверяет только записи audit после checkpoint, запись двигает checkpoint, а удалённый или повреждённый checkpoint означает полную проверку и перестраивается без ошибки. `coordinator.py ledger validate --full` (операция `state.validate`) пересчитывает цепочку от genesis без checkpoint, сверяет её с якорем импорта, манифестом и хешами legacy audit, запускает `integrity_check` и сверяет каждую строку, записанную командой, с последней записью audit её пути: находятся удаление, вставка и перестановка записей. `ledger migrate`, `ledger clean` и `ledger reset` в эпохе runtime store отказывают кодом 2 (#801).
- **[Команда `harness-runtime migrate` и runtime store]:** `harness-runtime migrate --repo <repo>` переводит state-каталог установки 1.x (ledger версии 3) в SQLite-store `state/runtime.db` одной операцией по ADR 0020: предусловия (нет QA-lease и очереди, нет dispatch в `dispatched`/`working` — строже ADR 0020, живость worker-а не проверяется, поэтому оператор дожидается отчётов или переводит зависшие dispatch в `abandoned`, структура и хэши ledger и контракт batch проходят Rust-проверку, равную `ledger validate`: запечатанные recovery events, startup evidence, context pressure, carried items, attention, записи `auto` и равенство batch его immutable plan; состояние, которое отклоняет `ledger validate`, отклоняет и migrate кодом 2, а списки полей и значений Rust сверяет с Python тест), legacy-замок `.coordinator.lock` с `owner.json` (`operation: runtime-cutover`) и удерживаемым `flock`, снимок state в `.harness/orchestration/state-snapshots/<utc>/` с `snapshot-manifest.json` и `fsync`, импорт в `runtime.db.importing`, сверка паритета в Rust (sha256 канонического JSON каждой записи выбранного поколения и проекции строк, расхождение допустимо только в полях правила repair, чью запись `migration-repair` с `before_sha256` и `after_sha256` хранит audit; legacy `audit/*.json` и `lock-audit/*.json` лежат в `legacy_audit` побайтно, первая запись цепочки `legacy-import` несёт `manifest_sha256`), повторный хэш state против снимка и точка фиксации: `runtime.db`, `AUTHORITY.json`, затем `ledger.json` с `version: 4` — старая установка 1.x отказывает с кодом 2. Каждый отказ и сбой печатает `REMEDY:` с действием оператора. Команда печатает одну JSON-строку и завершается с кодом 0 (повтор после точки фиксации — `already_cut_over: true` без изменений), 2 (отказ по предусловию, ничего не изменено), 3 (сбой после начала, частичный store удалён, authority прежняя) или 4 (legacy-запись во время импорта, расхождение паритета). Живой владелец замка не снимается, мёртвый — только по вердикту `owner-dead` с записью в `lock-audit`; legacy-поколения и audit не переписываются. Импорт чинит #781: batch с `risk_reassessment_required = true` без `risk_reassessment_candidate` получает `risk_reassessment_pending_next = true`, запись `migration-repair` хранит `before_sha256`, `after_sha256` и правило, а CHECK таблицы `batch` не принимает такую строку. Каноническая форма JSON Rust совпадает байт в байт с `_canonical` Python (golden-фикстура проверяется обоими языками). В debug-сборке `HARNESS_RUNTIME_TEST_PAUSE_AT` и `HARNESS_RUNTIME_TEST_FAIL_AT` останавливают или ломают каждый шаг для SIGKILL-тестов; в release-сборке этих хуков нет. Quarantine и overlay system-fields старой миграции не переносятся: состояние с неизвестным или нечитаемым значением отклоняется целиком (#797).
- **[Откат `harness-runtime rollback --to-legacy`]:** Команда `harness-runtime rollback --to-legacy [--repo <repo>] --approved-by <человек> --approved-at <время RFC 3339> --reason <текст>` возвращает state-каталог из runtime store установке 1.x по ADR 0020, раздел 5. Пустое поле approval и время не в формате RFC 3339 или из будущего отклоняются кодом `malformed_request`, approver `policy:` — кодом `policy_denied`. Команда держит замок экземпляра `serve` (работающий `serve` — код 2, `lease_held`), берёт legacy-замок с `operation: runtime-rollback` и отказывает кодом 2 без записи, если схема store новее runtime, в QA-lane есть lease или очередь либо исполнение dispatch в `launching`, `running`, `stopping` или `unknown`; dispatch в `dispatched` или `working` с остановленным исполнением или без него экспортируется как есть. Затем Rust пишет неизменяемый архив `state/runtime-export/<store_id>.tar` (детерминированный ustar: `store_meta.json`, вся audit-цепочка, operations, revisions и `execution_state`, `qa_lane.json`, `MANIFEST.json` с sha256), новое поколение формата v3 со всеми каталогами записей, побайтной копией legacy audit импортированного поколения и записью `runtime-rollback`, и сверяет поколение со store правилом паритета импорта. Store получает audit-запись `runtime-rollback` с sha256 архива, выходит из WAL и становится read-only; `runtime.db` не удаляется, версия схемы не понижается. `AUTHORITY.json` получает `authority: file-ledger`, `rolled_back_from`, поколение и архив, а замена `ledger.json` на `version: 3` — точка фиксации. Повтор после неё отвечает `already_rolled_back: true` с кодом 0, повтор после сбоя продолжает с последнего завершённого шага. Архив, который незавершённая попытка установила до audit-записи `runtime-rollback`, не назван ни одной записью, поэтому повтор заменяет его архивом изменившегося store; архив, названный этой записью, не заменяется. Коды выхода 0/2/3/4 те же, что у `migrate` (#803).
- **[Чтение `dispatch status`, `batch list`, `batch decision-packet` и `qa status` из store]:** При `ledger.json` версии 4 эти четыре команды получают записи через `runtime_client` (операция `state.read`, записи в форме legacy-файлов из одной read-транзакции и ревизия store) и не открывают ни файловый ledger, ни `runtime.db`; замок ledger не берётся, а `store_busy` и `revision_conflict` показываются как прежний `ledger_busy`. Runtime подключает store лениво: `hello` называет `store_id` и feature `state.read`, когда store — authority. `dispatch status` в этой эпохе не опрашивает движок и ничего не пишет, поле `report` пакета решения — адрес записи внутри store. Остальные команды coordinator при версии 4 по-прежнему отказывают с кодом 2; мутации через store остаются за #801 (#797).
- **[Сервер `harness-runtime serve` и `coordinator runtime status`]:** Rust workspace `native/harness-runtime` (crates `contracts`, `ipc` и бинарь `harness-runtime`, без `unsafe`) слушает Unix domain socket `$XDG_RUNTIME_DIR/harness/<repo-id>.sock` (без `XDG_RUNTIME_DIR` — каталог `/tmp/harness-<uid>` на Unix и `%LOCALAPPDATA%\harness` на Windows, вне любого репозитория). Каталог `0700`, сокет и файл токена `<repo-id>.token` — `0600`; uid клиента проверяется через `SO_PEERCRED`, токен предъявляется в `hello`. Кадр — длина `u32` big-endian и JSON UTF-8; `hello` согласует версию протокола по общему major. `runtime_client.py` повторяет запрос с тем же `operation_id` до `request_deadline`; недоступный runtime даёт `runtime_unavailable` без записи в обход, ошибка протокола — код 2 и `[<код>]` в первой строке `REMEDY:`. Коды ошибок и домены отказов runtime добавлены в реестр `systemFields.v1`, drift-проверка Python и Rust входит в CI. Один runtime на репозиторий обеспечивает файл блокировки `<repo-id>.lock` в каталоге runtime, а linked worktree обслуживается тем же runtime, что и основной checkout: адрес строится от общего git-каталога, корень рабочего дерева в него не входит, а `hello` сверяет `repo-id`. Каталог выбирает одно правило в Rust и Python, проверенное общей фикстурой. Runtime создаёт каталог `0700` и отказывает с `unauthorized_peer`, если каталог — symlink, принадлежит другому пользователю или открыт группе или прочим, либо его родитель доступен на запись другим без sticky bit; существующий каталог с правами шире `0700`, в том числе `$XDG_RUNTIME_DIR/harness`, больше не исправляется молча, а даёт отказ с remedy. Сервер держит разделяемый `flock` на каталоге, чтобы `systemd-tmpfiles` не удалил сокет и токен живого runtime, а клиент проверяет каталог до чтения токена. Запуск `serve` без `XDG_RUNTIME_DIR` требует записи в `/tmp`; сервис с `PrivateTmp=yes` и клиент вне него не видят друг друга, поэтому для сервисов задайте `XDG_RUNTIME_DIR`. Команда `runtime status` только читает (ADR 0021, #792, #807).
- **[Наблюдение за worker]:** `dispatch observe` читает локальные события, `terminal.json` и ledger без вызова модели; консоль показывает выбранный worker в разделе рабочих сессий с ответами на запросы native permissions. Закрытие, повторное открытие и reconnect панели не останавливают worker и не запускают второй процесс (#716).
- **[Ранний сбой worker]:** `execution_policy.worker_startup_timeout_seconds` (120 секунд по умолчанию) закрепляется в brief. `dispatch wait` возвращает `startup_failed` при доказанном раннем выходе, `startup_timeout` при пропущенном первом self-report и `worker_exited_without_report`, если после self-report процесс исчез без отчёта; последнее событие ничего не меняет в ledger (#716).
- **[Перезапуск одним решением]:** `batch resume-stop --restart` заменяет цепочку из двух подтверждений одним решением человека для доказанно остановленного worker. Причина повтора architect (`retry_reason`) попадает в brief из `--note`, пустая заметка отклоняется (#716).
- **[Доставка отчёта после отказа инструмента]:** `report submit --relayed-by --relay-reason --source-sha256` доставляет уже существующий файл отчёта и записывает отправителя в audit (#716).
- **[Диагностика sandbox_denied]:** Если ledger недоступен для записи (EROFS, EACCES, EPERM), команды возвращают `sandbox_denied` с путём и подсказкой про `sandbox.filesystem.allowWrite`, а не traceback `OSError` (#716).
- **[ChangeImpact и план проверки]:** `harness/repo_map/change_impact.py` строит по diff `base..candidate` (`git diff -M --name-status`) `ImpactSet`: `changed`, `impacted_modules` (обратное транзитивное замыкание по import-рёбрам графа Repo Map, построенного в процессе, без отсечения по бюджету токенов), `related_tests` без отсечения по первым N файлам и `unknown` с причинами. Изменение `conftest.py` любого уровня, `pyproject.toml`, `uv.lock`, `Makefile`, `.github/**`, скриптов verify, `harness/CAPABILITIES.json` или `skills/**`, удалённый или переименованный модуль с импортёрами, файл не на Python, динамический импорт, недоступный парсер (`graph-degraded`) и превышение порога `related_tests` выставляют `unknown`. Новый необязательный ключ `verification_plan_policy` (`max_related_tests`, `stages`) замораживается в batch при `batch create`; `dispatch propose` для developer-retry, code-review и qa строит `verification_plan` (стадии с `stage_id`, `kind`, `argv`, `timeout_seconds`, `selection`, `nodeids`, `environment_fingerprint`): стадия pytest получает `focused` по `ImpactSet` либо `full` при `unknown` и для qa. План лежит в brief, а его digest привязан к approval как `verification_plan_sha256`. Batch без ключа работает по замороженным командам, как раньше. Словари `selection` и `kind` зарегистрированы в `systemFields.v1` как `verification_plan.selection` и `verification_plan.stage_kind`. `repo_map_policy` замораживается в batch вместе с политикой плана, политика обязана содержать стадию `pytest`, а digest образов docker входит в `environment_fingerprint`. Файл Python, скрытый от графа политикой Repo Map или не разобранный парсером, который называет затронутый модуль, ставит `unknown` (`unseen-importer`); граф `base` при удалении или переименовании строится только по изменённым файлам. Исполнение плана, failed-only, кэши и полный clean-room gate на publish остаются за другими задачами ADR 0023 (#793).
- **[Отказ `impact_not_covered`]:** `dispatch propose` и `dispatch create` для code-review и qa отказывают с кодом 2 и перечнем тестов, если стадия pytest плана не `full` и не выбирает какой-либо из `related_tests` `ImpactSet`. Проверка машинная: текст отчёта роли её не заменяет (#793).
- **[Повтор только упавших тестов и stage evidence]:** `scripts/verify.py --worktree-cache` держит кэши mypy и pytest и JUnit предыдущего прогона в `.harness/.sandboxes/cache/<worktree-id>/<environment_fingerprint>/`: кэш другого worktree или другого `environment_fingerprint` не читается, а при `HARNESS_VERIFY_COLD` (его ставит gate runner только в clean-room QA, но не при локальном запуске через обёртку `test_summary.py`) флаг отказывает с кодом 2, так что clean-room QA остаётся холодным. `--failed-only` запускает одну стадию pytest с точными nodeid упавших тестов из JUnit того же кэша; переименованный или исчезнувший nodeid переводит выбор в `focused` (уцелевшие тестовые файлы целиком), пустой выбор и pytest, не собравший ни одного теста, дают `not_run` с кодом 5, а не `pass`. `--failed-first` по-прежнему только порядок и записывается как выбор `full`. `--evidence-dir` пишет `stage-evidence.v1` для mypy, pytest и clean-room: раздельные файлы stdout и stderr с sha256, код выхода, длительность, упавшие nodeid из JUnit и `not_run` для недошедших стадий. Одна схема (Python `harness/gate_runner/stage_evidence.py`, Rust `contracts::stage_evidence`) читается обеими сторонами по общему golden-файлу и сверяется со словарями `systemFields.v1`, поэтому Rust QA executor пишет её без изменений. Gate runner пишет такое же evidence для каждой команды (раздельные очищенные потоки, длительность, nodeid из `HARNESS_STAGE_JUNIT_XML`), помечает окружение clean-room прогона холодным и хранит документ и потоки как неизменяемые `qa-artifacts`, связанные хвостовой строкой `stage-evidence:` журнала QA в `qa run` и локальном QA. Недошедшая команда получает `not_run` всегда, а не только при `qa_preparation`, в том числе в `checks_run` отчёта QA. Failed-only, focused и кэшированные результаты publish не разрешают: его разрешает только полный clean-room прогон на итоговом SHA (#798).
- **[Egress-proxy для `network.hosts`]:** Контейнерный исполнитель `docker` принимает непустой `network.hosts`: для каждого dispatch он создаёт сеть `--internal` и отдельный sidecar из закреплённого digest образа `container.proxy_image`, а worker получает только эту сеть и переменные `HTTP_PROXY`/`HTTPS_PROXY` (в том числе строчные). Прокси пропускает HTTP и `CONNECT` только к хостам плана на портах 80 и 443, один раз резолвит имя и отказывает для loopback, link-local, unspecified, multicast и IP-литералов; остальное получает 403. Имя хоста LLM API нужно указать явно, а протоколы кроме HTTP(S), включая ssh git, не поддерживаются. При пустом списке хостов worker по-прежнему запускается с `--network none` без sidecar. Код прокси и `Dockerfile.proxy` поставляются в `.harness/container/` как часть `backend-orchestration` с контролем дрейфа; харнесс образы не собирает и не скачивает. Сеть, sidecar и worker получают метки `harness.dispatch`, `harness.repository`, `harness.plan_digest`, а сбой на любой ступени запуска удаляет все созданные объекты в обратном порядке (#706).
- **[Контейнерный clean-room QA]:** Если в `access_policy.operations.qa` задан контейнер, `qa run` закрепляет digest образа и `qa_execution` при propose и исполняет каждую QA-команду в своём foreground-контейнере `--rm --init` через `harness-runtime` (`qa.run`, протокол 1.4); Git и checkout остаются на хосте. stdout и stderr каждой команды сохраняются раздельно с реальным кодом выхода, а окончание классифицируется: `tooling`, `timeout` и `unknown` дают отчёт `blocked`, `infrastructure`, `environment_preparation` и прерывание дают новую попытку того же dispatch без отчёта и без траты бюджета developer-а. SIGINT, SIGTERM и срок команды останавливают контейнер с grace, сохраняют частичное evidence и освобождают lane. Пересобранный образ или отсутствующая переменная окружения блокируют прогон до первой команды; проект без этой настройки остаётся на хост-QA (ADR 0022, ADR 0023, ADR 0025, #810).
- **[Базовый образ worker-а]:** Payload `.harness/container/` получил необязательный `Dockerfile.sandbox`: Debian slim с тегом по дате, `git`, `curl`, `jq`, Python с закреплённым `uv` и Node.js, без `ENTRYPOINT`, `USER`, `VOLUME` и секретов. Проект собирает его сам командой `docker build` или `podman build` из заголовка файла и строит на нём свой образ worker-а; исполнитель по-прежнему принимает любой совместимый образ, а харнесс образы не собирает, не скачивает и не публикует. Файл поставляется с `backend-orchestration` с контролем дрейфа (#710).
- **[Руководство по контейнерному исполнителю]:** `backend-orchestration` ставит англоязычное руководство `.harness/docs/container-executor.md`: предпосылки для Docker и Podman, конфиг и overrides, совместимость образа worker-а, команды сборки образов worker-а и proxy, кэши, переменные окружения по имени, allowlist хостов, блокеры с remedy, очистка и пример проектного адаптера с маркером `HARNESS_EXECUTOR`. Пример сохраняет native approval агента и не содержит auto-approve и отключения его sandbox. Руководство прямо называет Podman и rootless Docker непроверенными настоящим smoke (#710).
- **[Smoke с настоящим Docker в CI]:** Новый job `docker-smoke` в GitHub Actions собирает базовый образ, проектный образ worker-а на нём и proxy-образ, затем через публичные команды coordinator, настоящий `harness-runtime`, Git worktree и store проверяет worker-а и контейнерный QA: владельца файлов на хосте, HTTP(S) к разрешённому хосту через proxy, `403` для другого хоста и отсутствие прямого выхода, код выхода QA-команды в отчёте и удаление всех объектов dispatch. Тесты помечены маркером `docker_smoke`, который `pyproject.toml` отбрасывает во всех прогонах pytest по умолчанию, поэтому `make verify` их не запускает, а провал smoke виден в CI; job проверяет только rootful Docker (#710).
- **[Контейнерный worker в Rust runtime]:** На Linux с runtime store контейнер worker-а docker-dispatch запускает, останавливает по сроку и удаляет сам `harness-runtime`, а Python больше не вызывает `docker` или `podman`, поэтому на хосте с Podman ни одна команда не уходит в `docker`. Запуск отклоняется до обращения к движку, если план открывает контейнеру сокет движка или каталог runtime, в том числе через symlink; логи и код выхода worker-а сохраняются до удаления его контейнеров, а `harness cleanup` не трогает объекты другого репозитория, живые исполнения и volumes. На файловом ledger и вне Linux `dispatch preflight` блокирует такой dispatch и подсказывает, что сделать (ADR 0022, ADR 0025, #708, #807).
- **[Слияние hooks при установке]:** `harness init`, `adopt` и `update` сливают управляемые hook-записи в `.claude/settings.local.json` по пути команды `.claude/hooks/<скрипт>`: недостающие записи добавляются, устаревшие заменяются, записи пользователя сохраняются, `--force-seed-file` и `--force-seed-files` по-прежнему заменяют файл шаблоном целиком. Запись, которую пользователь изменил, остаётся без изменений, а команда печатает `[WARNING]` и строки `hooks conflict`; повторный `harness update` ничего не меняет в файле и печатает строки `hooks merge` и `hooks check` (#799).
- **[Адаптер hooks второго runtime]:** Установка создаёт `.codex/hooks.json` из тех же скриптов `.claude/hooks/` с критическими guards и `require-bounded-check` на `PreToolUse` для `Bash`; файл сливается по тем же правилам, а запись интеграции называется `pvmalove-suite-codex-hooks`. Hooks на `Write` и `Edit`, `EnterWorktree` и `Skill` для него не подключаются, как и `mark-qa-gate-passed` на `PostToolUse`: этот runtime вызывает `PostToolUse` и после команды с ненулевым кодом выхода, а кода выхода в payload нет, поэтому hook записал бы маркер QA-гейта для упавшего прогона, а проектные hooks работают только после доверия слою `.codex/` и каждому hook по хэшу (#799).
- **[Проверка `hooks.policy`]:** `harness health` показывает действующий профиль hooks и его источник, эскалации, наличие, исполняемость и проводку критических hooks по каждому runtime, дрейф от шаблона и события, которых нет у runtime. Критический hook без события и без проверки вне hook даёт `warn`, а не молчаливый пропуск; проект без ключа `hook_policy` по-прежнему получает профиль `standard` без миграции `.harness/project.json` (#799).
- **[Профиль `standard` в навыках]:** `start-project` и `integrate-project` называют профиль `hook_policy` в манифесте и после `harness init` проверяют `.harness/project.json` и `hooks.policy`; `hook_policy` существующего проекта остаётся за его владельцем (#799).
- **[Поведенческие hooks ChangeImpact]:** Три advisory-hooks по матрице ADR 0024, раздел 2a, работают через конверт `hook_response.py` и общее тело `change_impact_hooks.py` и никогда не блокируют. `impact-first-touch` (`PreToolUse` `Write|Edit`, профили `standard` и `strict`) один раз за операцию сообщает модели о первом касании рискованного пути, влияние которого ChangeImpact не вычисляет по графу. `targeted-check-reminder` ведёт журнал касаний и на `Stop` и `SubagentStop` напоминает отчитать targeted-проверки brief в `checks_run`, если файлы менялись после отчёта; ход он не продолжает. `sensitive-path-recheck` (только `strict`) сообщает о каждой новой правке чувствительного пути и пишет evidence-запись. Повтор того же события в той же операции (`session_id` и `agent_id`) молчит, а новый digest или новая операция дают новое уведомление; маркеры создаются через `O_EXCL` в `.harness/.sandboxes/hook-events/`. Внутренняя ошибка, нечитаемый ввод и тайм-аут 10 с разрешают действие с диагностикой и пустым stdout; критичные guards по-прежнему блокируют. Значения зарегистрированы в systemFields.v1, `harness health` показывает новые строки в `hooks.policy` (#802).
- **[Fail-closed границы профиля `strict`]:** Под `strict` `dispatch propose` и `dispatch create` для code-review и QA, `qa run` до QA-lease и `dispatch publish` до push отказывают с кодом 2 и ошибкой `strict_impact_unknown`, если кандидат меняет чувствительный путь ADR 0024, раздел 2, а VerificationPlan не доказывает его ImpactSet. Запущенный dispatch решает по политике, которую закрепил его `hook_policy_sha256`; `minimal` и `standard` на этих границах не меняются, а команды восстановления не проверяются. По решению R1 все границы проверяет одна Python-функция coordinator-а: Rust runtime пока не исполняет ни одну из этих операций, а Rust-проверку `qa run` добавит задача, которая переводит исполнение QA в Rust (#802).
- **[Остаточные ограничения hooks ChangeImpact]:** Второй runtime подключает только `targeted-check-reminder` на `Stop` и `SubagentStop`; строки `Write` и `Edit` и журнал касаний ждут адаптера `apply_patch` (#830), поэтому до него напоминание там молчит. Hardlink на чувствительный файл обходит только предупреждение `sensitive-path-recheck`: авторитетны критический `protect-hook-policy` и diff-проверка границы `strict` (#802).
- **[Release Gate привязан к дереву кандидата]:** `dispatch publish`, `integration prepare` и `integration refresh` записывают неизменяемую пару `reports/integration-pair/<pair_id>.json` с `candidate_tree_sha` (`git rev-parse <candidate>^{tree}`), а `state.write` проверяет её поля. Новая read-only операция runtime `qa.evidence.verify` (протокол 1.6) выносит по сохранённому evidence пары вердикт `ok` или `refused` со списком нарушений: пару подтверждает только принятый полный QA-прогон с логом, stage evidence и потоками, проверенный local-QA или CI, принятый `integration collect-ci`; focused, failed-only и кэшированные результаты не подтверждают. В эпохе runtime store без `ok` `dispatch publish` ничего не пушит, а `integration next` вместо `handoff` возвращает `release-gate-refused`; Git-факты (голова issue-ветки, target в истории кандидата) проверяет Python в обеих эпохах. После merge `integration next --pull-request <n> --merge-commit <sha>` сравнивает дерево merge-коммита с `candidate_tree_sha`, и `/to-pull-requests` останавливается с блокером на `merge-tree-mismatch` (#812).
- **[CI-матрица сбоев и границ безопасности на seam 1]:** Новое задание `fault-injection` в GitHub Actions собирает debug-сборку `harness-runtime` с тестовыми hooks и запускает `pytest -m fault_injection tests/orchestration`: coordinator CLI против настоящего runtime, по одному тесту на каждый сценарий матрицы надёжности #784 (SIGKILL coordinator и runtime, потерянный ответ IPC, осиротевший worker, двойной запуск, повторно использованный PID, устаревший lease, частичный артефакт, подменённый образ OCI, SELinux EPERM, офлайн-установка зависимостей, конфликтующие batch) и на каждую границу безопасности (подменённая запись audit, сокет движка в монтировании, снятие чужого lease). Реестр `tests/orchestration/fault_injection_matrix.py` связывает сценарий с его тестом; при `HARNESS_REQUIRE_FAULT_INJECTION=1` выбранные помеченные тесты обязаны совпасть с реестром, а пропуск сценария становится провалом. Задание не перезапускает упавший тест и не терпит ошибку; маркер `fault_injection` не отбрасывается в обычных прогонах, поэтому `make verify` тоже выполняет эти тесты. Debug-сборка runtime печатает `INJECTED:<step>` в stderr, когда срабатывает отброс ответа `HARNESS_RUNTIME_TEST_FAIL_AT=<operation>:respond`, и тест потерянного ответа ждёт эту строку; в release-сборке hook отсутствует (#813).
- **[Файл effective policy hooks]:** `harness init`, `adopt` и `update` для `engineering-suite` и `backend-orchestration` записывают `.harness/hook-policy.json`: нормализованные профиль и эскалации из `hook_policy`, их `hook_policy_sha256`, набор критических guard-ов и SHA-256 шаблонов hooks. Digest считается только по разделу `policy`, поэтому он равен `hook_policy_sha256`, который закрепляет brief для той же конфигурации; повторный `update` без изменения конфигурации не меняет файл, а некорректный `hook_policy` завершает команду с кодом 2 и оставляет прежний файл. `harness health` (`hooks.policy`) сообщает об отсутствии файла или его расхождении с текущей конфигурацией как `warn`, а исправляет файл `harness update` (#829).
- **[TUI — клиент Сервера консоли]:** Перезапущенный процесс `harness console` до старта TUI подключается к Серверу консоли проекта по discovery-записи и токену (`Authorization: Bearer`) через WebSocket; без записи или при устаревшей записи он запускает сервер прежним путём. Если сервер недоступен, TUI не стартует: команда печатает причину и текстовый отчёт `harness health` и завершается с кодом 1 (ADR 0028). Ошибки клиента типизированы: сервер недоступен, токен отклонён, соединение потеряно, ответ не по протоколу, ответ с ошибкой. Перезапуск получает `--with websockets==<pin>`, при смене проекта консоль подключается к серверу нового проекта.

- **[Batch в hard cleanup]:** План и результат `harness cleanup --mode hard` называют `batch_id` и состояние batch у каждого worktree; worktree нетерминального batch по-прежнему защищён (#1015).
- **[Scope и план архитектора]:** Brief каждой роли содержит `allowed_paths` batch. Отчёт architect несёт необязательное поле `commit_plan`: `report submit` проверяет его правилами `--commit-plan-file` и отказывает при путях вне `allowed_paths`, а accept и `batch auto-decide` закрепляют его без файла плана (#1015).
- **[Дизайн архитектора в brief developer]:** Brief developer содержит `accepted_design` с id dispatch архитектора, `report_sha256` и `output` принятого отчёта (#1015).
- **[Context Package в preflight]:** `dispatch preflight` до регистрации Context Package отдаёт статус `not-registered` вместо пустого указателя (#1015).
- **[Окружение QA]:** Классификатор QA считает отсутствие C-компоновщика и слишком длинный путь сокета сбоем окружения (`qa-environment-failure`), а не дефектом кода (#1015).
- **[Test-author в health]:** Строка health называет поддержанный runtime и где его задать, уточняет, что preflight проверяет основной checkout, а in-process developer идёт обычным TDD (#1015).
- **[Наблюдение in-process]:** `dispatch observe` объясняет отсутствие потока событий у in-process воркера и показывает его чекпоинты; консоль выводит `stream_reason` (#1015).
- **[Контейнерный воркер]:** Architect, developer и code-review в контейнере исполнителя `docker` проходят `report submit` без ручного обхода: coordinator на хосте сам подтверждает воркера, а веб-консоль показывает его шаги. Контейнерный QA больше не требует переводить все роли на `external` (#1014).
- **[Консоль: справка сжималась в колонку в один символ]:** Страница «Справка» оборачивалась в класс `.help-screen` — карточку сетки экранов макета с колонкой 22px, поэтому текст на 1440×900 вытягивался на 14 000px. Обёртка страницы теперь `.help-page`.

- **[Approval старого store]:** Команда `harness-runtime repair-import-approval` восстанавливает отсутствующее human approval в store, мигрированном до #826, сохраняет данные после cutover и продолжает прерванную операцию по intent и backup. `--check` и полный validate объясняют необходимость repair; проверка исторических writer handoff принимает неизменные blocked-отчёты по правилу #850 (#970).

- **[Исполнитель тест-автора из настроек]:** Полный `/implement` наследует runtime/model/effort утверждённого developer, короткий `/fast-implement` использует явный профиль `project.json.test_author`. Общий selector обслуживает запуск, preflight и Health; нативный Agent наследует модель родителя вместо фиксированного `haiku`. Неподдержанный защищённый адаптер даёт `runtime_unsupported`, без подмены выбранного CLI. Live-проба также использует настройки developer (#993).
- **[Workdir `exec_command` в `block-direct-master`]:** `direct_commits.py` берёт каталог запуска из `tool_input.workdir` вызова `exec_command`, если он задан, и разрешает относительный путь от `cwd` payload. Раньше проверялся только `cwd` сессии, поэтому коммит в изолированном issue-worktree блокировался как коммит в защищённую ветку основного checkout. Явный `workdir` главнее `cwd`; нестроковый `workdir` блокирует команду fail-closed (#960).

- **[DNS и очистка сетей Podman]:** runtime подключает proxy к отдельной внешней сети с DNS, сохраняя worker во внутренней сети; при обнаружении сетей разбирает поля Podman `name`, `id` и `labels`, поэтому очистка удаляет обе принадлежащие dispatch сети. Проверки labels и порядка удаления сохранены (#943).

- **[Хост консоли в job на Windows]:** Супервизор процессов на Windows не считает хост скрытой консоли (`conhost.exe` системного каталога) участником исполнения. Исполнение, чей лидер вышел, получает `exited` с кодом выхода или `lost` и освобождает аренду, даже пока хост консоли ещё жив в job; раньше оно оставалось `running` до срока. Усыновление после рестарта runtime выбирает лидера, которого запустил runtime из аренды intent: родителя показывает снимок процессов, а лидер создан не раньше этого runtime. Хост консоли и процесс, созданный раньше лидера, лидером не становятся; если таких кандидатов нет при живых участниках исполнения или их больше одного, исполнение остаётся `unknown` с удержанной арендой. Windows-тесты супервизора печатают состав job строкой `JOB-MEMBERS` и ждут runtime, процессы и хранилище с ограниченным сроком, поэтому больше не висят до `timeout-minutes` задания `runtime-ipc-windows`. Поправки D1, D2, D3 и D6 записаны в ADR 0022, раздел «Решения реализации #806» (#921).
- **[Группа из одних зомби]:** Супервизор процессов на Linux считает группу пустой, если в ней остались только зомби: исполнение получает `exited` или `lost` по своим правилам, и аренда освобождается в той же транзакции. Раньше такое исполнение оставалось `running` или `unknown` с удержанной арендой до рестарта runtime. Пустоту доказывает только procfs PID namespace runtime без `hidepid`, а участник с хотя бы одним работающим потоком по-прежнему держит аренду (#909).
- **[Отказ записи stopping]:** Если хранилище отказывает в записи `stopping` после SIGTERM, runtime повторяет запись при повторяемом отказе и подбирает своего завершённого ребёнка, а не оставляет его зомби. Отказ навсегда оставляет исполнение `unknown` с удержанной арендой и без SIGKILL, и reconcile доводит его до `lost` (#909).
- **[QA-маркер во втором runtime]:** Навыки `qa-gate` и `to-pull-requests` находят `record-qa-gate-pass.sh`, когда `CLAUDE_PROJECT_DIR` не задан: путь берётся от основного worktree (первая запись `git worktree list --porcelain`), где установлен `.claude/hooks/`. Раньше путь становился `/.claude/hooks/…`, маркер не записывался, и `require-qa-gate` второго runtime блокировал создание PR после успешного `qa-gate`. В первом runtime команда по-прежнему берёт `CLAUDE_PROJECT_DIR` (#832).
- **[Вердикты legacy-замка на шаге 2 migrate]:** `harness-runtime migrate` и `rollback --to-legacy` судят legacy `.coordinator.lock` так же, как `ledger release-lock`: `owner-alive`, `owner-dead`, `owner-in-other-environment`, `owner-on-another-host`, `owner-unknown-recent` и `owner-unknown-stale` (3600 с от `acquired_at`); снимаются только `owner-dead` и `owner-unknown-stale`, отказ называет вердикт, а запись `lock-audit` — вердикт, владельца и время. Живость процесса на Windows теперь проверяется (`OpenProcess`, `GetExitCodeProcess`, `GetProcessTimes`) вместо отказа `owner-unprovable` (#804).
- **[Контекст до первого изменения кода]:** `context-package register --starting-file <путь>` закрепляет существующие ADR, модули и тесты для задач с ещё не созданными файлами. Регистрация принимает начальный snapshot до developer-отчёта, сохраняет пределы размера и политику путей и не переиспользует пакет, в котором нет явно запрошенных входов; write scope не расширяется (#897).
- **[External adapter после cutover]:** `dispatch send` экспортирует проверенный immutable brief из runtime store в приватный read-only JSON-файл внутри `.harness/.sandboxes/scratch/briefs/`, передаёт его adapter и сохраняет для worker после возврата команды. Конфликтующая копия отклоняется до запуска; файловый ledger использует прежний путь, Python не открывает SQLite (#897).
- **[Полный аудит после migration repair]:** `ledger validate --full` связывает legacy-путь записи `migration-repair` с live-строкой выбранного поколения и проверяет её `after_sha256`, затем все последующие изменения той же строки. Исправленный при cutover batch больше не вызывает ложный `invariant_violation`; подмена строки по-прежнему обнаруживается, audit и legacy-файлы не переписываются (#897).

- **[Проверка ветки перед коммитом]:** `block-direct-master` блокирует commit/push, если Git вернул ошибку при определении текущей ветки. Ответ `HEAD` с ненулевым кодом выхода больше не считается разрешённой веткой (#725).
- **[Хеш закреплённого runtime после cutover]:** Каталог `.harness/orchestration/state-snapshots` (снимок state, который делает `harness-runtime migrate`) не входит в хеш runtime, закрепляемый в batch: после cutover команды batch, спланированного до него, не отказывают с «the harness runtime changed after this batch was planned» (#801).
- **[Выходы из Настройки, Версий и Обновить Harness; секреты в Настройке]:** Номер раздела и меню на экранах Настройка, Версии конфигурации и Обновить Harness закрывают экран, как Esc, и затем открывают раздел, поэтому Главная обновляется; «Отмена» в подтверждении, поднятом с экрана Версий, оставляет пользователя на экране Версий. Значения секретов, уже записанные в `project.json` и `orchestration.json`, больше не попадают в интерфейс: страница просмотра (итоговые файлы и различия), редактор поля и различия версий показывают маску `••••••`, а применение, резервная копия, проверка устаревших данных и `reject_secrets` работают с настоящими данными.
- **[Восстановление незавершённого writer после blocked-отчёта]:** `batch rewind --preserved-commit --preserved-file` принимает также последний непринятый `blocked`-отчёт writer на его точном SHA. Человек подтверждает полный список файлов, recovery связывает их хэши с новым dispatch, а исходный отчёт остаётся неизменным. Это устраняет тупик tooling-retry при пропущенном `tooling_blocker.uncommitted_files`; обычный бюджет rewind, scope и независимые review/QA сохраняются (#837).
- **[Полная проверка внешнего worker]:** Native profile разрешает обеим ролям общий каталог `.harness/.sandboxes/runs/tests`, куда `make verify` создаёт временное окружение из связанного worktree. Остальные каталоги `runs` и соседние worktree остаются защищены (#836).
- **[Git refs внешнего worker]:** Native profile разрешает `packed-refs.lock` в общем Git-каталоге, чтобы обычный commit в связанном worktree не печатал отказ записи. Существующие остальные shared metadata, основной HEAD/index, config/hooks и служебные каталоги других worktree защищены; права исходников не расширены (#836).
- **[IPC внешнего worker]:** Codex adapter принимает явный `--network-access=enabled` для согласованной сетевой политики и локального socketpair IPC, необходимого asyncio; прежняя network-настройка workspace-write не переносится в named profile. По умолчанию сеть выключена, права исходников не меняются (#836).
- **[Проверки внешнего worker]:** Native profile адаптера разрешает обеим ролям служебные `.harness/.sandboxes/runs/qa` и `.harness/.sandboxes/logs`: обязательная bounded-wrapper теперь может подготовить временное окружение и сохранить лог, не получая запись в другие issue worktree (#836).
- **[Lifecycle внешнего Codex worker]:** Адаптер запускает `app-server` с native permission profile: read-only роль сохраняет исходники на чтение, но может записать self-report, heartbeat и completion report. Роль с записью получает доступ к Git-метаданным для коммитов в связанном worktree; общие config и hooks остаются на чтение. Перед передачей задачи адаптер сверяет модель, effort, CWD и профиль прав ответа `thread/start`; worker получает native identity своей сессии и сам регистрирует self-report. Несовместимый runtime или несовпадение параметров останавливают запуск без расширения прав (#836).
- **[Тест-автор в полном маршруте `/implement`]:** `test-author-preflight.sh` принимает необязательный `--worktree <путь>` и отвечает `checkout_mismatch`, если путь не совпадает с checkout скрипта или аргументы неверны, поэтому in-process developer отдельного worktree больше не получает `{"status":"ok"}` для основного checkout. Внешний transport автора не включает (`transport_unsupported`); любой отказ оставляет обычный TDD с названной причиной, не blocker. Новый clean-room сценарий `full_route_worktree` проверяет, что тест не попадает в основной checkout (#768).
- **[Временные данные QA и isolated runner]:** Команды `qa run` получают собственный `TMPDIR` в `.harness/.sandboxes/runs/qa/tmp-*`, который удаляется после прогона, а helper базы данных isolated runner создаёт каталог в `TMPDIR` вместо жёстко заданного `/tmp`. Внутри bubblewrap `/tmp` теперь, как hermetic `/tmp` в Bazel, — свой пустой каталог `.harness/.sandboxes/runs/isolated-test-<id>/tmp-*` на каждый запуск, удаляемый после него, а не tmpfs. Read-only `/tmp` внешнего sandbox больше не роняет QA (#769).
- **[Падение QA из-за окружения]:** Если QA gate упал по признакам окружения (`Read-only file system` или `Permission denied` на пути вне репозитория) и в выводе нет признаков дефекта кода, `batch auto-decide` не тратит developer-retry, а останавливает автоматический путь с причиной `no-automatic-route`/`qa-environment-failure` и remedy. Настоящее падение теста по-прежнему ведёт к retry (#769).
- **[QA-lease после занятого ledger]:** `qa run`, который после взятия QA-lease встретил ledger, занятый другой операцией, больше не оставляет lease на час. Освобождение QA-lane ждёт lock до 30 секунд, затем снимает lease и запись очереди своего dispatch и возвращает dispatch в `approved`, так что тот же dispatch сразу запускается снова. Если lock так и не освободился, ошибка называет dispatch, владельца lease и время его истечения, а `qa clear-stale-lease` после истечения lease возвращает такой dispatch в `approved` (поле `restored_dispatch_state` в ответе и записи восстановления). Lease другого владельца и lease нового запуска того же dispatch не снимаются (#776).
- **[Ветка задачи ниже базы интеграции]:** `batch create` отказывает с ошибкой `branch_start_missing_base` и не записывает batch, если ветка worktree не содержит свежий tip `origin/<integration_ref>`, который batch закрепил бы как базу. Раньше tip, сдвинутый между `git worktree add` и `batch create`, становился базой, и файлы чужих коммитов попадали в `changed_files`, scope warnings и оценку риска задачи. Remedy называет `git -C <worktree> merge --ff-only <база>`; coordinator сам ветку не двигает. Batch, заменяющий брошенный (`--supersedes`), и batch маршрута conflict-resolver так не проверяются: базу в их ветку приносит их собственный маршрут (#802).

## [1.5.1] - 2026-10-18

### Added

- **[Профили проверок batch]:** Необязательный ключ `verification_profiles` в `.harness/orchestration.json` задаёт команды developer и code-review для области путей. `batch create` замораживает команды первого профиля, чьи `paths` покрывают все `--allowed-path`; при частичном покрытии или без ключа batch получает общие списки, а clean-room QA по-прежнему выполняет `verification_commands` (#756).
- **[Быстрые проверки developer-retry]:** Необязательный ключ `retry_verification` (`lint` и `test_command`) даёт повторной попытке developer команды lint и одну команду тестов по `related_tests` её Context Package. Без связанных тестов или без ключа повтор выполняет обычные команды developer; первый developer-dispatch, code-review и QA не меняются, а `checks_run` по-прежнему сверяется с brief дословно (#757).
- **[Состояние lock ledger]:** Когда ledger занят, `ledger lock-status` сразу отвечает, кто держит lock, сколько он уже держится и когда его можно будет снять, не дожидаясь освобождения ledger. Та же сводка видна в разделе оркестрации консоли и обновляется на живом экране (#759).
- **[Принудительное снятие lock]:** `ledger release-lock --force --approved-by --approved-at --reason` снимает lock при любом вердикте только по одобрению человека и пишет запись аудита с контрольной суммой, которую проверяет `ledger validate`. Ни одна политика, включая `auto`, команду не запускает; в консоли она доступна с подтверждением (#759).

### Changed

- **[Параллельный pytest]:** `make verify` запускает pytest до восьми воркеров вместо четырёх, если хватает ядер (#758).
- **[Windows-проверки CI]:** Задание `verify-windows` отключено и сохранено в `verify.yml` закомментированным, `windows-latest` убран из матрицы пробы векторной памяти; Linux-проверки не изменились (#753).

### Fixed

- **[Lock воркера из sandbox]:** Lock записывает PID-пространство и загрузку владельца, поэтому `ledger release-lock` больше не принимает чужой процесс с тем же pid за живого владельца: lock остановленного воркера из sandbox снимается по таймауту. Записи старого формата проверяются, как раньше (#759).
- **[Очистка после squash-merge]:** Шаг очистки `/to-pull-requests` проверяет влитость ветки по состоянию PR, а не по `git branch -d`, который после squash-merge всегда отказывает. Удаление локальной ветки агент предлагает разработчику, а `git branch -D` выполняет разработчик (#753).
- **[Проверка метаданных в PR интеграционной ветки]:** CI больше не проверяет сообщения коммитов, которые уже есть в default branch. Раньше PR, вливающий свежий `master` в интеграционную ветку, падал на чужом опубликованном коммите, а исправить его сообщение уже нельзя. Новые коммиты PR проверяются, как раньше (#753).
- **[Конфигурация консоли без `project.json`]:** Раздел конфигурации консоли снова строит документ `project.json` по умолчанию. С 1.5.0 шаблон содержит плейсхолдер полей тестов, консоль его не заполняла и отказывала с ошибкой «требуется корректный JSON» (#753).

Сборка пишет только в пустые одобренные каталоги через временные backing-каталоги, тест читает артефакты без права записи; исходники и конфигурация остаются защищены. БД запускается только для выбранных SQL-тестов и завершается вместе с ними. Схема, CLI-флаги, `harness health` и preflight поддерживают настройки без изменения проектов, где они отсутствуют. Clean-room проверяет настоящий компилятор и PostgreSQL, включая rollback и ограничения; `HARNESS_REQUIRE_TEST_DATABASE=1` запрещает пропуск доказательства БД (#556).

- **[Тест-автор]:** Установка `pvmalove-suite` добавляет необязательный субагент `test-author`, его scoped guard `.claude/hooks/test-author-guard.py` и проверку активации `.claude/hooks/test-author-preflight.sh`. Субагент пишет один поведенческий тест и запускает его через `run-test.sh`: запись разрешена только внутри `test_paths` (зоны вида `<каталог>/**`), `Bash` только для вызова runner, а отказ возвращается мягким JSON с кодом 0 и не затрагивает dispatch и ledger. Preflight включает автора только при валидных `test_paths` и `test_runner`, подтверждённой изоляции, исправном guard и принятом в Claude Code доверии к проекту (`hasTrustDialogAccepted` для точного пути). Иначе он отвечает одной причиной (`project_untrusted`, `isolation_unavailable` и другие), а developer продолжает обычный маршрут. Поддержка ограничена Claude Code. Clean-room проверяет активацию, три состояния отсутствия доверия, мягкие отказы и настоящий поведенческий Red; `make test-author-probe` дополнительно запускает реальный Claude Code, который подтверждает срабатывание scoped hook и сам проходит цикл Red (#554). `make verify` и CI эту пробу не запускают: она требует учётных данных и тратит квоту.
- **[Изолированный запуск теста]:** Установка `pvmalove-suite` добавляет `.claude/hooks/run-test.sh <test-id>`: runner запускает один выбранный тест в песочнице bubblewrap, где production-код, `.git` и конфигурация runner доступны тесту и его дочерним процессам только на чтение, сокеты сервисов хоста в `/run` скрыты, а запись разрешена только в каталоги `test_paths`, временный каталог, кеш и отчёты запуска. Команда теста задаётся новым полем `test_runner` в `.harness/project.json`, а `test_paths` теперь описан в схеме и проверяется `harness health`. Новый проект получает оба поля флагами `harness init --test-path` и `--test-runner-command`; без флагов поля не пишутся. Без подтверждённой изоляции runner отказывает с понятной причиной и не запускает тест, а результат возвращает одной короткой JSON-строкой без вывода теста (#553).
- **[Цикл Red→Green→Refactor с тест-автором]:** Пока `test-author-preflight.sh` возвращает `ok`, developer ведёт каждый шаг реализации циклом с тест-автором: передаёт требование, seam, публичные сигнатуры и fixtures, проверяет ожидание по требованию до реализации и не ослабляет принятое ожидание ради Green. Статусы `red`, `needs_skeleton` и `contract_gap` обрабатываются явно; ошибки компиляции, импорта, fixture и окружения не считаются Red, а сразу зелёный тест не засчитывается. После трёх подряд неудачных вызовов по одному тесту действует обычный blocker, новых dispatch и состояний ledger нет. Clean-room сценарий со скриптованной моделью-заглушкой проверяет цикл (#555).
- **[Внешние runtime-адаптеры]:** Claude Code и Codex запускают отдельный worker в назначенном checkout по параметрам брифа. CLI устанавливает и обновляет адаптеры вместе с `backend-orchestration`, а настройки консоли показывают их состояние и требуют просмотра с подтверждением. Локальные файлы защищены от неявной замены; общий seed добавляет шесть разрешений для наблюдения за оркестрацией (#715).

- **[Запуск Claude worker в issue-worktree]:** Установка `backend-orchestration` добавляет `.harness/adapters/claude_worker.py` — runtime adapter для `transport: external`. Инструмент Agent не умеет стартовать subagent в существующем checkout (subagent стартует в основном checkout, `EnterWorktree` его там отклоняет), поэтому Claude in-process worker не может стартовать в `worker_worktree`. `dispatch send --adapter` запускает адаптер в `worker_worktree`, а он стартует отделённый headless `claude -p` на модели, effort и `allowed_tools` из брифа с `dontAsk`. Адаптер лежит вне хешируемого runtime-пакета, поэтому его установка не меняет пин открытого batch. Skill `implement` и руководство `worktrees.md` описывают оба пути: адаптер даёт настоящий cwd, а in-process subagent работает по абсолютным путям и `git -C`, и его self-report доказывает checkout, в котором он работает, а не cwd (#718).

### Fixed

- **[Восстановление незавершённой разработки]:** `batch rewind --preserved-commit` сохраняет явно подтверждённые коммиты и перечисленные через `--preserved-file` незакоммиченные файлы остановленного writer без отчёта или checkpoint. Следующий запуск проверяет сохранённый checkout; история, ручные согласования и бюджеты повторов сохраняются (#733).
- **[Кандидат после rewind]:** История и проверка ledger используют `source_dispatch_id` регистрации кандидата, поэтому повторный rewind после регистрации сохраняет читаемый ledger (#715).

- **[Правила технического русского]:** Правила письма для документации и журнала изменений собраны в `docs/technical-russian.md`: связный текст, точная терминология и формат Keep a Changelog без ограничения длины предложений (#645).
- **[Раздельная подготовка окружения QA]:** Параметр `qa_preparation` отделяет настройку окружения от выполнения проверок кода. Сбой инфраструктуры больше не списывает попытки разработчика (#618).
- **[Проверка прав доступа]:** Координатор проверяет права перед запуском QA, Git и публикации. При нехватке прав координатор останавливает операцию и выводит инструкцию по исправлению (#617).
- **[Классификация ошибок Git]:** Координатор точно определяет причину сбоя при операциях с Git. Система больше не подменяет отказ в доступе на ошибку конфликта слияния (#617).
- **[Автоматический путь auto]:** При `approval_policy: auto` координатор проходит путь от `batch approve` до принятого publish без человека. Политика согласует каждый шаг, а `batch auto-decide` принимает решения по отчётам и пишет их как `policy:auto` с evidence (#643).
- **[Остановки и итоговый отчёт]:** Закрытый список остановок прекращает автоматический путь и передаёт каждый следующий шаг человеку. Команда `batch auto-report` выводит итоговый отчёт до открытия PR; PR открывает только человек (#643).
- **[Первый коммит документов прожарки]:** `/to-spec` коммитит изменённые документы прожарки (`CONTEXT.md`, `CONTEXT-MAP.md`, ADR в `docs/adr/`) первым коммитом `docs: …` в новую integration-ветку эпика и публикует ветку с этим коммитом. Текущий checkout переключается на новую ветку, посторонние изменения в коммит не попадают. Хук `block-direct-master.sh` разрешает только такой коммит и только до публикации ветки (#644).
- **[Перенос неполных пунктов]:** Read-only роль перечисляет невыполненные пункты brief в `incomplete_items`. Координатор передаёт их целевой роли через `--carry-incomplete` или повторяет этап суженным retry (#501).
- **[Перезапуск tooling с изменениями]:** Перезапуск инструмента после сбоя наследует незакоммиченные изменения developer. Разработчик продолжает работу без потери правок (#502).
- **[Fix-forward разработчика]:** Brief `developer-retry` несёт закрытый список перенесённых пунктов, а отчёт закрывает каждый пункт. Координатор отклоняет отчёт, если история после snapshot переписана (#503).
- **[Rebase внутри retry]:** Маршрут `rebase-fix-forward` переносит работу developer на новый target внутри retry. Координатор сверяет перенесённые коммиты через `rebased_from` и patch-id (#504).
- **[Замещающий batch]:** Команда `batch create --supersedes` продолжает работу после `abandon` в новом batch. Новый batch переносит принятый план architect и последний принятый candidate (#506).
- **[Delta-review после fix-forward]:** Code-review после fix-forward проверяет только изменения исправления. Координатор переводит review в полный режим, если условия delta-review не выполнены (#625, #628).
- **[Политика доступа ролей]:** Конфигурация задаёт доступ ролей в режимах, которые не зависят от транспорта. Координатор передаёт работу роли только после подтверждения доступа воркера (#624).
- **[QA-evidence для хука]:** Хук `require-qa-gate` принимает принятое координатором QA-evidence того же HEAD. Повторный `make verify` перед PR больше не нужен (#631).
- **[Справка verify]:** Команда `scripts/verify.py --help` описывает стадии проверки и ничего не запускает. Неизвестный аргумент завершает команду с кодом 2.

### Fixed

- **[Причина сбоя трекера]:** `harness health --online` называет причину сбоя `git ls-remote origin`: учётные данные, TLS-сертификат, прокси или сеть. Подсказка указывает исправление, а stderr, URL `origin` и учётные данные не попадают в вывод (#626).
- **[Поиск тестов unittest]:** `harness install` больше не ставит `.harness/__init__.py`, и `python -m unittest` из корня проекта снова находит тесты проекта. `harness update` удаляет этот файл прежней установки (#626).
- **[Трекер в memory sync]:** `harness memory sync` берёт трекер из поля `tracker` в `.harness/project.json` и сохраняет подгруппы пути проекта. Команда явно адресует хост в `gh` и `glab` (#626).
- **[Closure после rebase]:** Closure перенесённых пунктов после `rebase-fix-forward` принимает только коммиты цепочки retry. Перенесённые копии прежних коммитов больше не закрывают пункты (#627).
- **[Подготовка batch в implement]:** `/implement` готовит batch только по английским агентским источникам. Русская документация больше не попадает в процедуру подготовки (#641).
- **[Ложная блокировка коммитов]:** Хук `block-direct-master` больше не блокирует команду из переменной, если слово `commit` стоит только в опции. Команды без `git commit` и `git push` проходят (#642).
- **[Ложный проход QA]:** QA gate выполнял только первую часть строковой команды вида `python a.py && python b.py`. Теперь оболочка выполняет всю цепочку, и gate видит каждый сбой.
- **[Хуки на Python 3.9]:** Хуки проекта снова работают на Python 3.9. Раньше ошибка импорта блокировала любую команду Bash.
- **[Порядок остановок auto]:** Политика `auto` ищет остановку в порядке: целостность, бюджет, маршрут. Исчерпанный бюджет больше не скрывает нарушение целостности.
- **[Блокеры review в auto]:** Политика `auto` не принимает отчёт review, если ось Standards или Spec называет `blockers`. Такой отчёт останавливает автоматический путь до решения человека.
- **[Итоговый отчёт auto]:** `batch auto-report` показывает находки координатора, которые ещё не попали в brief. Отчёт считает расход бюджета на один dispatch, а подсказка следующего шага учитывает смену политики.
- **[Очистка ledger]:** `ledger clean` больше не удаляет checkpoint живых batch. При нечитаемой записи batch команда отказывает и ничего не удаляет.
- **[Повтор после решения политики]:** Инфраструктурный повтор проверяет хеш QA-отчёта. Отчёт, изменённый после решения, больше не разрешает новый brief.
- **[Публикация dispatch]:** `dispatch publish` ограничивает время `git push` и точно сверяет ветку на remote. Зависший push больше не держит блокировку ledger.
- **[Освобождение очереди QA]:** Прерванный `qa run` освобождает lease и очередь QA. Захват очереди запуском `integration local-qa` больше не ломает восстановление dispatch.
- **[Checkpoint после сдвига базы]:** Координатор сравнивает checkpoint разработчика с базой отчёта после сдвига integration-ветки. Файлы из upstream больше не вызывают ложный отказ.
- **[Разрешение конфликтов]:** `integration resolve` после гонки с target называет созданный batch и точную команду `batch abandon`. Повтор resolve после этого проходит.
- **[Проверка локального QA]:** `integration local-qa` правильно сообщает, что ветка не основана на target. `context-package register` сравнивает `--base-commit` с фактической базой пакета.
- **[Файлы не в UTF-8]:** Координатор читает diff с файлами в устаревших кодировках без аварийного завершения. Отчёт или манифест роли не в UTF-8 даёт ошибку с инструкцией.
- **[Context Package]:** Context Package включает изменённые файлы с не-ASCII именами и вложенные ADR. Сбой Git при сборке пакета даёт ошибку с инструкцией.
- **[Устойчивость Repo Map]:** Repo Map переходит в деградированный режим при повреждённом lock, политике не в UTF-8 и ошибке чтения bundle. Кэш больше не оставляет временные файлы.
- **[Память проекта]:** Память принимает glob-шаблоны в корне проекта. Занятый индекс даёт ошибку «memory writer busy».
- **[Инвентарь интеграций]:** Установщик больше не перезаписывает нечитаемый `.harness/integrations.json`. Команда просит исправить файл и сохраняет записи проекта.
- **[Статистика доставки]:** Отчёт статистики проверяет карточку тарифов и сообщает инструкцию при нечитаемых файлах. Повреждённые записи ledger больше не прерывают отчёт.
- **[Пульт harness console]:** Экраны пульта показывают ошибку фонового запуска вместо бесконечного статуса «выполняется…». Дашборд по умолчанию перехватывает вывод команд.
- **[Сводка qa-gate]:** Сводка `qa-gate` сообщает `Status: ERROR`, если команду нельзя запустить. `diff_coverage` учитывает изменённые файлы с не-ASCII именами.

### Security

- **[Push из issue-ветки]:** Хук `block-direct-master` блокирует `git push --all`, `--branches`, `--mirror` и glob-refspec. Такие push могли обновить `main` или `integration/*`.
- **[Проверка приватных имён]:** `check_private_terms` блокирует публикацию, если Git не ответил вовремя. Раньше таймаут пропускал проверку.
- **[Каталог поколений ledger]:** Ledger отклоняет имя поколения с разделителями пути. Указатель больше не выходит за каталог ledger.
- **[Список vendor snapshot]:** Проверка vendor snapshot сверяет список файлов в `SHA256SUMS`, а не только их число. Лишняя или повторная строка больше не скрывает непроверенный файл.

- **[Создание интеграционной ветки]:** Хук защиты от прямых коммитов проверяет каждый каталог в команде. Публикация новой интеграционной ветки больше не блокируется (#446, #476).
- **[Блокировка только реальных команд]:** Хук опасных команд Git реагирует исключительно на реальный запуск. Харнесс разрешает упоминание команд в цитатах и скриптах (#566).
- **[Корректная проверка путей]:** Хуки временных файлов разрешают запись в каталоги памяти агентов. Хуки проверяют объем вывода тестов только при реальном запуске (#445).
- **[Фиксация проверок в worktree]:** Скилл `qa-gate` корректно находит конфигурацию в связанных рабочих каталогах. Скилл надежно записывает маркер прохождения тестов (#463, #600).
- **[Строгая фиксация контроля качества]:** Скрипт проверки выставляет маркер только при полном прохождении проверок. Маскировка ошибок через `|| true` больше не позволяет обойти контроль (#611).
- **[Безопасное обновление эпиков]:** Скилл `/to-tickets` обновляет описание эпика через файлы. Это предотвращает искажение текста из-за экранирования в командной строке (#447).
- **[Очистка неактивных рабочих каталогов]:** Команда жесткой очистки удаляет неактивные рабочие каталоги после отправки изменений. Мусор больше не накапливается на диске (#565).
- **[Стабильная работа на Windows]:** Установщик корректно обрабатывает неинтерактивный ввод на Windows. Команда `health` экранирует пути и безопасно запрашивает задачи (#514, #602).
- **[Устойчивость блокировок журнала]:** Координатор повторяет попытки при занятой блокировке журнала. Координатор автоматически снимает поврежденные блокировки по таймауту (#498, #525).
- **[Надежный перезапуск разработчика]:** Повторный запуск разработчика наследует контекстный пакет и инструкции. Отмененные задачи не мешают продолжению работы (#524, #540).
- **[Устранение взаимных блокировок]:** Промежуточная фиксация изменений продолжается без задержек. Разработчики устранили ошибки зависания при проверке окружения (#606).
- **[Ранние отчеты остановки]:** Координатор корректно принимает отчет об остановке до изменения файлов. Конвейер требует соблюдения всех проверок перед кодированием (#607).
