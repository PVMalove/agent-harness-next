# Changelog

Изменения выпусков записываются в формате [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/) и версионируются по SemVer.

## [Unreleased]

### Added

- **[Проверка перед cutover]:** `harness-runtime migrate --check --repo <repo>` выполняет только проверку предусловий migrate — версия ledger, пустой QA-lane, нет dispatch в `dispatched`/`working`, нет store прошлого отката, валидный ledger — без approval и без записи. Отвечает одной JSON-строкой `{"ready": true, ...}` с кодом 0, после cutover — `ready: false, already_cut_over: true`, при отказе — кодом и remedy обычного migrate (#814).
- **[harness update переводит state на runtime store]:** `harness update` принимает `--approved-by`, `--approved-at` и `--reason` (все три вместе). На `ledger.json` версии 3 он до установки первого файла вызывает `harness-runtime migrate --check`, после установки — `harness-runtime migrate` с этим approval (ADR 0020, раздел 6). Без approval, на ledger версий 1–2, без бинарника `harness-runtime` или при отказе проверки update ничего не устанавливает и печатает команду исправления. Проект без state и проект на runtime store обновляются как раньше (#814).
- **[Пошаговая проверка тест-автора]:** `harness health` проверяет отдельной строкой каждое условие тест-автора (блок `test_author`, корень проекта по Git, доверие Claude Code, guard, runner и probe изоляции) и для каждого отказа печатает шаг исправления, а `harness health --fix` добавляет отсутствующий блок `test_author` в `.harness/project.json` по плану developer и не меняет существующий. Руководство «Как включить тест-автора» добавлено в документацию проекта и шаблон целевого проекта (#1122).
- **[Перенос неподтверждённого отчёта architect]:** `batch create --supersedes --carry-architect <dispatch>` переносит непринятый отчёт architect закрытого batch, если человек подтвердил именно его (`--architect-report-sha256`, `--architect-confirmed-by`, `--architect-confirmed-at`), и новый batch начинает с developer без нового architect. Перенос отклоняется без подтверждения человека, при другом SHA-256 или Definition of Done и при `commit_plan` вне `allowed_paths` нового batch (#1052).
- **[Журнал worker под runtime]:** Новая команда `dispatch logs --dispatch <id> [--offset N] [--follow]` показывает события worker под надзором runtime из его журнала запуска, а с `--follow` печатает каждое событие строкой JSON, пока worker работает, и не держит замок ledger. Тот же журнал читают `dispatch observe` и экран worker в веб-консоли (#1124).
- **[Адаптеры и PATH serve]:** `harness health` сверяет стандартные адаптеры Claude и Codex с версией harness (`orchestration.adapters`) и ищет `claude` и `codex` в PATH окружения `harness-runtime serve` (`orchestration.worker_binaries`), который runtime теперь сообщает в ответе `status`. Отсутствие двоичного файла, нужного роли с транспортом `external`, даёт `fail` с командой запуска serve (#1124).
- **[Кэш cargo для QA-контейнеров]:** Элемент `cache` в `access_policy.*.filesystem` принимает необязательное поле `variable`, и контейнерный исполнитель сам передаёт контейнеру переменную с путём кэша, поэтому настраивать окружение `harness-runtime serve` не нужно; кэш без `variable` не меняет digest плана. Каждый QA-прогон задаёт `CARGO_TARGET_DIR` в своём каталоге: cargo-этапы прогона переиспользуют собранные зависимости, а собранный код кандидата удаляется вместе с прогоном и не переходит в другой (#1097).

### Changed

- **[Инструкции агентов в harness/project/instructions]:** Инструкции агентов собраны в один каталог шаблонов `harness/project/instructions/` вместо `harness/project/docs-agents/` и `harness/docs/`. Руководства по-прежнему ставятся seed-файлами в `docs/agents/` проекта: этот путь читают вендорные skills. Управляемые контракты `technical-english.md`, `project-memory.md` и `container-executor.md` ставятся в `.harness/instructions/` вместо `.harness/docs/`; `harness update` удаляет их старые копии, а для ссылки на `technical-english.md` в `AGENTS.md`/`CLAUDE.md` проекта предлагает diff. Все инструкции написаны на английском; русские описания остаются на сайте (#814).
- **[Агенты без закреплённой модели]:** Агенты `code-review-spec`, `code-review-standards`, `pr-composer` и `test-author` больше не задают `model`, а `to-tickets` не требует «дешёвой модели» для advisory-вызова: модель выбирает конфигурация runtime или роли. Guard test-author принимает и отсутствие строки `model`, и `model: inherit` старого seed (#814).

### Fixed

- **[Статус dispatch при закрытии batch в runtime store]:** `batch abandon` и `batch not-required` в эпохе runtime store закрывали dispatch только в записи batch, а запись `dispatch-status` оставалась `dispatched`/`working`: проверка существования шла по файлу, которого у store нет. Теперь статус получает `abandoned` или `cancelled`, как в файловом ledger (#814).
- **[delivery-stats на runtime store]:** Метрики оркестрации `delivery-stats` после cutover читали оставшиеся файлы поколения файлового ledger — устаревшие данные — или отвечали «нет данных». Теперь записи `batches` и `dispatches` читаются через `state.read` runtime проекта; без работающего runtime отчёт называет `harness-runtime serve` (#814).
- **[Задержка ответа serve]:** `harness-runtime serve` принимал соединение только на следующем такте опроса (до 25 мс), а клиент открывает соединение на каждый запрос, поэтому каждая команда coordinator ждала. Цикл accept теперь ждёт соединение через `poll(2)`: `state.read` на пустом store — около 3,4 мс вместо 25 мс; флаг остановки проверяется не реже, чем раньше (#1146).
- **[Retry проверки на store]:** `batch decide --decision retry` по маршруту `verification` в эпохе runtime store падал с `NotADirectoryError`: хеш отчёта считался чтением файла, которого в store нет. Регистрация кандидата берёт `report_sha256` записи, который ledger сверяет с отчётом в обеих эпохах (#1146).
- **[Ложный blocked контейнерного worker]:** Контейнерный worker, который записал отчёт и вышел раньше, чем coordinator его наблюдал, больше не попадает в `blocked` с `worker-exited-without-report`: `dispatch wait`, `dispatch status --dispatch` и `report submit` подтверждают модель по сохранённому выводу вышедшего контейнера. Адаптер Claude в контейнере запускается через `python3` образа и только записывает отчёт, runtime маскирует значения переменных `environment` в логах worker, а `harness health` для роли в контейнере проверяет движок и образы вместо `claude` на хосте (#1125).
- **[Тест-автор в worktree developer]:** Preflight тест-автора берёт корень проекта из Git и больше не требует `CLAUDE_PROJECT_DIR`, а переменная, которая указывает на другой каталог, даёт отказ `project_dir_mismatch`. Linked worktree доверен, если в Claude Code доверен основной checkout, поэтому in-process developer `/implement` вызывает тест-автора в своём worktree без отдельного диалога доверия (#1122).
- **[Право записи в worktree]:** `batch create`, а для пишущей роли `dispatch preflight` и `dispatch send`, проверяют запись в worktree задачи и его git-метаданные и отказывают с названным каталогом и remedy, а не узнают о проблеме из отчёта `blocked` developer. Skill `implement` до смены метки `status::*` проверяет, что сессия открыта в основном checkout и может писать в worktree, их git-метаданные и inbox (#1126).
- **[Адаптер живёт с worker]:** Под надзором runtime стандартные адаптеры Claude и Codex больше не завершаются раньше worker, поэтому dispatch работающего worker не попадает в `blocked` с `worker-exited-without-report`. Любой адаптер теперь обязан вернуть код выхода worker (`128 + N` при сигнале N), который `runtime_failure.exit_code` показывает при выходе без отчёта; без `execution` в brief адаптеры, как раньше, запускают worker отсоединённо (#1124).
- **[Отчёт read-only роли]:** Адаптер Claude даёт read-only роли (например, `architect` и `code-review`) право записи только в свой файл отчёта, поэтому под `dontAsk` она сдаёт отчёт и не может менять другие файлы. Адаптер ищет `claude` также в `~/.local/bin`, если его нет в PATH окружения `harness-runtime serve` (#1123).
- **[Hooks и старый конверт]:** Hook `runtime-autostart` при старом конверте hooks, который его не регистрирует, больше не блокирует каждый вызов `Bash` и не зацикливает `Stop`, а печатает предупреждение `[runtime-autostart-failed]` с командой исправления. `harness update` не подключает hook, неизвестный установленному конверту, и печатает команду `harness update --force-seed-file`, которая заменяет конверт за один запуск, а `harness health` (`hooks.policy`) сообщает такой рассинхрон (#1100).
- **[QA без исполняемого файла]:** Падение стадии QA, которое runtime отнёс к окружению (`tooling` при выходе 126/127 или `timeout`), даёт отчёт `blocked`: retry повторяет QA без траты попытки developer, а `batch auto-decide` останавливается с `qa-environment-failure`. Контейнерный QA с `qa_preparation` проверяет наличие каждого исполняемого файла гейта до первой команды, а шаблон получил образ QA с тулчейном Rust. Без `qa_environment_probes` и `qa_project_file_checks` диагноз `unknown` требует разбора coordinator без автоматического повтора (#1096).

## [2.0.0]

### Breaking Changes

- **[Обязательный Rust runtime]:** Operational state оркестрации хранит runtime store `state/runtime.db`, а пишет в него только `harness-runtime serve`. Недоступный runtime даёт `runtime_unavailable` и код 2 (#792, #801, #807).
- **[Ledger версии 4]:** `harness-runtime migrate` переводит ledger версии 3 в runtime store и пишет `ledger.json` с `version: 4`, после чего установка 1.x отказывает с кодом 2 (#797).
- **[Файловая эпоха до migrate]:** Coordinator 2.0.0 работает на файловом `ledger.json` версии 3, пока человек не выполнит `harness-runtime migrate`, а ledger версий 1 и 2 сначала нужно перевести командой `coordinator.py ledger migrate`. Контейнерный QA, docker-исполнитель, команды `recovery` и operational hold требуют runtime store и в файловой эпохе завершаются с кодом 2 и remedy `harness-runtime migrate` (#814).
- **[Новый проект на runtime store]:** Проект без состояния оркестрации получает store командой `harness-runtime init --repo <repo> --approved-by <человек> --approved-at <время RFC 3339> --reason <текст>`, без файлового ledger и без `migrate`. Команду выполняет человек: approval проверяется как у `migrate`, approver `policy:` отклоняется. Повтор отвечает `already_initialized: true` без записи, а ledger версий 1–3 и записи 1.x команда отклоняет кодом 2 с remedy `harness-runtime migrate`. Coordinator больше не создаёт файловый ledger: `batch create`, `batch plan` и `ledger reset` на проекте без состояния завершаются с кодом 2, ничего не пишут и называют в remedy `harness-runtime init`. `harness health` показывает для такого проекта `warn` с этой командой, `migrate` на пустом состоянии (`nothing_to_migrate`) ведёт к ней же. `serve` store не создаёт. ADR 0036 (#1146).
- **[Migrate по approval]:** `harness-runtime migrate` и `rollback --to-legacy` требуют `--approved-by`, `--approved-at` и `--reason` и выполняются только человеком. Порядок перехода и отката — в [руководстве миграции на 2.0](https://pvmalove.github.io/agent-harness-next/guides/upgrade-2-0/) (#803, #826).

### Added

- **[Видимость harness-runtime serve]:** Быстрый старт (ru и en) получил раздел «Runtime» об однократном `migrate`, постоянном `serve`, проверке `coordinator.py runtime status` и сервисе `systemd --user`, а `harness health` — проверку `orchestration.runtime`, которая при неотвечающем runtime даёт `fail` с командой `harness-runtime serve --repo <repo>`. Ту же команду называют веб-консоль, отказ `orchestration.ledger_summary`, `harness cleanup` и `harness worktree-remove`, а шапка консоли показывает, работает ли runtime (#1081).
- **[Ход работы in-process воркера]:** Вкладка «Ход работы» веб-консоли для in-process dispatch без потока событий показывает причину, время heartbeat, self-report модели с отметкой совпадения и последние 20 чекпоинтов, пока воркер работает и после его остановки. Живая лента `steps.subscribe` передаёт эти данные в поле `observation`, у других dispatch оно `null` (#1051).
- **[Автозапуск harness-runtime serve]:** В Claude Code hook `runtime-autostart` перед командой coordinator вызывает `harness-runtime ensure`, который переиспользует работающий serve или запускает свой вне песочницы агента, а `Stop` и `SubagentStop` вызывают `harness-runtime release`, и свой serve завершается, когда store простаивает; ручной serve не останавливается. Сбой запуска даёт предупреждение с причиной и журналом serve, Codex и Windows остаются на ручном запуске, а hook появляется после `harness update` и сборки release-бинарника (#1088).
- **[Остановка и перезапуск runtime]:** `harness-runtime stop --repo <repo>` останавливает runtime репозитория так же, как SIGTERM, и ждёт освобождения lock, а без runtime отвечает `not_running`, поэтому повтор безопасен. `harness-runtime restart --repo <repo>` заменяет живой runtime без поиска pid, и контракт одинаков на Unix-сокете и Windows named pipe (#1053).
- **[Этапы и аннотации CI]:** Полный путь `verify.yml` идёт этапами: быстрый гейт `lint` (ruff, mypy, `cargo fmt`, Clippy, метаданные) и `docs` до тяжёлых наборов Linux и Windows, которые без него не запускаются; Linux-наборы берут одну debug-сборку `harness-runtime` из задания `rust`. Ошибки Clippy, ruff и mypy, упавшие тесты, непокрытые изменённые строки и находки проверок метаданных и терминов видны аннотациями на своих строках во вкладке «Files changed», а сводка показывает диаграмму итогов, свёрнутые traceback и команду повтора (#1059).
- **[Сверка консоли с макетом]:** Каждая страница и вкладка веб-консоли сверена с макетом на ширине 1440 и 390 px и перестроена по его блокам, порядку и плотности, а страница обновления получила панели «Миграция runtime-store» и «Результат последнего запуска». Playwright обходит все вкладки на обеих ширинах и проверяет, что панели не выходят за рамки и axe-core не находит нарушений, а поле без источника показывает «нет данных» с причиной (#1066, #1071).
- **[Веб-консоль по макету]:** Оболочка и десять страниц веб-консоли повторяют блоки, порядок, заголовки, вкладки, фильтры и кнопки принятого макета, а шапка показывает реальную версию harness, репозиторий и ветку. Сервер консоли отдаёт настоящие данные проекта, установки, runtime store, здоровья, KPI и вердикт Release Gate вместо демонстрационных значений макета, поле без источника показывает «нет данных», а подтверждения необратимых действий сохранены (#1039, #1046).
- **[Смена статуса тикета]:** Карточку доски задач можно перенести в другую колонку перетаскиванием или выбором статуса в окне тикета: запрещённый перенос показывает причину, разрешённый после подтверждения выполняется как job сервера `board-status`, а перенос в «Бэклог» ставит `status::blocked`. Перенос выполняет новая команда `harness ticket-status <repo> --spec <спека> --ticket <тикет> --to <колонка>`, которая проверяет переход по свежим данным трекера и ledger, заменяет метку `status::*` в GitHub, GitLab или локальном трекере и при отказе возвращает код 3 без записи (#915, #1044).
- **[Страница «Доска задач»]:** Веб-консоль показывает доску задач с переключателем спек, KPI, поиском, фильтрами, пятью колонками и окном тикета, которое копирует промпт и критерии приёмки. Страница только читает данные и обновляется по событиям тикета или batch, а при недоступном трекере показывает последний снимок с его возрастом и причиной (#1041).
- **[Страницы проекта и настройки]:** Веб-консоль получила страницы «Открыть проект», «Обновить Harness», «Настройка» и «Справка» с теми же фактами, что TUI; сервер по-прежнему обслуживает один проект, а другой открывается командой `harness console --web <путь>`. Обновление, установка и запись конфигурации запускаются только как job сервера после подтверждения, секреты в конфигурации замаскированы, а мастер настройки и версии конфигурации остаются в TUI (#1040).
- **[Снимок доски задач]:** Сервер консоли отдаёт `task_board.specs` и `task_board.snapshot`: открытые спеки проекта и доску спеки с колонками, блокерами, критериями приёмки, ссылками на issue и PR и готовым промптом агента. Трекер читается только командами чтения, снимок кэшируется на 60 с, а при недоступном трекере приходит последний снимок с возрастом и причиной (#989).
- **[Снимки проекта и справки]:** Сервер консоли отдаёт `open_project.snapshot` (план установки, capability, конфликты и до 20 соседних Git-каталогов с командой `harness console --web <путь>`) и `help.snapshot` (справка на `ru` или `en`), а экраны TUI читают их через сервер. Установка в обслуживаемый проект выполняется подтверждённым job сервера `setup-init`, `setup-adopt` или `setup-update`, а проверка и установка другого пути пока остаются в TUI (#1001).
- **[Снимок Repo Map]:** Сервер консоли отдаёт `repo_map.snapshot` с картой из кэша для HEAD, режимом карты, состоянием parser bundle, языками проекта и статусом памяти, а экран TUI Repo Map читает его через сервер. «Собрать карту» и операции памяти выполняются как job сервера, а установка парсеров и запись настроек пока остаются локальными (#998).
- **[Снимки диагностики и Harness]:** Сервер консоли отдаёт `diagnostics.snapshot`, `harness.snapshot` и `harness.maintenance`, поэтому экраны TUI Диагностика и Harness больше не запускают проверки и команды сами. Фиксы `harness health --fix` (онлайн-вариант — только с подтверждением) и команды обслуживания выполняются как job сервера, а очистка требует digest показанного плана (#997).
- **[Снимки отчётов и оркестрации]:** Сервер консоли отдаёт снимки экранов Отчёты, Оркестрация, Восстановление и Контейнерный запуск постранично, поэтому большой ledger и тела отчётов не упираются в лимит кадра, а экраны TUI читают их через сервер. Действия восстановления запускаются как job сервера, а запись исправления и `resume` выполняются только с подтверждением (#984).
- **[Лёгкий и полный CI]:** PR в `integration/**` запускает одно задание `verify-light` (lint, `cargo fmt`, Clippy, тесты diff PR и проверку метаданных), а PR и push в `master` и вызов из другого workflow — полный `make verify` и `cargo test`. `integration collect-ci` не подтверждает лёгкой проверкой пару, которой нужен полный прогон, поэтому в `ci_required_checks` перечисляются полные проверки, например `verify` и `rust` (#1018).
- **[Выбор тестов по diff]:** Флаг `verification_plan_policy.ticket_diff_selection` (по умолчанию выключен) для batch с целью `integration/*` строит планы developer-retry, code-review и QA только по тестам diff `base..candidate`, включая цели `cargo test`, и не расширяет выбор до `full`, а diff без тестов записывает стадию `no-tests-in-diff` как `not_run`. С выключенным флагом и для цели `master` планы, gate и stage evidence не меняются (#935).
- **[Политика тестов тикета]:** ADR 0023 и 0026, playbook и навык `to-pull-requests` описывают diff-прогон для пары в `integration/*`, полный прогон только для пары в ветку по умолчанию, полный CI через `integration collect-ci` с запасным `integration local-qa` и fix-тикеты после падения полного прогона. Тест сверяет имена в документах с кодом (#938).
- **[Ручное подтверждение записи]:** Hook `protect-hook-policy` для записи в `.harness/project.json` через shell отвечает вердиктом `ask`: в Claude Code человек подтверждает её вручную, вне Claude Code отказ остаётся блоком. Жёсткие отказы (ключ `hook_policy`, настройки и каталоги hooks) сильнее вопроса и не спрашивают, в том числе в смешанной команде (#938).
- **[Windows CI]:** Задания `verify-windows` снова включены на полном пути CI (не для PR в `integration/**`) и входят в `needs` у `dashboard` (#938).
- **[Тест-автор в worker worktree]:** External developer Claude Code может вызвать защищённого тест-автора в своём доверенном checkout: health показывает готовность или причину отказа, а live-проба подтверждает цикл на коде worker, не меняя основной checkout. In-process, Codex и Rust остаются за границей этой поддержки (#971).
- **[Canonical-конфиги и восстановление]:** `make verify` до тестов проверяет, что tracked конфиги оркестрации canonical: значение, которое нормализатор исправил бы с предупреждением, становится ошибкой с файлом, JSON pointer и допустимыми значениями. Regression suite восстановления на runtime store проверяет закрытый список сценариев и то, что `recovery resume` не перезапускает принятый этап (#685).
- **[Контейнерный маршрут и восстановление]:** В разделе Orchestration консоли появились экраны «Контейнерный маршрут» со стадиями от Setup до Cleanup и «Восстановление» с Fix по превью diff, Reload и Resume; каждое действие — отдельная кнопка с причиной недоступности, а одобрение и очистка привязаны к digest показанного плана. Консоль не обращается к движку контейнеров, не добавляет `--docker`, auto-approve или прав агента и не показывает значения переменных окружения (#711).
- **[Smoke Podman с SELinux]:** Отдельный workflow `podman-smoke` на self-hosted runner владельца запускает worker и QA-контейнер в rootless Podman на Fedora с SELinux и проверяет egress, очистку ресурсов и лимиты memory, pids и cpu. Маркер `podman_smoke` исключён из обычного pytest, а триггера `pull_request` у workflow нет (#811).
- **[Guards для apply_patch]:** Критичные guards `protect-hook-policy`, `block-scratch-outside-docs-tasks` и `test-author-guard` разбирают payload `apply_patch` так же, как второй runtime, и принимают по каждому пути то же решение, что для `Write`/`Edit`: патч блокируется, если заблокирован хоть один путь, а неразбираемый — с `apply-patch-unparseable`. `.codex/hooks.json` подключает оба project-wide guards, и `harness health` (`hooks.policy`) на свежей установке даёт `ok` (#830).
- **[Команды восстановления batch]:** `coordinator.py recovery status|reload|resume|fix|abort --batch <id>` работают на runtime store без TTY и stdin и печатают документ `recoveryStatus.v1` (код 0 при успехе, 2 при отказе). `recovery resume` снимает удержание и реагирует на исполнение открытых dispatch без второго worker, а записанная остановка продолжается только через аудируемый `batch resume-stop` (#925).
- **[Удержание batch]:** Удержанный batch кодом 2 без записи отказывает в командах, которые двигают его lifecycle (`dispatch create`, `send`, `report submit`, `qa run`, `dispatch publish`, `batch decide`, `batch resume` и другие), а heartbeat, cancel, abandon, attention и чтения остаются доступны. `batch auto-decide` записывает остановку `operational-hold` и никогда не делает abandon, а decision packet предлагает маршрут восстановления (#925).
- **[Супервизор процессов runtime]:** На Linux `harness-runtime` сам запускает внешний worker dispatch из сохранённого brief, поэтому повтор `dispatch send` возвращает тот же receipt без второго запуска. После аварии runtime новый runtime усыновляет процесс или записывает исполнение `lost`, останавливает worker по сроку `worker_execution_timeout_seconds` и освобождает аренду только после выхода всей группы процессов, а отчёт, присланный до выхода worker, не теряется (#805).
- **[Супервизор на Windows]:** На Windows `harness-runtime` запускает внешний worker в именованном Job Object, который переживает runtime, а после рестарта находит его по имени, усыновляет лидера и доводит до конца начатую остановку. По сроку исполнение получает `CTRL_BREAK`, затем `TerminateJobObject`, а контейнеры и QA-прогоны остаются только на Linux (#806).
- **[Параллельные batch]:** Coordinator-ы разных batch пишут в runtime store параллельно, а каждая команда читает store из одного снимка, поэтому коммит другого batch не даёт `ledger_busy`, а `dispatch status`, `batch auto-report`, `batch decision-packet` и `qa status` не ждут писателя. Из двух команд с одним решением по всем batch коммитит одна (`revision_conflict`), а `harness-runtime serve` переводит store версий 1 и 2 на версию 3 при старте (#804).
- **[QA-lease с fencing]:** QA-lane в store — lease с монотонным `fencing_token`: runtime записывает идентичность владельца из ядра и после `expires_at` снимает lease только вердиктом `owner-dead`, а следующий `qa run`, `integration local-qa` или `ledger release-lock` делает это без `--force`, с записью audit и восстановлением QA dispatch владельца. Владелец продлевает lease каждую треть `lease_ttl_seconds` (300 с по умолчанию), а `qa status`, `dispatch status` и `ledger lock-status` показывают состояние lease (#804).
- **[Запуск `harness console --web`]:** Команда запускает Сервер консоли проекта, печатает URL с токеном, открывает браузер (`--no-open` отключает) и завершается; уже работающий сервер переиспользуется (#865).
- **[Запись lifecycle через store]:** При `ledger.json` версии 4 каждая мутация batch и dispatch идёт в runtime одной транзакцией на batch с проверкой ревизии строк, а повтор с тем же `operation_id` возвращает сохранённый результат. Python не открывает `runtime.db` и не имеет запасного пути записи, `revision_conflict`, `store_busy` и `runtime_unavailable` — разные ошибки с кодом 2, а `harness-runtime serve` переводит store версии 1 на версию 2 при старте (#801).
- **[Checkpoint audit-цепочки]:** Обычная команда проверяет только записи audit после checkpoint, а удалённый или повреждённый checkpoint перестраивается полной проверкой без ошибки. `coordinator.py ledger validate --full` пересчитывает цепочку от начала, сверяет её с импортом и находит удаление, вставку и перестановку записей, а `ledger migrate`, `ledger clean` и `ledger reset` в эпохе runtime store отказывают кодом 2 (#801).
- **[Команда `harness-runtime migrate`]:** `harness-runtime migrate --repo <repo>` переводит ledger версии 3 в store `state/runtime.db`: проверяет его, как `ledger validate`, делает снимок state, сверяет паритет импорта и пишет `ledger.json` версии 4. Коды выхода: 0 — успех или повтор без изменений, 2 — отказ без изменений, 3 — сбой с удалённым частичным store, 4 — расхождение паритета; отказ печатает `REMEDY:`. Migrate отказывает при dispatch в `dispatched`/`working`, QA-lease или очереди QA, поэтому сначала дождитесь отчётов или переведите зависшие dispatch в `abandoned` (#797).
- **[Откат `harness-runtime rollback --to-legacy`]:** Команда с human approval возвращает state-каталог из runtime store установке 1.x: пишет неизменяемый архив store и новое поколение ledger версии 3, сверяет его со store, после чего store становится read-only, а `runtime.db` не удаляется. Команда отказывает кодом 2 без записи при работающем `serve`, QA-lease или очереди и живом исполнении dispatch, повтор после сбоя продолжает с последнего завершённого шага, а коды выхода те же, что у `migrate` (#803).
- **[Чтение статусов из store]:** При `ledger.json` версии 4 `dispatch status`, `batch list`, `batch decision-packet` и `qa status` читают записи через runtime из одной транзакции, не открывают файловый ledger и не берут его замок, а `store_busy` и `revision_conflict` показываются как прежний `ledger_busy`. `dispatch status` в этой эпохе не опрашивает движок и ничего не пишет (#797).
- **[Сервер `harness-runtime serve`]:** `harness-runtime serve` обслуживает репозиторий и его linked worktree через сокет в `$XDG_RUNTIME_DIR/harness` (иначе `/tmp/harness-<uid>`, на Windows `%LOCALAPPDATA%\harness`) с проверкой uid и токена, а `coordinator runtime status` только читает состояние. Недоступный runtime даёт `runtime_unavailable` без записи в обход, а symlink, чужой или открытый другим каталог даёт `unauthorized_peer`. Сервис с `PrivateTmp=yes` и клиент вне него не видят друг друга, поэтому для сервисов задайте `XDG_RUNTIME_DIR` (#792, #807).
- **[Наблюдение за worker]:** `dispatch observe` читает локальные события, `terminal.json` и ledger без вызова модели; консоль показывает выбранный worker в разделе рабочих сессий с ответами на запросы native permissions. Закрытие, повторное открытие и reconnect панели не останавливают worker и не запускают второй процесс (#716).
- **[Ранний сбой worker]:** `execution_policy.worker_startup_timeout_seconds` (120 секунд по умолчанию) закрепляется в brief. `dispatch wait` возвращает `startup_failed` при доказанном раннем выходе, `startup_timeout` при пропущенном первом self-report и `worker_exited_without_report`, если после self-report процесс исчез без отчёта; последнее событие ничего не меняет в ledger (#716).
- **[Перезапуск одним решением]:** `batch resume-stop --restart` заменяет цепочку из двух подтверждений одним решением человека для доказанно остановленного worker. Причина повтора architect (`retry_reason`) попадает в brief из `--note`, пустая заметка отклоняется (#716).
- **[Доставка отчёта после отказа]:** `report submit --relayed-by --relay-reason --source-sha256` доставляет уже существующий файл отчёта и записывает отправителя в audit (#716).
- **[Диагностика sandbox_denied]:** Если ledger недоступен для записи (EROFS, EACCES, EPERM), команды возвращают `sandbox_denied` с путём и подсказкой про `sandbox.filesystem.allowWrite`, а не traceback `OSError` (#716).
- **[ChangeImpact и план проверки]:** `dispatch propose` для developer-retry, code-review и QA строит по diff `base..candidate` набор затронутых модулей и связанных тестов (ChangeImpact) и `verification_plan`, где стадия pytest получает выбор `focused`, а для QA и при неизвестном влиянии (изменение `conftest.py`, зависимостей, CI, файлов не на Python, динамический импорт) — `full`. План лежит в brief, его digest привязан к approval, политику задаёт необязательный ключ `verification_plan_policy`, а batch без ключа работает по замороженным командам, как раньше (#793).
- **[Отказ `impact_not_covered`]:** `dispatch propose` и `dispatch create` для code-review и qa отказывают с кодом 2 и перечнем тестов, если стадия pytest плана не `full` и не выбирает какой-либо из `related_tests` `ImpactSet`. Проверка машинная: текст отчёта роли её не заменяет (#793).
- **[Повтор упавших тестов]:** Скрипт проверки получил флаги `--worktree-cache`, который хранит кэши mypy и pytest отдельно для каждого worktree и окружения, и `--failed-only`, который повторяет только упавшие тесты прошлого прогона, а clean-room QA всегда остаётся холодным. `--evidence-dir` и gate runner пишут `stage-evidence.v1` для каждой стадии (потоки с sha256, код выхода, длительность, упавшие тесты, `not_run` для недошедших), но publish разрешает только полный clean-room прогон на итоговом SHA (#798).
- **[Egress-proxy для `network.hosts`]:** Исполнитель `docker` принимает непустой `network.hosts`: worker попадает во внутреннюю сеть dispatch, а sidecar-прокси из закреплённого образа `container.proxy_image` пропускает HTTP(S) только к хостам плана на портах 80 и 443 и отказывает для loopback, link-local и IP-литералов. Имя хоста LLM API нужно указать явно, ssh git и другие протоколы не поддерживаются, а при пустом списке worker, как раньше, запускается с `--network none` (#706).
- **[Контейнерный clean-room QA]:** Если в `access_policy.operations.qa` задан контейнер, `qa run` исполняет каждую QA-команду в своём контейнере через `harness-runtime` с закреплённым digest образа, а Git и checkout остаются на хосте. Сбой инфраструктуры даёт новую попытку без траты бюджета developer, ошибка инструмента и тайм-аут — отчёт `blocked`, а пересобранный образ или отсутствующая переменная окружения блокируют прогон до первой команды (#810).
- **[Базовый образ worker]:** Payload оркестрации получил необязательный `Dockerfile.sandbox` (Debian slim, `git`, `curl`, `jq`, Python с `uv` и Node.js, без секретов), на котором проект сам собирает свой образ worker. Исполнитель принимает любой совместимый образ, а харнесс образы не собирает, не скачивает и не публикует (#710).
- **[Руководство по контейнерному исполнителю]:** `backend-orchestration` ставит англоязычное руководство `container-executor.md` о Docker и Podman, конфиге, совместимости и сборке образов, кэшах, allowlist хостов, блокерах, очистке и примере адаптера. Пример сохраняет native approval агента, а Podman и rootless Docker руководство называет непроверенными настоящим smoke (#710).
- **[Smoke Docker в CI]:** Новый job `docker-smoke` собирает образы worker и proxy и через публичные команды coordinator и настоящий `harness-runtime` проверяет worker и контейнерный QA: владельца файлов, доступ только к разрешённому хосту, код выхода QA и удаление объектов dispatch. Маркер `docker_smoke` исключён из pytest по умолчанию, поэтому `make verify` эти тесты не запускает, а job проверяет только rootful Docker (#710).
- **[Контейнерный worker в runtime]:** На Linux с runtime store контейнер worker docker-dispatch запускает, останавливает и удаляет сам `harness-runtime`, поэтому на хосте с Podman ни одна команда не уходит в `docker`, а план, который открывает контейнеру сокет движка или каталог runtime, отклоняется. На файловом ledger и вне Linux `dispatch preflight` блокирует такой dispatch с подсказкой (#708, #807).
- **[Слияние hooks при установке]:** `harness init`, `adopt` и `update` сливают управляемые hook-записи в `.claude/settings.local.json` по пути команды `.claude/hooks/<скрипт>`: недостающие записи добавляются, устаревшие заменяются, записи пользователя сохраняются, `--force-seed-file` и `--force-seed-files` по-прежнему заменяют файл шаблоном целиком. Запись, которую пользователь изменил, остаётся без изменений, а команда печатает `[WARNING]` и строки `hooks conflict`; повторный `harness update` ничего не меняет в файле и печатает строки `hooks merge` и `hooks check` (#799).
- **[Адаптер hooks второго runtime]:** Установка создаёт и сливает по тем же правилам `.codex/hooks.json` с критическими guards и `require-bounded-check` на `PreToolUse` для `Bash`, а hooks на `Write`, `Edit`, `EnterWorktree` и `Skill` для него не подключаются. `mark-qa-gate-passed` тоже не подключается, потому что этот runtime вызывает `PostToolUse` и после упавшей команды, а проектные hooks работают только после доверия слою `.codex/` и каждому hook по хэшу (#799).
- **[Проверка `hooks.policy`]:** `harness health` показывает действующий профиль hooks и его источник, эскалации, наличие, исполняемость и проводку критических hooks по каждому runtime, дрейф от шаблона и события, которых нет у runtime. Критический hook без события и без проверки вне hook даёт `warn`, а не молчаливый пропуск; проект без ключа `hook_policy` по-прежнему получает профиль `standard` без миграции `.harness/project.json` (#799).
- **[Профиль `standard` в навыках]:** `start-project` и `integrate-project` называют профиль `hook_policy` в манифесте и после `harness init` проверяют `.harness/project.json` и `hooks.policy`; `hook_policy` существующего проекта остаётся за его владельцем (#799).
- **[Поведенческие hooks ChangeImpact]:** Три advisory-hooks по ADR 0024 никогда не блокируют: `impact-first-touch` предупреждает о первом касании рискованного пути, `targeted-check-reminder` на `Stop` напоминает отчитать targeted-проверки в `checks_run`, а `sensitive-path-recheck` (только `strict`) сообщает о каждой правке чувствительного пути. Повтор события в той же операции молчит, внутренняя ошибка или тайм-аут разрешают действие, а `harness health` показывает новые hooks в `hooks.policy` (#802).
- **[Границы профиля `strict`]:** Под `strict` `dispatch propose` и `dispatch create` для code-review и QA, `qa run` и `dispatch publish` отказывают с `strict_impact_unknown`, если кандидат меняет чувствительный путь, а план проверки не доказывает его влияние. Запущенный dispatch решает по закреплённой политике, профили `minimal` и `standard` не меняются, а команды восстановления не проверяются (#802).
- **[Остаточные ограничения hooks ChangeImpact]:** Второй runtime подключает только `targeted-check-reminder` на `Stop` и `SubagentStop`; строки `Write` и `Edit` и журнал касаний ждут адаптера `apply_patch` (#830), поэтому до него напоминание там молчит. Hardlink на чувствительный файл обходит только предупреждение `sensitive-path-recheck`: авторитетны критический `protect-hook-policy` и diff-проверка границы `strict` (#802).
- **[Release Gate по дереву]:** `dispatch publish`, `integration prepare` и `integration refresh` записывают неизменяемую пару с деревом кандидата, а runtime по сохранённому evidence выносит вердикт `ok` или `refused`: пару подтверждает только принятый полный QA-прогон, проверенный local-QA или CI, но не focused, failed-only или кэшированные результаты. Без `ok` `dispatch publish` ничего не пушит, а после merge `integration next` сверяет дерево merge-коммита с кандидатом и останавливает `/to-pull-requests` на `merge-tree-mismatch` (#812).
- **[CI-матрица сбоев]:** Задание `fault-injection` прогоняет coordinator против debug-сборки runtime по одному тесту на каждый сценарий матрицы надёжности #784 (SIGKILL, потерянный ответ IPC, повтор PID, устаревший lease, подменённый образ и другие) и на каждую границу безопасности. Пропуск сценария считается провалом, задание не перезапускает упавшие тесты, а `make verify` тоже выполняет эти тесты (#813).
- **[Файл effective policy hooks]:** `harness init`, `adopt` и `update` записывают `.harness/hook-policy.json` с нормализованным профилем hooks, его `hook_policy_sha256`, набором критических guards и хешами шаблонов, а некорректный `hook_policy` завершает команду с кодом 2 и оставляет прежний файл. `harness health` (`hooks.policy`) сообщает об отсутствии или расхождении файла как `warn`, а исправляет его `harness update` (#829).
- **[TUI как клиент сервера]:** `harness console` до старта TUI подключается к Серверу консоли проекта по WebSocket с токеном, а без живого сервера запускает его прежним путём. Если сервер недоступен, TUI не стартует: команда печатает причину и текстовый `harness health` и завершается с кодом 1 (#953).

### Fixed

- **[venv в issue worktree]:** Новая команда `harness worktree-venv <repo> <worktree>` связывает `.harness/.venv` issue worktree с venv основного checkout, если `uv.lock` и `pyproject.toml` совпадают, поэтому `make lint` и проверки brief идут без `make bootstrap`. При отличающемся lock команда отвечает `refused` с расходящимися файлами и советует отдельный venv, а генерируемый `.harness/.gitignore` игнорирует `.venv` (#1103).
- **[Подготовка окружения local-qa]:** `integration local-qa` выполняет `qa_preparation` перед проверками, как `qa run`. Провал подготовки (например, `uv sync` с кодом 2) ответ называет стадией `environment-preparation` с `qa_stages` и диагнозом, а отказ записи свидетельств — стадией `artifact-persistence`; у каждой стадии свой remedy (#1101).
- **[План проверки local-qa]:** `integration local-qa` запускает план, которого требует пара: для пары `ticket-diff` (PR тикета в `integration/*` при `verification_plan_policy.ticket_diff_selection`) — план диффа тикета по политике исходного batch, иначе — полные `verification_commands`. Запрос закрепляет `selection`, digest и сам план; повтор запускает закреплённый план (#1101).
- **[local-qa на runtime store]:** `integration local-qa` пишет лог QA и stage evidence в runtime store, как `qa run`, и сохраняет вердикт runtime на пару неизменяемой записью. В эпохе store проверенным считается только результат с вердиктом `ok` (#1101).
- **[Обновление seed-файлов]:** `harness update` по baseline sha256 в `.harness/harness.lock` отличает устаревший seed-файл от изменённого локально: устаревший заменяется без флага, а изменённый и файл без baseline остаются и перечислены отдельно. Каждая перезапись seed-файла сначала сохраняет прежние байты в `.harness/.sandboxes/seed-backups/`, установка 1.x записывает baseline командой `harness update <repo> --record-seed-baseline`, а `harness health` проверяет его формат (#1049).
- **[Быстрая проверка brief]:** Проверка ledger больше не перебирает все исторические формы brief: каждая команда, читающая dispatch, тратила на неё около секунды на запись, а с полями #1015 — вчетверо больше. Принимаются и отклоняются те же формы, что раньше (#1059).
- **[Windows-прогон тестов]:** Полный Windows-прогон снова находит Git Bash вместо заглушки WSL, поэтому около 220 тестов hooks больше не падают. Тесты не зависят от CRLF, разделителей путей и `PATHEXT`, а запуск инструментов на Windows находит шимы `gh.cmd` (#1059).
- **[Тесты без ожидания времени]:** Тесты сроков lease, heartbeat, `dispatch wait`, дедлайна и паузы остановки сдвигают общие тестовые часы и ждут события runtime вместо фиксированных пауз, поэтому не падают на медленной машине. Debug-сборка `harness-runtime` читает смещение часов из `HARNESS_RUNTIME_TEST_CLOCK_FILE` и печатает события `TRACE:` при `HARNESS_RUNTIME_TEST_TRACE`; release-сборка их не содержит (#1059).
- **[Аудит закрытия batch]:** `batch abandon` пишет в аудит перехода approver, время, причину и открытые dispatch, а `batch list` и `batch auto-report` показывают запись `abandoned` (#1015).
- **[Batch в hard cleanup]:** План и результат `harness cleanup --mode hard` называют `batch_id` и состояние batch у каждого worktree; worktree нетерминального batch по-прежнему защищён (#1015).
- **[Scope и план архитектора]:** Brief каждой роли содержит `allowed_paths` batch. Отчёт architect несёт необязательное поле `commit_plan`: `report submit` проверяет его правилами `--commit-plan-file` и отказывает при путях вне `allowed_paths`, а accept и `batch auto-decide` закрепляют его без файла плана (#1015).
- **[Дизайн архитектора для developer]:** Brief developer содержит `accepted_design` с id dispatch архитектора, `report_sha256` и `output` принятого отчёта (#1015).
- **[Context Package в preflight]:** `dispatch preflight` до регистрации Context Package отдаёт статус `not-registered` вместо пустого указателя (#1015).
- **[Окружение QA]:** Классификатор QA считает отсутствие C-компоновщика и слишком длинный путь сокета сбоем окружения (`qa-environment-failure`), а не дефектом кода (#1015).
- **[Test-author в health]:** Строка health называет поддержанный runtime и где его задать, уточняет, что preflight проверяет основной checkout, а in-process developer идёт обычным TDD (#1015).
- **[Наблюдение in-process]:** `dispatch observe` объясняет отсутствие потока событий у in-process воркера и показывает его чекпоинты; консоль выводит `stream_reason` (#1015).
- **[Контейнерный воркер]:** Architect, developer и code-review в контейнере исполнителя `docker` проходят `report submit` без ручного обхода: coordinator на хосте сам подтверждает воркера, а веб-консоль показывает его шаги. Контейнерный QA больше не требует переводить все роли на `external` (#1014).
- **[Сжатая колонка справки]:** Страница «Справка» веб-консоли больше не сжимается в колонку шириной в один символ, из-за которой текст на экране 1440×900 вытягивался на 14 000 px (#1071).
- **[Approval старого store]:** Команда `harness-runtime repair-import-approval` восстанавливает отсутствующее human approval в store, мигрированном до #826, сохраняет данные после cutover и продолжает прерванную операцию по intent и backup. `--check` и полный validate объясняют необходимость repair; проверка исторических writer handoff принимает неизменные blocked-отчёты по правилу #850 (#970).
- **[Исполнитель тест-автора]:** Полный `/implement` запускает тест-автора с runtime, моделью и effort утверждённого developer, а `/fast-implement` — с явным профилем `test_author` из `project.json`, и те же настройки используют preflight, health и live-проба. Нативный Agent наследует модель родителя вместо фиксированного `haiku`, а неподдержанный адаптер даёт `runtime_unsupported` без подмены CLI (#993).
- **[Workdir в `block-direct-master`]:** `block-direct-master` берёт каталог запуска из `workdir` вызова `exec_command`, поэтому коммит в изолированном issue-worktree больше не блокируется как коммит в защищённую ветку основного checkout. Явный `workdir` главнее `cwd`, а нестроковый `workdir` блокирует команду (#960).
- **[DNS и сети Podman]:** Runtime подключает proxy к отдельной внешней сети с DNS, оставляя worker во внутренней сети, и разбирает поля сетей Podman, поэтому очистка удаляет обе сети dispatch (#943).
- **[Хост консоли на Windows]:** Супервизор на Windows не считает хост скрытой консоли участником исполнения, поэтому исполнение с вышедшим лидером получает `exited` или `lost` и освобождает аренду, а не остаётся `running` до срока. Усыновление после рестарта выбирает только лидера, запущенного runtime, а Windows-тесты супервизора больше не висят до тайм-аута задания (#921).
- **[Группа из одних зомби]:** Супервизор на Linux считает группу из одних зомби пустой, поэтому исполнение получает `exited` или `lost` и освобождает аренду, а не остаётся `running` или `unknown` до рестарта runtime. Участник с хотя бы одним работающим потоком по-прежнему держит аренду, а при `hidepid` в procfs пустота группы не доказывается (#909).
- **[Отказ записи stopping]:** Если хранилище отказывает в записи `stopping` после SIGTERM, runtime повторяет запись при повторяемом отказе и подбирает своего завершённого ребёнка, а не оставляет его зомби. Отказ навсегда оставляет исполнение `unknown` с удержанной арендой и без SIGKILL, и reconcile доводит его до `lost` (#909).
- **[QA-маркер во втором runtime]:** Навыки `qa-gate` и `to-pull-requests` без `CLAUDE_PROJECT_DIR` находят скрипт записи маркера QA-гейта в основном worktree, поэтому второй runtime больше не блокирует создание PR после успешного `qa-gate`. В первом runtime путь по-прежнему берётся из `CLAUDE_PROJECT_DIR` (#832).
- **[Legacy-замок при migrate]:** `harness-runtime migrate` и `rollback --to-legacy` судят legacy-замок так же, как `ledger release-lock`, снимают его только при вердикте `owner-dead` или `owner-unknown-stale` (3600 с) и называют вердикт в отказе. На Windows живость владельца теперь проверяется, а не даёт отказ `owner-unprovable` (#804).
- **[Контекст до изменения кода]:** `context-package register --starting-file <путь>` закрепляет существующие ADR, модули и тесты для задач, чьи файлы ещё не созданы, и сохраняет пределы размера и политику путей. Пакет без явно запрошенных входов не переиспользуется, а write scope не расширяется (#897).
- **[External adapter после cutover]:** `dispatch send` экспортирует проверенный immutable brief из runtime store в приватный read-only файл, передаёт его adapter и сохраняет для worker после возврата команды, а конфликтующая копия отклоняется до запуска. Файловый ledger использует прежний путь (#897).
- **[Аудит после migration repair]:** `ledger validate --full` проверяет строку, исправленную при cutover, по её записи `migration-repair` и всем последующим изменениям, поэтому такой batch больше не даёт ложный `invariant_violation`. Подмена строки по-прежнему обнаруживается (#897).
- **[Проверка ветки перед коммитом]:** `block-direct-master` блокирует commit/push, если Git вернул ошибку при определении текущей ветки. Ответ `HEAD` с ненулевым кодом выхода больше не считается разрешённой веткой (#725).
- **[Хеш runtime после cutover]:** Снимок state, который делает `harness-runtime migrate`, не входит в хеш runtime, закреплённый в batch, поэтому batch, спланированный до cutover, больше не отказывает с «the harness runtime changed after this batch was planned» (#801).
- **[Выходы и секреты настройки]:** Номер раздела и меню на экранах Настройка, Версии конфигурации и Обновить Harness закрывают экран, как Esc, и обновляют Главную, а «Отмена» в подтверждении с экрана Версий оставляет пользователя на нём. Записанные секреты из `project.json` и `orchestration.json` показываются маской `••••••` в просмотре, редакторе поля и различиях версий (#773).
- **[Восстановление writer после blocked]:** `batch rewind --preserved-commit --preserved-file` принимает последний непринятый `blocked`-отчёт writer на его точном SHA, а человек подтверждает список файлов, хэши которых recovery связывает с новым dispatch. Это устраняет тупик tooling-retry при пропущенном `tooling_blocker.uncommitted_files`, а бюджет rewind, scope и независимые review/QA сохраняются (#837).
- **[Полная проверка внешнего worker]:** Native profile разрешает обеим ролям общий каталог `.harness/.sandboxes/runs/tests`, куда `make verify` создаёт временное окружение из связанного worktree. Остальные каталоги `runs` и соседние worktree остаются защищены (#836).
- **[Git refs внешнего worker]:** Native profile разрешает `packed-refs.lock` в общем Git-каталоге, чтобы обычный commit в связанном worktree не печатал отказ записи. Существующие остальные shared metadata, основной HEAD/index, config/hooks и служебные каталоги других worktree защищены; права исходников не расширены (#836).
- **[IPC внешнего worker]:** Codex adapter принимает явный `--network-access=enabled` для согласованной сетевой политики и локального socketpair IPC, необходимого asyncio; прежняя network-настройка workspace-write не переносится в named profile. По умолчанию сеть выключена, права исходников не меняются (#836).
- **[Проверки внешнего worker]:** Native profile адаптера разрешает обеим ролям служебные `.harness/.sandboxes/runs/qa` и `.harness/.sandboxes/logs`: обязательная bounded-wrapper теперь может подготовить временное окружение и сохранить лог, не получая запись в другие issue worktree (#836).
- **[Lifecycle Codex worker]:** Адаптер Codex запускает `app-server` с native permission profile: read-only роль может записать только self-report, heartbeat и отчёт, а пишущая роль получает доступ к Git-метаданным для коммитов в связанном worktree. Перед передачей задачи адаптер сверяет модель, effort, CWD и профиль прав, и несовпадение останавливает запуск без расширения прав (#836).
- **[Тест-автор в `/implement`]:** Preflight тест-автора принимает `--worktree <путь>` и отвечает `checkout_mismatch`, если путь не совпадает с его checkout, поэтому in-process developer отдельного worktree больше не получает `ok` для основного checkout. Внешний transport автора не включает (`transport_unsupported`), а любой отказ оставляет обычный TDD с названной причиной (#768).
- **[Временные данные QA]:** Команды `qa run` и isolated runner получают свой временный каталог в `.harness/.sandboxes/runs/`, который удаляется после запуска, вместо жёстко заданного `/tmp`, поэтому read-only `/tmp` внешнего sandbox больше не роняет QA (#769).
- **[Падение QA из-за окружения]:** Если QA gate упал по признакам окружения (`Read-only file system` или `Permission denied` на пути вне репозитория) и в выводе нет признаков дефекта кода, `batch auto-decide` не тратит developer-retry, а останавливает автоматический путь с причиной `no-automatic-route`/`qa-environment-failure` и remedy. Настоящее падение теста по-прежнему ведёт к retry (#769).
- **[QA-lease после занятого ledger]:** `qa run`, который после взятия QA-lease встретил занятый ledger, больше не оставляет lease на час: он ждёт lock до 30 секунд, снимает lease и очередь своего dispatch и возвращает dispatch в `approved` для нового запуска. Если lock не освободился, ошибка называет dispatch и владельца lease, а `qa clear-stale-lease` после истечения lease тоже возвращает dispatch в `approved` (#776).
- **[Ветка ниже базы]:** `batch create` отказывает с `branch_start_missing_base` и не записывает batch, если ветка worktree не содержит свежий tip `origin/<integration_ref>`, поэтому чужие коммиты больше не попадают в `changed_files` и оценку риска задачи. Remedy называет `git -C <worktree> merge --ff-only <база>`, а batch с `--supersedes` и маршрут conflict-resolver так не проверяются (#802).

## [1.4.5] - 2026-10-13

### Added

- **[Стадии в отчётах консоли]:** Раздел «Отчёты» показывает все записанные стадии, в том числе без отчёта, а не только завершённые отчёты. Стадия без отчёта открывает хронологию batch, а список обновляется клавишей `r` или кнопкой ↻ (#676).
- **[Фильтры и порядок стадий]:** Стадии отбираются по статусу и по завершённости (все, незавершённые, завершённые) вместе с прежними фильтрами по тикету, роли, результату и дате. Если запрос не удался, значение остаётся «неизвестно», а при отсутствии PR консоль пишет «PR ещё не создан» (#676).
- **[Оценка запуска в dispatch status]:** `dispatch status` показывает для каждого dispatch оценку `startup`: состояние worker (`absent`, `reported`, `rejected-at-startup`, `stopped`, `live` или `unknown`), классификацию сбоя и то, что осталось неизвестным. Capacity, rate-limit и service-unavailable различаются между собой и отделены от дефектов кода (#679).
- **[Проверка флагов adapter]:** `dispatch send` сверяет `--adapter-arg` с `dispatch --help` adapter и отклоняет неподдерживаемый флаг до передачи brief, оставляя dispatch одобренным и неотправленным. Если справка не отвечает, причина попадает в `adapter_preflight` как ограничение, а не как подтверждение возможностей (#679).
- **[Проба runtime без worker]:** `dispatch runtime-probe` проверяет app-server runtime по brief: модель в `model/list`, поля `thread/start` и один `turn/start` на read-only thread без инструментов. Ошибка capacity, rate-limit или недоступности после `thread/start` даёт классифицированный сбой, а не READY; проба ничего не пишет в ledger и не заменяет model self-report (#679).

### Fixed

- **[Рекомендация для списка в настройке]:** Принятая рекомендация для поля-списка обновляет галочки выбора, а последующие правки сохраняются; частичный выбор больше не искажает JSON черновика (#676).
- **[Преждевременный abandon]:** Предупреждение о молчащем dispatch и сообщения о восстановлении называют read-only команды `batch auto-report`, `batch decision-packet`, `dispatch status` и `ledger validate` и предлагают ожидание, `resume-stop` или `rewind`, а `batch abandon` остаётся отдельным решением человека. Исчерпанный бюджет инфраструктурных повторов оставляет batch в состоянии остановки до выбора человека, счётчики не сбрасываются (#679).
- **[Перезапуск неизвестного worker]:** `batch resume-stop` отказывает, если `dispatch status` показывает worker в состоянии `live` или `unknown`, пока оператор не остановит worker через runtime и не повторит команду с `--runtime-stopped`. Прежний путь для отклонённого self-report, отчёта и сбоя запуска не меняется (#679).

- **[Строгие enum отчёта]:** `blockers` и `risks` требуют объект `{"status": "none", "details": ""}` либо `{"status": "present", "details": "описание"}`, а результат проверки — ровно `pass`, `fail` или `not_run`. Старые строки, `passed`, `not-run` и `not_run_architect_read_only` больше не принимаются; сохранённые отчёты не переписываются (#672, #674).

## [1.3.2] - 2026-10-11

### Added

- **[Ручное восстановление оркестрации]:** Остановленный `auto`-batch можно возобновить командой `batch resume-stop`, а вернуться на предыдущий этап — командой `batch rewind --to`. Принятые отчёты и решения сохраняются, `ledger validate` проверяет журнал без записи, а ранний сбой с кодом 429 больше не требует checkpoint (#662).

Пайплайн идёт дальше, а publish ждёт, пока более поздний gate независимо подтвердит стадию. `batch resume-stop` теперь распознаёт и инфраструктурную причину в тексте blocked report; решение остаётся за человеком (#662).
- **[Порог повтора по замечаниям review]:** Параметр `auto_retry_min_severity` и флаг `batch create --auto-retry-min-severity` задают, с какой серьёзности замечаний review `auto` отправляет работу на повтор. По умолчанию `info`: прежнее поведение не меняется (#662).

### Changed

- **[Просмотр отчёта auto не пишет остановку]:** Команда `batch auto-report` только читает состояние. Остановку записывает `batch auto-decide`: batch переходит в `paused`, откуда его возобновляет человек (#662).
- **[Единый abandon]:** Оба пути отказа записывают `abandoned` с `last_accepted`, поэтому `batch create --supersedes` принимает любой из них (#662).

Явный `--worktree` проверяется в `dispatch preflight` и `dispatch send` (#662).
- **[Строже batch resume]:** Команда `batch resume` отказывает для batch с `approval_policy: auto`, записанной остановкой или ручным восстановлением. Для них используется `batch resume-stop` (#662).

- **[Итоговый отчёт auto]:** `batch auto-report` показывает находки координатора, которые ещё не попали в brief. Отчёт считает расход бюджета на один dispatch, а подсказка следующего шага учитывает смену политики.
- **[Очистка ledger]:** `ledger clean` больше не удаляет checkpoint живых batch. При нечитаемой записи batch команда отказывает и ничего не удаляет.
- **[Повтор после решения политики]:** Инфраструктурный повтор проверяет хеш QA-отчёта. Отчёт, изменённый после решения, больше не разрешает новый brief.
- **[Публикация dispatch]:** `dispatch publish` ограничивает время `git push` и точно сверяет ветку на remote. Зависший push больше не держит блокировку ledger.
- **[Освобождение очереди QA]:** Прерванный `qa run` освобождает lease и очередь QA. Захват очереди запуском `integration local-qa` больше не ломает восстановление dispatch.
- **[Checkpoint после сдвига базы]:** Координатор сравнивает checkpoint разработчика с базой отчёта после сдвига integration-ветки. Файлы из upstream больше не вызывают ложный отказ.
- **[Разрешение конфликтов]:** `integration resolve` после гонки с target называет созданный batch и точную команду `batch abandon`. Повтор resolve после этого проходит.
- **[Проверка локального QA]:** `integration local-qa` правильно сообщает, что ветка не основана на target. `context-package register` сравнивает `--base-commit` с фактической базой пакета.
- **[Файлы не в UTF-8]:** Координатор читает diff с файлами в устаревших кодировках без аварийного завершения. Отчёт или манифест роли не в UTF-8 даёт ошибку с инструкцией.
- **[Context Package]:** Context Package включает изменённые файлы с не-ASCII именами и вложенные ADR. Сбой Git при сборке пакета даёт ошибку с инструкцией.
- **[Устойчивость Repo Map]:** Repo Map переходит в деградированный режим при повреждённом lock, политике не в UTF-8 и ошибке чтения bundle. Кэш больше не оставляет временные файлы.
- **[Память проекта]:** Память принимает glob-шаблоны в корне проекта. Занятый индекс даёт ошибку «memory writer busy».
- **[Инвентарь интеграций]:** Установщик больше не перезаписывает нечитаемый `.harness/integrations.json`. Команда просит исправить файл и сохраняет записи проекта.
- **[Статистика доставки]:** Отчёт статистики проверяет карточку тарифов и сообщает инструкцию при нечитаемых файлах. Повреждённые записи ledger больше не прерывают отчёт.
- **[Пульт harness console]:** Экраны пульта показывают ошибку фонового запуска вместо бесконечного статуса «выполняется…». Дашборд по умолчанию перехватывает вывод команд.
- **[Сводка qa-gate]:** Сводка `qa-gate` сообщает `Status: ERROR`, если команду нельзя запустить. `diff_coverage` учитывает изменённые файлы с не-ASCII именами.

### Security

- **[Push из issue-ветки]:** Хук `block-direct-master` блокирует `git push --all`, `--branches`, `--mirror` и glob-refspec. Такие push могли обновить `main` или `integration/*`.
- **[Проверка приватных имён]:** `check_private_terms` блокирует публикацию, если Git не ответил вовремя. Раньше таймаут пропускал проверку.
- **[Каталог поколений ledger]:** Ledger отклоняет имя поколения с разделителями пути. Указатель больше не выходит за каталог ledger.
- **[Список vendor snapshot]:** Проверка vendor snapshot сверяет список файлов в `SHA256SUMS`, а не только их число. Лишняя или повторная строка больше не скрывает непроверенный файл.
