# Кэш cargo в QA-контейнерах

**Статус: ACCEPTED (2026-11-13).** Документ дополняет ADR 0022 (запуск команд QA в контейнере),
ADR 0023 (план доступа и его digest) и ADR 0025 (контейнерный исполнитель): он фиксирует, где
QA-прогон хранит загруженные crates и собранные зависимости Rust и почему собранный код не
переходит из прогона одного кандидата в прогон другого.

## Контекст системы

`qa run` выполняет каждую одобренную команду в отдельном контейнере `--rm` внутри одного
clean-room: run root содержит checkout кандидата и временный каталог и удаляется после прогона.
Образ QA задаёт `CARGO_HOME=/usr/local/cargo` в своём слое, поэтому каждый cargo-этап заново
скачивает индекс реестра и crates и заново распаковывает их исходники. Свежие mtime распакованных
исходников перезапускают build-скрипты с `rerun-if-changed` (например, bundled `libsqlite3-sys`) и
всё, что от них зависит: каждый cargo-этап собирает зависимости с нуля.

Поле `environment` плана доступа передаёт только имена переменных, а значения берутся из окружения
`harness-runtime serve`. Задать путь кэша через `environment` можно только ручной настройкой
окружения serve.

## Действующий контракт

### 1. Выбор механизма

| Вариант | Суть | Решение |
|---|---|---|
| A | Ничего не кэшировать | отвергнут: каждый прогон и каждый cargo-этап скачивает и собирает зависимости заново |
| B | Элемент `cache` плана с полем `variable` для `CARGO_HOME` и `CARGO_TARGET_DIR` внутри run root | **выбран** |
| C | Сборочный каталог между прогонами с ключом по `Cargo.lock`, toolchain и профилю | отвергнут: код кандидата (`build.rs`, тесты) исполняется с правом записи в этот каталог и может оставить в нём собранный код для следующего кандидата; надёжно отделить зависимости от кода workspace внутри `target/` нельзя |
| D | sccache или другой внешний кэш компиляции | отвергнут: новая зависимость образа и демон, тот же вопрос доверия к записи |
| E | Именованный volume движка | запрещён: исполнитель не создаёт долгоживущих объектов движка (ADR 0025) |

### 2. Поле `variable` у элемента `cache`

- Элемент `filesystem` с `resource: "cache"` может назвать переменную окружения:
  `{"resource": "cache", "path": "<abs>/.harness/.sandboxes/cache/cargo", "access": "write",
  "variable": "CARGO_HOME"}`.
- Исполнитель сам передаёт контейнеру `--env <variable>=<разрешённый путь кэша>`. Значение —
  корень, уже закреплённый в плане и его digest; это не значение из окружения serve и не секрет.
- `variable` допустимо только у `cache`, имя соответствует `[A-Za-z_][A-Za-z0-9_]*`, уникально
  среди элементов `cache` компонента, не совпадает с именем из `environment` того же плана и не
  входит в имена, которые задаёт runtime: `HOME`, `GIT_CONFIG_COUNT`, `GIT_CONFIG_KEY_0`,
  `GIT_CONFIG_VALUE_0`, `HARNESS_EXECUTOR`, `HTTP_PROXY`, `HTTPS_PROXY`, `http_proxy`,
  `https_proxy`, `NO_PROXY`, `no_proxy`, `TMPDIR`, `TMP`, `TEMP`, `GIT_CEILING_DIRECTORIES`,
  `HARNESS_VERIFY_COLD`, `CARGO_TARGET_DIR`.
- План без `variable` сохраняет прежнюю форму и прежний `plan_digest`.
- Монтирование не меняется: только bind mount тех же путей, `--rm --init`, `--user uid:gid`,
  tmpfs `HOME`.

### 3. `CARGO_TARGET_DIR` одного прогона

Runtime QA-прогона задаёт `CARGO_TARGET_DIR=<run_root>/cargo-target` наравне с `TMPDIR`. Каталог
общий для всех cargo-этапов и всех workspace одного прогона и удаляется вместе с run root.
Сборочный каталог между прогонами не переиспользуется. Значение runtime всегда важнее имени из
`environment` плана: голое `--env CARGO_TARGET_DIR` плана не выводится.

### 4. Почему ключ по `Cargo.lock` и toolchain не нужен

- Кэш реестра cargo (`registry/index`, `registry/cache`, `registry/src`, `git/`) адресуется
  именем, версией и источником crate и не зависит от toolchain.
- Сборочный каталог живёт один прогон одного кандидата.
- Toolchain уже входит в `environment_fingerprint` этапа через digest образа (`runtime_images`).

## Операционные последствия

- Каталог кэша создаёт человек до прогона (`mkdir -p`): bind mount и проба записи требуют
  существующий каталог. Рекомендуется абсолютный путь в основном checkout
  (`.harness/.sandboxes/cache/cargo`): относительный путь разрешается от worktree dispatch.
- Доступ к crates.io остаётся явным: хосты реестра перечисляются в `network.hosts` операции `qa`.
- Evidence запуска записывает только имена переменных (`launch.settings`); значения путей
  попадают только в argv контейнера, как `TMPDIR`.
- Остаточные риски: кэш загрузок доступен кандидату на запись, поэтому кандидат может изменить
  распакованные исходники crates для следующих прогонов; cargo проверяет контрольные суммы архивов
  `registry/cache`, но не распакованных `registry/src`. Sparse-индекс по-прежнему делает
  запросы к реестру при разрешении зависимостей.
- Процедура измерения времени QA до и после изменения описана в разделе «Caches»
  `harness/docs/container-executor.md`.
