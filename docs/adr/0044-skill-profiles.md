# Профили скиллов и измерение стартового контекста

**Статус: PROPOSED (2026-11-27).** Тикет #838, ADR 0024, ADR 0037, ADR 0039. Контракт станет
ACCEPTED после спайка runtime: он проверяет поведение Claude Code и Codex (гипотезы H1–H6 ниже) и
фиксирует коэффициенты оценщика.

## Контекст системы

Каждая сессия Claude Code и Codex получает стартовый контекст: корневые инструкции, rules,
метаданные скиллов и описания субагентов. Харнес не умел его измерять и не мог дать изолированной
сессии узкий набор скиллов. Discovery-ссылки `.claude/skills` и `.agents/skills` указывают на весь
`.harness/skills`, поэтому каждая сессия видит весь установленный набор. Замер собственной установки
харнеса показал, что корневые инструкции весят примерно в 8 раз больше видимых метаданных скиллов,
поэтому измерение охватывает все источники, а не только скиллы.

В целевом проекте установщик скрывает от git только `/docs/tasks/` и `/.harness/.sandboxes/`
(`GITIGNORE_LINES`). Поэтому `.harness/skills` и discovery-ссылки там обычно хранятся в git и
попадают в каждый linked worktree, в том числе в issue worktree worker-а. В репозитории самого
харнеса эти пути игнорируются, и в linked worktree их нет. Контракт применения профиля рассчитан на
оба случая.

## Действующий контракт

### 1. Конфигурация и resolved-файл

- Профили описывает необязательный файл `.harness/skill-profiles.json` со своей схемой и
  валидатором. В нём: именованные профили (списки имён скиллов), необязательный профиль
  `interactive`, профиль на роль внешнего worker-а и запасной профиль для всех worker-ов, бюджет
  стартового контекста в токенах оценки (общий и на профиль) и необязательный размер окна модели
  для доли в отчёте. Файл может содержать только бюджет без профилей.
- Источник — только этот файл. Переменные окружения, параметры инструментов и текст brief
  игнорируются, как в ADR 0024 §1.
- Профиль ссылается на любое имя из установленного `.harness/skills`: first-party, vendor или
  проектный скилл. Файлы скиллов не меняются; `lock-project-skills` не меняется.
- Зависимости скиллов resolver находит статическим сканом файлов каждого скилла профиля.
  Относительная ссылка `../<установленный скилл>/` — жёсткая зависимость: инструменты нормализуют
  `..` по тексту пути, поэтому без зависимости в профиле файл не найдётся. Упоминание `/<скилл>` в
  тексте — мягкая зависимость: упоминание бывает и предложением следующего шага, поэтому оно даёт
  только `warn`, а поле профиля `ignore_mentions` подавляет его для перечисленных имён.
- Неизвестный скилл, отсутствующая жёсткая зависимость, неизвестная роль в `worker.roles` или
  нарушение схемы останавливают установку с кодом 2; существующие каталоги и resolved-файл не
  меняются. Если capability `backend-orchestration` не установлена, раздел `worker` не применяется,
  и health сообщает это как `warn`.
- `harness init`, `adopt`, `update` и `harness health --fix` вызывают одну функцию сборки. Она
  пишет `.harness/skill-profiles.lock.json` и каталоги профилей. Повторный запуск без изменений
  оставляет файлы байт-в-байт.
- Resolved-файл: `{schema, config_sha256, profiles: {<имя>: {skills: [{name, path, sha256}],
  skill_profile_sha256}}, interactive, worker}`, где `sha256` — SHA-256 байтов `SKILL.md`, а
  `skill_profile_sha256` — SHA-256 компактной канонической формы `{"profile", "skills": [{"name",
  "sha256"}]}`, той же, которой считается `hook_policy_sha256`. Профиль роли:
  `worker.roles[<роль>]`, иначе `worker.default`, иначе профиля нет.

### 2. Применение: каталог профиля

- Для каждого профиля строится `.harness/skill-profiles/<профиль>/`: по ссылке на каждый скилл
  профиля и свой `REGISTRY.md`. Полный `.harness/skills/REGISTRY.md` не меняется.
- Main checkout: при заданном `interactive` ссылки `.claude/skills` и `.agents/skills` указывают на
  его каталог; без него — на `.harness/skills`, как раньше. Coordinator работает в main checkout и
  видит тот же набор.
- Worktree пользователя получает интерактивный профиль командой `harness worktree-skills <repo>
  <worktree>` тем же механизмом, что и worker (ниже); `--clear` восстанавливает ссылки.
  Автоматический запуск из SessionStart не используется.
- Внешний worker. Adapter (`claude_worker.py`, `codex_worker.py`) перед запуском:
  1. сверяет SHA-256 каждого `SKILL.md` main checkout со снимком профиля из brief и отказывает в
     запуске при расхождении;
  2. строит каталог сессии `.harness/.sandboxes/skill-sessions/<dispatch>/` со ссылками на
     `<main>/.harness/skills/<имя>` и записывает в его `state.json` исходное состояние
     discovery-ссылок worktree;
  3. отслеживаемой git ссылке `.claude/skills` или `.agents/skills` ставит `skip-worktree` в
     индексе этого worktree и перенаправляет её на каталог сессии, а отсутствующую ссылку создаёт.
     Поэтому изменение не видно в `git status`, не попадает в `changed_files` и не даёт ложных
     `scope_warnings`.
  После выхода worker-а adapter восстанавливает исходные ссылки и снимает флаг; при `dispatch
  cancel` и recovery то же делает coordinator по `state.json`.
- Adapter-ы ставятся в проект как автономные stdlib-скрипты, поэтому логика каталога сессии и
  переключения ссылок живёт в самих adapter-ах и не импортирует пакет `harness`.
- In-process роли и субагенты работают в процессе родителя. Если спайк подтвердит, что субагент
  Claude Code не наследует список скиллов родителя (H5), профиль роли переносится в поле `skills`
  субагента; иначе субагент наследует набор родителя, и это документированное ограничение.
- Нативные переключатели runtime (deny `Skill(<имя>)`, `skills.config`) не используются: один
  механизм через уже поддержанные пути discovery работает одинаково в обоих runtime.
- Если runtime находит полный набор в обход каталога профиля (например, поднимается к родителю —
  H4), `harness health` даёт warn «изоляция не гарантирована», а документация описывает это
  ограничение.

### 3. Профиль не граница безопасности

Агент может прочитать любой `SKILL.md` по пути. Профиль сокращает только стартовый контекст и
автоматический выбор скилла. Аналог `protect-hook-policy` для профилей не вводится.

### 4. Привязка к dispatch

- `dispatch create` закрепляет в brief снимок resolved-списка скиллов роли и
  `skill_profile_sha256`. Поле входит в `OPTIONAL_TRANSITION_FIELDS`; `recovery.py` сверяет его
  при продолжении.
- Supervisor Rust перед запуском worker-а пересчитывает digest только по снимку brief-а, как для
  `hook_policy` (ADR 0024 §3), и отказывает при расхождении. Adapter строит ссылки из снимка,
  поэтому правка конфигурации после approval не меняет запущенный dispatch.
- Brief без `skill_profile_sha256`, созданный до этого контракта, принимается; worker получает
  весь набор.
- `dispatch publish` отказывает, если коммиты batch меняют `.claude/skills` или `.agents/skills`,
  с remedy «восстановите ссылку и пересоберите коммит». Это последняя линия защиты на случай, если
  флаг `skip-worktree` снят или ссылка изменена в обход adapter-а.

### 5. Измерение и оценщик

- Новая версия оценщика в `harness/token_estimator.py` считает ASCII- и не-ASCII-байты с двумя
  коэффициентами. Каждый коэффициент — консервативный максимум по двум runtime, поэтому оценка
  остаётся верхней границей. Коэффициенты калибруются разовым ручным замером на зафиксированном
  корпусе и закрепляются golden-тестом; в работе оценщик сети не использует.
- Новая версия заменяет `utf8-bytes-per-2-v1` у всех потребителей: Context Package, бюджет роли,
  Repo Map, поиск по памяти, preflight dispatch. Пути, где известен только размер файла, применяют
  ко всем байтам коэффициент для не-ASCII. Запись Context Package получает
  `token_estimator_version` и новый `schema_version`; старые записи читаются как
  `utf8-bytes-per-2-v1`. Запущенный dispatch доделывает работу со своим закреплённым
  `context_budget`.
- Состав стартового контекста зависит от runtime. Claude Code: `CLAUDE.md` с `@`-импортами,
  `.claude/rules/*.md`, метаданные скиллов профиля без скрытых `disable-model-invocation` (если
  спайк подтвердит H1), описания `.claude/agents/*.md`. Codex: `AGENTS.md`, `.claude/rules/*.md`
  (обязательное чтение по ADR 0039), метаданные скиллов профиля по результату проверки H2.
- Глобальный профиль пользователя (`~/.claude/CLAUDE.md`, `~/.claude/skills`, `~/.agents/skills`)
  выводится отдельной строкой «вне проекта» и в бюджет не входит. MCP отмечается «не измерено».
- Команда `harness context-budget` (рабочее имя, есть `--json`) выводит таблицу «источник →
  оценка» в разрезе runtime × профиль. Проверка `harness health` использует тот же расчёт.
  Превышение бюджета в любой ячейке даёт `warn` с итогом, порогом и крупнейшими источниками. Без
  порога проверка даёт `ok` с итогами и подсказкой, где задать бюджет; `fail` не используется.

### 6. Drift

`snapshot_diff` и `files.skill_snapshot` не меняются: каталоги профилей не входят в файлы пакета.
Проверка `files.skill_profiles` сверяет каталоги профилей с resolved-файлом и сообщает мягкие
зависимости и неполную изоляцию; бюджет проверяет `files.context_budget`. `files.discovery_links` принимает
каталог профиля `interactive` как цель ссылки. Суженный набор не считается drift.

### Гипотезы, которые проверяет спайк

- H1: `disable-model-invocation: true` убирает описание скилла из стартового контекста Claude Code.
- H2: `allow_implicit_invocation: false` в Codex оставляет описание в контексте.
- H3: worker Claude Code без `Skill` в `--allowedTools` всё равно получает список скиллов.
- H4: runtime в linked worktree внутри main checkout находит `.claude/skills` или `.agents/skills`
  родителя.
- H5: субагент Claude Code не наследует список скиллов родителя.
- H6: в Codex есть `[[skills.config]] enabled = false`, в Claude Code — `--disable-slash-commands`.

Спайк также проверяет, как флаг `skip-worktree` ведёт себя при rebase роли rebaser, если
integration-ветка меняет discovery-ссылки.

## Операционные последствия

- **Без конфигурации ничего не меняется.** Если `.harness/skill-profiles.json` нет, discovery-ссылки,
  `init`, `update` и `health` ведут себя как раньше; это проверяет регрессионный тест.
- **Удаление.** `harness uninstall` удаляет каталоги профилей, resolved-файл и схему профилей, а
  `.harness/skill-profiles.json` обрабатывает так же, как `.harness/project.json`. Каталоги сессий
  лежат в `.harness/.sandboxes/` и удаляются вместе с ним.
- **Публикация.** Коммит, меняющий discovery-ссылки, `dispatch publish` отвергает.
- **Context Package.** Запись получает `schema_version` 4 и `token_estimator_version`.
- **Пороги Context Package.** Смена оценщика меняет `estimated_tokens` новых пакетов и допуск
  dispatch по `context_budget`; golden-данные оркестрации обновляются вместе с ней.
- **Windows.** Ссылки на отдельные скиллы требуют того же symlink-режима (Developer Mode), что и
  текущие discovery-ссылки.
- **Проверки:** тесты валидатора и resolver-а, golden-тест оценщика, тест материализации и
  регрессии без файла, сверка digest в recovery и Rust, ручная проверка изоляции в обоих runtime.

## Рассмотренные альтернативы

- **Профили в `.harness/project.json` (образец `hook_policy`).** Отклонено: владелец выбрал
  отдельный файл с resolved-файлом, который даёт точку для drift и health.
- **Профиль в dispatch brief как источник.** Отклонено: coordinator, то есть агент, сам определял
  бы набор worker-а, что противоречит ADR 0024 §1.
- **Нативные переключатели runtime.** Отклонено: два разных непроверенных механизма; запрет вызова
  может не сокращать контекст.
- **Материализованные копии профилей.** Отклонено: дублирование файлов и сложнее drift и update.
- **Переключение ссылок worker-а без `skip-worktree`, защита только в publish.** Отклонено: worker
  видит изменённые ссылки в `git status` и может их закоммитить; каждый такой случай — отказ и retry.
- **Переключением ссылок владеет supervisor Rust.** Отклонено: файловые и git-операции в Rust,
  ссылки в Windows через FFI-крейт, изменение receipt и reconcile; самый большой объём.
- **Только относительные ссылки как зависимости.** Отклонено: профиль без вызываемой зависимости
  проходит молча и ломается только в сессии.
- **Явный манифест зависимостей `requires`.** Отклонено: ручное сопровождение для всех скиллов,
  включая каждый новый vendor-снимок.
- **Оценщик `utf8-bytes-per-2-v1` без изменений.** Отклонено: для английского текста он завышает
  оценку примерно вдвое.
