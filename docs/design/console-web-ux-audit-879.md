# Аудит макетов консоли для веб-версии

**Дата:** 3 ноября 2026. **Задача:** #879, родитель #862, трек Web Console эпика #784.
**Основа:** `integration/web-console`, commit `8d1b487d580e714e2297090f52e0d46cc444ad70`.
**Статус:** отчёт аудита; рекомендации для макетов #880/#881, не утверждение нового дизайна.

Принятые макеты дают основу информационной архитектуры: десять разделов, общий контекст,
списки с деталями, план перед действием и явные причины отказа. Их стоит сохранить. Перед
реализацией веба нужно спроектировать адаптивный каркас, работающую навигацию, общий жизненный
цикл команд и состояния соединения. Добавлять ещё один обзорный dashboard для этого не нужно.

## Предмет и метод

Прочитаны все 12 HTML-страниц из [console-mockups](console-mockups/README.md), общий
`console.css`, [ADR 0028](../adr/0028-web-console.md), [ADR 0027](../adr/0027-console-task-titles.md)
и сохраняемая часть [ADR 0009](../adr/0009-harness-console.md). Применён навык `ui-ux-audit`
([Madina Gbotoe](https://madinagbotoe.com/),
[исходная методика](https://github.com/mgbotoe/claude-code-share/tree/main/claude-code-skills/ui-ux-audit)):
инвентаризация существующего → проверка дублирования → доказуемые пробелы → минимальные улучшения.
Портфельные примеры из навыка к инженерной консоли не переносятся.

Исходники проверены в браузере через локальный HTTP-сервер. Все страницы открыты и проверены
по DOM; визуально рассмотрены главная, восстановление и контейнерный маршрут. Главная проверена
при viewport 390×844 CSS px; восстановление и контейнерный маршрут — при 1600×1100.
Остальные размеры ниже — предложенная матрица приёмки будущих макетов, а не выполненные проверки.

В этой ветке нет `design-contract-720.md`. Отдельно прочитано принятое уточнение #720/#725 из
[зафиксированной версии документа](https://github.com/PVMalove/claude-agent-harness/blob/6a7f74807b109b00b20201b9443f12a5fa38fefe/docs/design/console-mockups/design-contract-720.md):
вариант A, компактное меню, единый фон, контекст после короткого содержимого, символ и текст
статуса, полные причины ошибок. Исторические заливки и отступы HTML не отменяют этого решения.
Документ здесь не копируется; пороги TUI в столбцах не становятся браузерными breakpoint-ами.

Это аудит дизайн-источника, не проверка реализованного веб-клиента и не исследование с
пользователями. Демонстрационные числа, пути и сообщения не доказывают возможности runtime.
Статичность HTML ожидаема для макета; она становится пробелом только при попытке использовать
эти файлы как готовую спецификацию веб-поведения. Исходные макеты и TUI #720 не изменяются.

| [Восстановление](console-mockups/recovery.html) | Подтверждённая граница, runtime отдельно от lifecycle, unknown, stale approval, независимое перечитывание (строки 56–137) | Сохранить контекст при переподключении; серверный отказ на устаревшее решение, без оптимистического «продолжено» |
| [Контейнерный запуск](console-mockups/container-route.html) | Шесть этапов, mounts/hosts/env без значений, digest, worker/QA/evidence отдельно, защита живого worker | Полный digest и пути по доступному действию вместо одной клавиши `d`; потеря наблюдения отдельно от завершения |

Пустые и ошибочные состояния **уже нарисованы** для ряда экранов. Например, Repo Map различает
отсутствие кэша и сбой сборки, а отчёты — пустой фильтр и недоступный ledger. Повторная разработка
этих состояний с нуля увеличит объём без пользы; требуется общая матрица и недостающие переходы.

## Проверка избыточности

| Повтор | Решение | Почему это не потеря функции |
| --- | --- | --- |
| Версия, проект, ветка в шапке, полосе пути и контексте главной (`home.html`: `.top`, `.strip`, `aside`) | Один постоянный контекст проекта; на странице оставлять только контекст текущего объекта | Полный путь доступен по раскрытию/копированию, не повторяется в трёх больших блоках |
| Сессии на главной и в оркестрации, batch в оркестрации и отчётах | Сохранить разные входы, использовать общие идентификаторы и переход к одной сущности | Главная отвечает «что требует внимания», оркестрация — «где стадия», отчёт — «какое доказательство»; это разные задачи |
| Ошибка в карточке диагностики и в раскрытом списке группы | Карточка ведёт к той же проверке, детали раскрываются один раз | Сводный счётчик и подробность нужны, два полных текста подряд — нет |
| Запуск обновления из настроек адаптеров, каталога и отдельного экрана | Несколько входов в один план/подтверждение/job | Пользователю не приходится выяснять, какой из независимых запусков он одобрил |
| История batch, QA-лог, вывод команды и будущий live-лист | Один набор фактов с фильтрами по batch/dispatch/job; ссылки между представлениями | Живой лист не заменяет доказательства QA и не создаёт второй журнал истины |
| Команда, основная кнопка, клавиша Enter и палитра | Одна операция с разными способами вызова | Копирование CLI остаётся отдельным действием и ничего не запускает |

Не рекомендуется добавлять вторую панель всех метрик на главную, ещё один редактор памяти
рядом с Repo Map, отдельную реализацию подтверждений для каждого экрана или обязательный
AI-чат. Эти добавления дублируют существующие поверхности либо не следуют из #879/#862.

## Дополнительный проход unslop

По запросу владельца применена методика [unslop](https://github.com/heydamir/unslop),
автор Damir Sokolovsky, CC BY 4.0; прочитаны `SKILL.md`, `references/signs.md` и
`references/tokens.md` на revision `a6f121eee5f29c2f74976b75456feae8b66afb3a`.
Выбран точечный проход: в исходниках нет цветных градиентов, свечения, декоративных hero
и рекламных обещаний, поэтому полная смена оформления не обоснована. Рекомендации ниже
не означают изменения исходных макетов или утверждения новой палитры.

Направление: **продукт** — пульт наблюдения за агентами и принятия решений;
**характер** — спокойный, точный, собранный; **среда** — рабочий инструмент для длительного
чтения логов; **акценты** — выбранная сессия и действие, требующее внимания;
**деталь** — единое оформление клавиш и статусов рядом с фактами.

| Проход | Наблюдение и свидетельство | Предлагаемая правка веб-варианта |
| --- | --- | --- |
| 1. Отступы | В `console.css` смешаны 14/18/22/26 px, навигационные строки 42 px; `.dense` задаёт второй набор размеров | Одна шкала отступов с шагом 4 px, компактные строки меню 36 px; не уплотнять формы ценой потери подписи |
| 2. Цвет | Блоки используют `--surface`, `--panel`, рамки и отдельный фон; активная строка получает дополнительный outline | Сохранить палитру и семантические статусы, применить принятый единый фон; акцентом обозначать выбор и основное действие |
| 3. Значки | Статусы и замки показаны символами разного начертания (`.e-*`, worktree); смысл уже продублирован текстом | Согласовать размер и выравнивание символов; не удалять их как «декор», поскольку символ + текст — принятый контракт |
| 4. Текст | В узкой главной действия названы «2 →» и «8 →»; исторические пометки «предлагаю» входят в демонстрационные страницы | В веб-варианте оставить смысловые названия действий, авторские пояснения перенести в отдельное сравнение |
| 5. Типографика | `nav h6`, `.sec-h`, `aside h5` задают uppercase и tracking; часть текста меньше 14 px | Заголовки обычным регистром, несколько согласованных размеров, табличные цифры; сохранить читаемый моноширинный текст логов |
| 6. Компоновка | Отдельные wide/narrow копии с фиксированными размерами, многократно повторённый контекст | Один адаптивный каркас и единый контекст; порядок разделов и существующие функции сохранить |
| 7. Детали | `.btn.dis` обозначает запрет только внешним видом; подсказки клавиш и обрезание значений оформлены по-разному | Настоящие состояния элементов, постоянная причина запрета, единый вид клавиш и раскрытие полного значения |
| 8. Визуальные материалы | Изображений-наполнителей и графиков без данных нет | Не добавлять иллюстрации, графики и новые метрики ради оформления; содержанием остаются сессии, факты и evidence |
| 9. Движение | Зацикленной анимации и `transition-all` нет | Не добавлять декоративное движение; смена состояния не должна сдвигать читаемый вывод |

При конфликте общего рецепта unslop с утверждённым контрактом консоли приоритет имеет
контракт: сохраняются статусные символы, существующий акцент, функции и порядок разделов.
Сравнение будущих правок должно показывать исходник и вариант рядом либо переключателем,
а также явно помечать демонстрационные данные. Видео, установка навыка и генерация
изображений для этого прохода не требуются.

## Пробелы и приоритеты

**P0** — до утверждения веб-макетов: ошибка способна привести к неверному решению или повторному
действию. **P1** — до реализации соответствующего экрана: без этого основной сценарий
неполон. **P2** — после согласования основного пути: улучшение чтения и плотности.
Это приоритет дизайна, не заявление об обнаруженной уязвимости работающего приложения.

### P0 · G1. Общий жизненный цикл команды

**Доказательство:** `update-harness.html:195–197` запрещает выход во время обновления;
`harness.html:232–242` показывает исполнение и повтор по Enter, но не уход и возврат к job.
ADR 0028 §2, напротив, закрепляет job за сервером и сохраняет его при отключении клиента.

**Улучшение:** один компактный индикатор активной команды с переходом к выводу; уход со страницы
не отменяет job. Показать «проект занят» со ссылкой на уже идущую команду, отдельное подтверждение
отмены и результат повторного подключения. После неоднозначного ответа сначала наблюдать job;
не предлагать слепой повтор мутирующего действия. Двойное нажатие не создаёт второй запуск.
Это общий компонент для всех экранов, а не новый dashboard команд.

### P0 · G2. Свежесть, потеря связи и устаревшее решение

**Доказательство:** в макетах нет сценария WebSocket reconnect; `reports.html:151–153` уже
сохраняет прежние данные при ошибке, а `recovery.html:119–129` описывает конкурентную правку
и stale approval. ADR 0028 §3 добавляет курсор и `cursor_expired`.

**Улучшение:** различать загрузку, свежий снимок, старый снимок, переподключение, потерянный
курсор и отказ источника. Сохранять прочитанные данные с отметкой времени; после истечения
курсора перечитывать снимок и обозначать возможный разрыв истории. При потере связи не
объявлять worker остановленным. Подтверждение относится к текущему плану/переходу: сервер
повторно проверяет его, устаревшее окно получает объяснение и новый просмотр, не обход gate.
Это дополняет имеющиеся защиты, а не заменяет их клиентским запретом кнопки.

### P0 · G3. Другой проект не подменяет текущий

**Доказательство:** `open-project.html:35` обещает смену проекта для всех экранов, а
`help.html:50` описывает установочный мастер. ADR 0028 §1 запрещает переключение проекта
внутри браузерного клиента: один сервер обслуживает один проект.

**Улучшение:** для веба показать кандидатов и копируемую команду запуска отдельной консоли.
Не переносить терминальный мастер как браузерный доступ к произвольным каталогам; текущий
проект и его job остаются прежними. Это замена смысла одного веб-экрана, без изменения TUI
и без расширения доступа сервера. В справке нужно то же объяснение.

### P1 · G4. Узкая ширина и прокрутка

**Доказательство:** `console.css:15–16` и встроенные стили `home.html` задают ширины 1440/780 px.
Медиа-запросов нет. В браузере при viewport 390 px DOM главной показал ширину документа 1472 px;
два `.app` остались 1440 и 780 px. Узкая иллюстрация расположена ниже широкой и не заменяет её.
`main`, `.page`, `aside` используют `overflow:hidden`; это требует проверки длинных данных.

**Улучшение:** один адаптивный каркас вместо двух копий страницы: сворачиваемая навигация,
контекст под содержимым, перенос путей, локальная прокрутка таблиц и вывода. Нельзя скрывать
причину disabled-действия или основную кнопку при смене ширины. Пороги выбрать по содержимому,
проверив 320, 390, 768, 1024 и 1440 CSS px и увеличение текста. Предложенная цель следует
[W3C Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html): обычное содержимое
перестраивается; для действительно двумерных таблиц возможна отдельная прокрутка.

### P1 · G5. Навигация описана, но её веб-контракт не задан

**Доказательство:** меню и крошки нарисованы на всех страницах; `home.html:188–213` даже
описывает возврат, сокращение пути и защиту черновика. При DOM-проверке ссылки страниц ведут
в `#` либо не имеют `href`; scripts отсутствуют во всех 12 страницах. Например,
в Harness все 36 ссылок имеют `href="#"`.

**Улучшение:** в #880 задать адреса разделов и выбранного batch/dispatch/job, Back/Forward,
восстановление вкладки и фильтров, поведение отсутствующего объекта. Меню только переходит;
переход не выполняет команду. При уходе из черновика показывать выбор сохранения/отказа по
контракту формы. Навигация из справки не обходит открытое подтверждение. Крошки и палитра
используют тот же маршрут, а не отдельный механизм исполнения.

### P1 · G6. Семантика элементов, фокус и клавиатура

**Доказательство:** DOM всех 12 страниц содержит ноль `input`, `select`, `textarea`, `button`.
Поля представлены `div`/`span`, действия — ссылками, disabled — классами `.dis`/`.off`,
вкладки — `span`. Это иллюстрации состояний, не доступные формы.

**Улучшение:** в новых макетах различить ссылки-переходы, кнопки-действия и поля с постоянной
подписью. Показать видимый фокус, раскрытие меню, полный цикл диалога и возврат фокуса к
инициатору; подтвердить, что опасная кнопка не получает автоматический фокус. Объяснять
недоступность рядом с действием. Не перехватывать цифры и буквы в полях ввода, не полагаться
на конфликтующие с браузером Ctrl+P/Ctrl+Q и F1/F2 как единственный способ управления.
Ориентир — [W3C Focus Visible](https://www.w3.org/WAI/WCAG22/Understanding/focus-visible.html).
Нет оснований утверждать, что текущий прототип уже соответствует WCAG или не имеет
браузерного фокуса вообще: ручная проверка screen reader и полный аудит доступности не выполнены.

### P1 · G7. Общая матрица пустых и ошибочных состояний

**Доказательство:** состояния уже есть у диагностики, отчётов, Repo Map, обновления и
восстановления; главная показывает только три сессии и две проблемы, оркестрация — заполненную
историю. В configuration прямо отсутствуют дальнейшие страницы мастера.

**Улучшение:** для каждого источника показать отдельно: ещё не запрашивали, загружаем, успешно
пусто, фильтр не дал совпадений, частичный ответ, отказ, устаревшие данные и успех. У каждой
ошибки — причина и безопасный следующий шаг; неизвестное значение не превращается в ноль
или зелёный статус. На главной отсутствие сессий не требует создания worker; в отчётах сброс
фильтра не выполняет команду; на конфигурации конфликт черновика не приводит к перезаписи.
При динамическом обновлении важные статусы должны быть доступны вспомогательным технологиям
без переноса фокуса ([W3C Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)).

### P1 · G8. Один живой лист с честной границей наблюдения

**Доказательство:** `orchestration.html` даёт историю batch, `reports.html` — завершённые
отчёты, `container-route.html` — отдельные receipt/inspect/exit/report. Единой последовательности
шагов агента и оркестрации в этих макетах нет; она требуется #862 и ADR 0028 §3.

**Улучшение:** один лист с привязкой к batch/dispatch и источнику события, фильтрами и ссылками
на отчёт, QA и решение человека. Когда пользователь читает старую часть, новые строки не
сдвигают её: счётчик и «К новым событиям» вместо принудительной прокрутки. Состояния «нет
событий», «история с разрывом» и «источник недоступен» различаются. Показывать только allowlist
наблюдения, без thinking, входов инструментов и raw JSON. По текущему ADR Codex показывает
plain-хвост с меткой «структура недоступна», не выдуманные структурированные шаги.

### P2 · G9. Плотность, термины и длинные значения

**Доказательство:** `home.html` содержит встроенную копию стилей, остальные страницы используют
`console.css`; исторические подписи страниц называют восстановление «7», контейнерный запуск
«6», хотя пункты меню 6 и 7 — отчёты и Repo Map. В узкой главной действия сокращены до «2 →»,
«8 →», а длинные строки сессий обрезаны. В справке смешаны описание клавиш и заметки автору.

**Улучшение:** единый набор веб-компонентов и названий в #880/#881, без правки архива #720.
Вложенные экраны идентифицировать крошками, не новой нумерацией меню. Краткое название задачи
показывать перед служебным ID; полные ID, пути, причины и digest доступны по раскрытию и
копированию. Сохранить символ + текст статуса и RU/EN, разделять running/pending/unknown/skip.
Длинные строки EN, Windows-пути и смешанный русский текст должны входить в примеры; отдельная
проверка контраста и метрик производительности остаётся для реализованного веба.

## Следующие макеты и проверка сценариев

В #880 сначала согласовать G1–G3 и каркас G4–G7: главная, навигация, команда, вывод,
подтверждение и общие состояния. В #881 применить тот же каркас ко всем остальным экранам и
нарисовать G8, затем уплотнить G9. Для визуального просмотра по дополнительному запросу владельца подготовлено
[сравнение до/после](console-web-unslop/README.md) всех 12 экранов. Исходники читаются без
изменений; просмотрщик применяет отдельные стили в изолированном iframe. Это визуальные
варианты для обсуждения, не реализация G1–G8 и не утверждённые макеты #880/#881.

Результат #879 не даёт разрешения реализовать новые
действия, менять права, gates или схему runtime. Доска задач имеет отдельный дизайн-тикет
#912; переносить её проектирование в этот аудит не требуется.

| Сценарий приёмки будущих макетов | Что должно быть видно |
| --- | --- |

интеграционных или e2e-тестов консоли. В #879 нет изменения исполняемого поведения: критерии
проверяются наличием отчёта, ссылками на свидетельства, приоритетами и неизменностью исходников.
Fedora/SELinux/rootless Podman и Windows остаются поддерживаемыми окружениями целевой
архитектуры; этот аудит не запускает контейнеры и не подтверждает платформенную совместимость.
