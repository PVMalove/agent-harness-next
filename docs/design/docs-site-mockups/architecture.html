Архитектура

Policy и исполнение разделены. Python принимает решения, Rust runtime хранит operational state и запускает процессы, а Git остаётся владельцем истории и кандидатов.

Кто владеет чем

В harness у каждой сущности ровно один writer. Это главное правило, из которого следуют остальные границы.

СущностьWriterЧто это значит
Lifecycle batch/dispatchRust runtimeПереходы сохраняются транзакцией; Python не пишет в store напрямую.
Approvals и policyPythonРешение принимает человек и policy-слой; runtime исполняет сохранённое решение.
Операционный intentRust storeIdempotency key, attempt и reconcile живут в одной транзакции.
Git-история и candidateGitКандидат, ветки и worktree — обычные Git-объекты; runtime их не переписывает.
AuditRust storeХэш-цепочка с checkpoint для инкрементальной проверки.
i

Fallback-writer запрещён. Если runtime недоступен, Python не начинает писать в файловый ledger «чтобы продолжить». Операция возвращает типизированную ошибку с remedy.

Rust runtime

harness-runtime serve — один процесс на state-каталог. Он слушает Unix domain socket на Linux или named pipe на Windows, проверяет peer identity и выполняет типизированные операции.

Runtime не решает policy: он принимает уже approved brief, проверяет digest-ы и исполняет только сохранённый план. Python не запускает worker-а или QA-контейнер напрямую.

Runtime store

Operational state — SQLite WAL с короткими транзакциями без внешних вызовов. Схема store версионируется, а несовместимая версия отвергается без записи.

  • Authority. ledger.json версии 4 и AUTHORITY.json называют store единственным writer-ом.
  • Audit. Каждая мутация оставляет запись в хэш-цепочке; checkpoint ускоряет обычную проверку, validate --full пересчитывает всё.
  • Leases. QA-lane — singleton с fencing token; lease мёртвого владельца снимается только по вердикту owner-dead.
# полная проверка цепочки и строк store
python3 .harness/orchestration/coordinator.py --repo . ledger validate --full

# authority и snapshot
cat .harness/orchestration/state/AUTHORITY.json

IPC и идемпотентность

Кадр — длина и JSON. Рукопожатие согласует версию протокола, а конверт несёт operation_id, deadline, expected_revision и digest-ы.

ПолеНазначение
operation_idДетерминированный ключ намерения; повтор возвращает сохранённый результат.
expected_revisionCAS по строке; конфликт — типизированная ошибка, а не тихая перезапись.
deadlineОграничивает ожидание; клиент повторяет с тем же id.
fencing_tokenЗащищает singleton QA-lane от двух владельцев.

Исполнение идёт в три шага: intent → запуск → committed. Перед повтором runtime делает reconcile и не запускает второй процесс, если объект уже существует.

Supervisor

Идентичность процесса — boot, namespace, pid и время старта. Этого достаточно, чтобы не принять чужой процесс с тем же pid за живой worker.

  • Linux: группы процессов и systemd scope, stop по deadline с grace-периодом.
  • Windows: Job Objects с именем по операции; исполнение переживает рестарт runtime.
  • Контейнеры: OCI-образ, метки dispatch, запрет монтирования сокетов движка и runtime.
  • Recovery: после SIGKILL runtime усыновляет исполнение по меткам или пишет lost; освобождение lease — только после доказанного выхода группы.
✓

Проверяемо. dispatch status показывает исполнение и объект qa_lane; ledger lock-status — вердикт и release_available.

Безопасность

Граница доверия проходит между Python policy, Rust runtime и untrusted worker. Runtime — trusted host supervisor; worker — кандидат в контейнере или отдельном процессе.

ГраницаПравило
Runtime socketТолько peer uid/SID и capability-токен; каталог 0700, сокет 0600.
Engine socketНикогда не монтируется в worker или QA-контейнер.
ApprovalImmutable brief связывает план, образ, policy digest и verification digest.
HooksКритические guards не отключаются профилем; strict не блокирует recovery.
SecretsНе попадают в командную строку, логи, audit или отчёты.
