# Оставшиеся идеи после Harness Next 2.0.0: промпты для проверки и прожарки

Сверено с кодом веток `integration/harness-runtime-reliability` и `integration/web-console` и с
трекером 10 ноября 2026 года. Предыдущая сверка (13 октября 2026 года) — в истории git этого файла.

Каждый блок можно скопировать в отдельный чат этого репозитория. Сначала агент проверяет текущий
код и трекер: реализация могла измениться после этой сверки. Промпты предназначены для обсуждения;
они не разрешают реализацию, публикацию новых задач, платные эксперименты или изменение настроек
рантайма. Подтверждённые решения существующих спецификаций и ADR сохраняются; обсуждаются только
новые пробелы и вопросы, которые ещё не решены.

## Что изменилось с 13 октября

- Harness Next 2.0 построен: Rust runtime — единственный writer operational state (SQLite WAL
  store, ADR 0020), супервизор процессов и OCI-контейнеров (ADR 0022), IPC с идемпотентными
  операциями (ADR 0021), инкрементальная проверка и `stage-evidence.v1` (ADR 0023), профили hooks
  (ADR 0024), Release Gate (ADR 0026); Веб-консоль на FastAPI и React (ADR 0028, ADR 0029).
- Выпуск 2.0.0 ведёт эпик #1058; пока он не завершён, новые функции не начинаются.
- Из очереди 13 октября закрыты: #679, #552, #675, #634, #549, #553, #554, #555, #556, #557, #577.
- Закрыты как перекрытые Harness Next: #452 (остаток — баг #1064) и #516 (Веб-консоль #862).
- Переписаны под архитектуру 2.0: #455, #518, #519, #520, #578. Освежены факты в #838–#847,
  сверка #834 — комментарием.
- Векторный слой памяти: NO-GO по измеренному качеству (#431, эпик #420, 2 октября 2026 года).

## 1. Матрица доказательств требований поверх stage evidence

Спека переписана под 2.0:
https://github.com/PVMalove/agent-harness-next/issues/519

```text
Прожарь со мной #519 в agent-harness-next. Прочитай новую редакцию issue, ADR 0023 и 0026,
stage_evidence.py и его Rust-близнец, release_gate.py и разделы Acceptance criteria в to-spec
и to-tickets. Проверь, что матрица не вводит второй тип receipt, а расширяет stage-evidence.v1
результатами assertions, и что записи идут в runtime store через IPC.
Обсуди только нерешённое: формат устойчивых ID критериев в тикетах, место проверки матрицы
в Release Gate, поведение пары без матрицы, ручная проверка с attestation. Зелёный полный
прогон без нужного assertion не подтверждает критерий.
Результат: решения для ADR и минимальный первый срез с отрицательными проверками
malformed/stale/missing/conflicting evidence.
```

## 2. Учёт расхода и бюджеты в runtime store

Спеки переписаны под 2.0:
https://github.com/PVMalove/agent-harness-next/issues/455
https://github.com/PVMalove/agent-harness-next/issues/518

```text
Прожарь со мной #455 и #518 в agent-harness-next. Прочитай новые редакции, ADR 0020–0022,
record_telemetry в workflow/reports.py, launch.rs и stop.rs супервизора, схему store.
Сверь, что учёт и резервирования живут в runtime store, а не в отдельном хранилище, и что
duration enforcement — это дедлайн исполнения супервизора.
Обсуди только нерешённое: имя и контракт IPC-операции приёма наблюдений, импорт массива
batch.telemetry, место reserve относительно execution.launch, причина остановки budget в
словарях systemFields.v1. Неизвестная база счётчика не равна нулю; неизвестный исход
удерживает резерв.
Результат: решения для ADR, порядок срезов (duration-only раньше token/cost) и сценарии
SIGKILL runtime между reserve и launch.
```

## 3. Полнота защиты Git-команд при профилях hooks

Hooks и профили `minimal`/`standard`/`strict` (ADR 0024) есть; пробел #1023 найден на практике.

```text
Проверь полноту Git guards в agent-harness-next: git-workflow, block-dangerous-git,
block-direct-master, protect-hook-policy, профили hooks ADR 0024 и их тесты. Построй матрицу
для force-push, force-with-lease, удаления локальных и удалённых refs и опасных команд с
разными порядками флагов и оболочками, отдельно для каждого профиля.
Различай защищённую базу, integration branch, свою issue-ветку после доказанного merge (#1023)
и прямой запрос пользователя. Сначала покажи подтверждённый пробел и воспроизводимый
безопасный тест, затем минимальное исправление и ложные блокировки законного workflow.
Для #1023 сначала цепочка RCA по эпику #1022, а не правка симптома.
Сохрани project-only metadata. Результат: покрытые случаи, реальные пробелы, критерии проверки.
```

## 4. Управление live context через возможности рантайма

Context Package, бюджет контекста роли и checkpoint/resume есть; вклад скиллов в стартовый
контекст разбирает #838.

```text
Прожарь со мной Context Pruning для agent-harness-next. Найди сценарий, где Context Package,
context_advisory, checkpoint/resume и профили скиллов (#838) не удерживают нужный контекст.
Установи по первичным источникам, можно ли штатными средствами Claude Code и Codex управлять
live context.
Как сохранить требования, решения, незавершённые действия и evidence при сокращении контекста?
Сравни управление live context, более узкий Package и новую session с проверяемым handoff
(чекпоинты dispatch в runtime store). Сохрани immutable brief и native runtime; не добавляй
собственный agent loop.
Результат: измеримый сценарий, доступный seam и минимальная проверка качества либо причина
отложить идею.
```

## 5. Mailbox и выбор следующей независимой задачи

В 2.0 batch работают параллельно с lease и fencing (#804); доска задач консоли меняет статус
тикета (#915). Гипотеза — парковка задачи и переход к другой в пределах разрешённой очереди.

```text
Прожарь со мной Mailbox для agent-harness-next. Проверь blockers, needs_attention, recovery,
зависимости тикетов, lease параллельных batch и harness ticket-status. Покажи сценарий, в
котором не хватает именно перехода к другой задаче, а не записей ожидания или их просмотра.
Кто утверждает очередь и объём полномочий? Как доказать независимость задач, сохранить dirty
worktree и pending decision, не занять задачу дважды (lease) и безопасно возобновить её после
ответа или restart runtime? Обсуди stale ответы, смену требований, fairness. Сравни ручной
выбор через доску задач с минимальной opt-in автоматикой.
Результат: границы scheduler, контракт pending decision и сценарии recovery. Не расширяй
полномочия агента самим фактом появления mailbox.
```

## 6. Автоматическое форматирование по настройкам проекта

QA-команды, hooks с ChangeImpact (#802) и stage evidence существуют.

```text
Прожарь со мной автоматическое форматирование в agent-harness-next. Проверь format/lint/QA
команды, ChangeImpact-hooks и точки их вызова. Найди повторяемую проблему, которую не решает
проектная команда форматирования.
Где нужен запуск: до теста, review или commit? Как ограничиться разрешёнными путями batch,
сохранить чужие dirty changes и не переписать файлы вне scope? Раздели formatter и исправления
линтера, меняющие поведение. Обсуди актуальность stage evidence после изменения файлов.
Результат: минимальная opt-in интеграция с проектной командой и проверка пользы; без
встроенного набора formatter для всех языков.
```

## 7. Подключение MCP для конкретного сценария

```text
Прожарь со мной opt-in MCP-интеграцию в agent-harness-next. Выбери один реальный сценарий и
проверь, что уже дают runtime-native tools, tracker CLI, integrations.json и Сервер консоли.
Сравни MCP с этими маршрутами по нужным операциям, точности и сопровождению.
Кто владеет конфигурацией сервера, версиями, credentials и разрешёнными tools? Как отличать
чтение от изменения внешней системы, подтвердить доступ и сохранить переносимость? Как MCP
сочетается с профилями hooks? Обсуди недоверенные ответы, таймауты, отказ сервера и очистку.
Не предполагай право подключать серверы или менять глобальные настройки.
Результат: use case, минимальный контракт подключения, проверки и решение, нужен ли отдельный
проектный пакет.
```

## 8. Критический разбор до реализации

Architect, независимые Standards/Spec review, test-author и QA существуют. Исследование
накопления ошибки в ролевой цепочке — #844.

```text
Прожарь со мной пользу critic pass до реализации в agent-harness-next. Прочитай границы
architect, developer, review и QA и выводы #844, если исследование уже выполнено. Найди класс
ошибок, которые поздний review обнаруживает слишком дорого и которые ранняя критика могла бы
выявить (пример: план architect с путями вне scope батча, #1017).
Сравни один ограниченный critic pass с многораундовыми дебатами. Определи trigger по риску,
предел раундов и затрат, формат findings и владельца решения при несогласии. Консенсус не
считай доказательством истины; сохрани approvals и независимую QA.
Результат: критерии добавочной пользы на выбранных сценариях, минимальный протокол либо отказ
от нового этапа. Субагентов и платные эксперименты не запускай.
```
