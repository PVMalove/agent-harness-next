# Артефакты и черновики { #artifacts-scratchpads-management }

## Локальное хранилище runtime { #local-runtime-storage }

Сгенерированные данные runtime лежат в `.harness/.sandboxes/` основного checkout и общие для всех его связанных worktree. Каталоги:

- `runs/`: одноразовые окружения (например, `runs/tests/` для прогонов проверок, `runs/qa/` для QA-checkout, `runs/drift/` для проверок upstream);
- `cache/`: пересобираемые кеши (например, `cache/repo_map/`);
- `logs/`: логи тестов и запусков;
- `reports/`: сгенерированные отчёты;
- `worktrees/`: управляемые checkout задач;
- `scratch/`: входящие роли (`scratch/inbox/`);
- `pr_body/`: одноразовые файлы публикации.

`.harness/orchestration/state/` хранит долговечный ledger, и очистка его не затрагивает.

`harness cleanup <repo> --mode soft` показывает, что будет удалено: просроченные временные запуски (`runs/` старше 24 часов), черновики (`scratch/`, `pr_body/`), просроченные логи (`logs/` старше 24 часов) и устаревшие каталоги верхнего уровня вне `.sandboxes/` (`.cache`, `test-logs`, `tmp`, `reports`, `scratch`). Флаг `--apply` выполняет удаление. `--mode hard` дополнительно показывает очистку пересобираемых кешей (`cache/`), отчётов (`reports/`) и старых чистых управляемых worktree (`worktrees/`); выполняет её команда `--apply --confirm HARD`. В обоих режимах временные данные и worktree должны быть старше 24 часов, порог меняет `--min-age-hours`. Очистка сохраняет активные запуски, worktree незавершённых batch, грязные деревья и ветки с коммитами, которых нет в `origin`. Hard-очистка удаляет worktree batch в состоянии `completed`, `failed`, `abandoned` или `not-required` и его локальную ветку, если дерево чистое, запушено в `origin` и старше порога. План и результат `--apply` называют `batch_id` и `state` каждого worktree. Удалённые ветки очистка не удаляет никогда.

Это руководство описывает только артефакты задач и черновики. Контракты оркестрации лежат в `.harness/orchestration/playbook.md`, CLI описывает `harness --help`.

* **Где хранить.** Спецификации, черновики и промежуточные файлы сохраняйте внутри репозитория проекта, а не в системных временных каталогах (`AppData/Local/Temp`, `/tmp`): запись туда отклоняет `block-scratch-outside-docs-tasks.sh`.
* **Каталог проекта.** Промежуточные документы задач кладите в `docs/tasks/` (создайте его, если его нет).
* **Черновик сессии проекта.** Если нативный hook передаёт `session_id`, используйте `.harness/.sandboxes/scratch/sessions/<session_id>/scratchpad/` внутри проекта. Hook проверяет канонический путь проекта и точную привязку к сессии: чужую сессию и symlink за пределы проекта он отклоняет. Внешний черновик runtime без доверенной привязки не поддерживается, поэтому используйте путь проекта или `docs/tasks/`. Это правило не разрешает произвольные системные временные пути и не ослабляет требования к именам файлов публикации.
* **Тела PR.** Тело или комментарий PR/MR, в том числе отчёт о завершении для `task-report::required`, опубликованный комментарием к задаче, относятся к одноразовым метаданным публикации, а не к артефактам задачи. Сохраняйте такой файл только в `.harness/.sandboxes/pr_body/` и никогда в `docs/tasks/`. Удаляйте файл после успешной команды `gh`/`glab`; если команда не удалась, оставьте его для повторной попытки.
  * **Hook проверяет имя файла, а не только каталог.** `block-scratch-outside-docs-tasks.sh` разрешает файл в `.harness/.sandboxes/pr_body/`, только если его *basename* содержит `pr-body`, `pr-comment` или `issue-comment` (без учёта регистра), например `.harness/.sandboxes/pr_body/pr-body-<issue>-<slug>.md` или `.harness/.sandboxes/pr_body/issue-comment-<issue>-<slug>.md`. Файл с другим именем в том же правильном каталоге (`report-<issue>-completion.md`, `notes.md`) hook отклоняет так же, как путь во временном каталоге системы. Исправляйте имя файла, а не каталог.
* **Только до публикации.** `docs/tasks/` хранит черновики *до* публикации спецификации или задачи в трекере. Не считайте его источником истины. После публикации долговечная запись живёт в трекере: в самой задаче для GitHub/GitLab либо в `.scratch/<feature-slug>/spec.md` и `.scratch/<feature-slug>/issues/` для локального markdown-трекера (см. `docs/agents/issue-tracker.md`), который `docs/tasks/` не использует вовсе.
* **Именование.** Каждая спецификация или черновик ОБЯЗАН содержать ID задачи в трекере (если он есть) и описательное имя. Так называются и файл, и его каталог (см. ниже). Если ID ещё неизвестен, используйте описательный slug и переименуйте оба после выдачи ID.
  * *Пример:* `issue-45-search-pagination`.
* **Один каталог на спецификацию.** Каждая спецификация или задача, отдельная или часть эпика, получает собственный каталог прямо в `docs/tasks/`, а не одиночный файл. Файл спецификации или задачи лежит в корне этого каталога рядом с двумя зарезервированными подкаталогами:
  * `tickets/`: по файлу на каждую дочернюю задачу, только для эпика с дочерними задачами (см. ниже);
  * `artifacts/`: Live Artifact из `/grilling`, то есть список путей Discovery Context, одобренных в этой сессии. `/to-spec` копирует тот же список в раздел `## Relevant Files (Discovery Context)` самой спецификации.
  * *Пример (отдельная задача):* `docs/tasks/issue-45-search-pagination/issue-45-search-pagination.md` и `docs/tasks/issue-45-search-pagination/artifacts/discovery-context.md`, если сначала отработал `/grilling`.
  * *Группировка по эпику.* Задача принадлежит родительскому эпику, если в ней есть ссылка `## Parent`/`Blocked by` на другую задачу или связь через родительскую ссылку трекера: sub-issue на GitHub или связь `relates_to` на GitLab (см. `docs/agents/triage-labels.md`). Тогда каталог называется по эпику: `issue-<epic-id>-<epic-slug>/`. В его корне лежит файл спецификации эпика, а тела всех подзадач лежат в `tickets/` (по файлу на задачу, не плоско рядом со спецификацией). Имена файлов внутри следуют обычному правилу именования; группирует их только каталог.
    *Пример:* эпик #26 («search-revamp») с подзадачами #27 и #28:
    ```
    docs/tasks/issue-26-search-revamp/
      issue-26-spec-search-revamp.md
      tickets/
        issue-27-pagination.md
        issue-28-filters.md
      artifacts/
        discovery-context.md
    ```
* **Порядок работы.** В `/to-spec` или при создании черновика явно записывайте файл в его собственный каталог в `docs/tasks/` (внутри каталога эпика, если он есть). Эти файлы нельзя коммитить: `docs/tasks/` намеренно находится в gitignore. Но и удалять черновик не нужно. Одноразовое тело PR или комментария в `.harness/.sandboxes/pr_body/` удаляют сразу после успешной публикации, а содержимое `docs/tasks/` остаётся постоянным локальным архивом: после публикации спецификации или задачи его не удаляет ни один скилл или инструмент. Если нужен постоянный *закоммиченный* след в самом репозитории, место ему в `docs/adr/` через `domain-modeling`, а не здесь.
