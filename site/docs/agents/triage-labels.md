# Метки триажа { #triage-labels }

Поток доставки описан в [git-workflow.md](git-workflow.md). Это руководство задаёт авторитетный словарь меток триажа.

Этот репозиторий **не** использует канонический словарь из пяти ролей upstream `mattpocock/skills` (`needs-triage` / `needs-info` / `ready-for-agent` / `ready-for-human` / `wontfix`) в виде буквальных меток. `triage/SKILL.md` (`.harness/skills/triage/`) сразу использует таксономию ниже с пространствами имён. Этот файл служит справочником, а не таблицей перевода. Каждая ось, включая `type::*`, использует собственные значения репозитория в корпоративном стиле, а не значения upstream.

## Таксономия { #the-taxonomy }

Каждая задача или PR после триажа несёт ровно одну метку с каждой из первых трёх осей ниже, кроме периода, пока на ней стоит `status::specs`: на этой стадии режим выполнения ещё не решён (см. [Конечный автомат](#state-machine)).

### 1. Тип (`type::*`) { #1-type-type }

| Метка | Значение |
| --- | --- |
| `type::bug` | Что-то сломано |
| `type::feature` | Новая функция или улучшение |
| `type::refactoring` | Внутренняя перестройка без изменения поведения |
| `type::chore` | Сопровождение, инструменты или обновление зависимостей |
| `type::security` | Исправление или усиление безопасности |
| `type::performance` | Улучшение производительности |
| `type::hotfix` | Срочное исправление в production |

### 2. Режим выполнения: кто делает работу { #2-execution-mode-who-does-the-work }

| Метка | Цвет | Значение |
| --- | --- | --- |
| `hitl` | жёлтый `#fbca04` | Human-in-the-loop: нужны ревью, тестирование или одобрение от вас |
| `afk` | голубой `#54c1e8` | Away-from-keyboard: агент может завершить задачу сам |

Документационные тикеты, то есть те, что меняют только `docs/`, `site/`, `README.md` и
`CHANGELOG.md`, получают `hitl`, а не `afk`: результат читает человек, и он же решает, готов ли текст к публикации.
`/implement` и `/fast-implement` не берут такие тикеты в afk-пайплайн.

### 3. Статус (`status::*`): на каком этапе pipeline задача { #3-status-status-where-it-sits-in-the-pipeline }

| Метка | Цвет | Значение |
| --- | --- | --- |
| `status::specs` | фиолетовый `#5319e7` | Проектирование и написание спецификации: эпик или крупная задача превращается в спецификацию и раскладывается на задачи. Для взятия в разработку пока рано. |
| `status::ready` | зелёный `#0e8a16` | Задача полностью описана и готова к взятию в работу |
| `status::in-progress` | синий `#1d76db` | Над задачей сейчас работает активная сессия |
| `status::blocked` | красный `#b60205` | Задачу блокирует зависимость, либо она ждёт от вас дополнительных сведений |

### Контекстные метки: ставятся по необходимости { #context-labels-applied-when-relevant }

| Метка | Цвет | Кто ставит | Значение |
| --- | --- | --- | --- |
| `task-report::required` | серый `#6a737d` | `/to-spec`, `/to-tickets`; обрабатывает `/to-pull-requests` | Агент обязан опубликовать отчёт о завершении до закрытия. Ставится по умолчанию на каждую задачу, если вы не попросили пропустить. В конечный автомат самого `triage` не входит, см. SKILL.md скилла `/to-pull-requests`. |
| `resolution::wontfix` | серый `#c2c2c2` | `/triage` | Запрос явно отклонён. Ставится при закрытии; обработка `.out-of-scope/` описана в `triage/OUT-OF-SCOPE.md`. |

### 4. Приоритет (`priority::*`): необязательно, только информация { #4-priority-priority-optional-purely-informational }

Автоматически эту ось пока ничто не использует; она нужна, чтобы мейнтейнер мог отметить срочность.

| Метка | Значение |
| --- | --- |
| `priority::p0` | Критично, бросить всё |
| `priority::p1` | Высокий |
| `priority::p2` | Средний |
| `priority::p3` | Низкий |

### 5. Серьёзность (`severity::*`): необязательно, только информация { #5-severity-severity-optional-purely-informational }

Автоматически эту ось пока ничто не использует; она нужна, чтобы мейнтейнер мог отметить влияние.

| Метка | Значение |
| --- | --- |
| `severity::s1` | Критическое влияние |
| `severity::s2` | Серьёзное влияние |
| `severity::s3` | Незначительное влияние |
| `severity::s4` | Пренебрежимое влияние |

### 6. Окружение (`env::*`): только для целевых проектов, необязательно { #6-environment-env-target-project-only-optional }

К какому развёрнутому окружению относится задача или PR. В таксономию самого репозитория harness не входит: метки заводятся только в целевых проектах, которые отслеживают развёртывания.

| Метка | Значение |
| --- | --- |
| `env::prod` | Production |
| `env::staging` | Staging |
| `env::qa` | QA |
| `env::dev` | Разработка |

Группировка по эпику метки не использует: задача, выделенная из эпика, связывается с ним через родительскую ссылку трекера: **sub-issue** на GitHub, а на GitLab раздел `## Parent: #<epic>` в описании задачи плюс связь `relates_to`. Тот же механизм `/wayfinder` применяет для связи карты и задач; см. [issue-tracker.md](issue-tracker.md#wayfinding-operations). `wayfinder:map` и `wayfinder:<type>` (`research`/`prototype`/`grilling`/`task`) остаются отдельным пространством имён `/wayfinder` (цвета ниже). При этом задача Wayfinder (не сама карта) тоже несёт соответствующую метку `hitl`/`afk` плюс `status::ready`, а при взятии в работу переводится в `status::in-progress`: это те же две оси, что и везде в этой таксономии, но ставит их сам `/wayfinder`, а не `/triage`. `status::specs` и `wayfinder:map` означают разное: первое задаёт состояние триажа на задаче-эпике, второе помечает собственный артефакт-карту Wayfinder, и карта никогда не несёт метку `status::*`.

| Метка | Цвет | Значение |
| --- | --- | --- |
| `wayfinder:map` | тёмно-синий `#0052cc` | Сама задача-карта: Destination, Notes, Decisions-so-far, туман. |
| `wayfinder:research` | зелёный `#00875a` | Тип AFK-задачи: чтение документации, API и локальных ресурсов, чтобы выяснить факт. |
| `wayfinder:prototype` | оранжевый `#ff8b00` | Тип HITL-задачи: дешёвый конкретный артефакт, на который можно отреагировать. |
| `wayfinder:grilling` | фиолетовый `#6554c0` | Тип HITL-задачи: разговор, случай по умолчанию. |
| `wayfinder:task` | сланцевый `#8993a4` | Тип HITL- или AFK-задачи: ручная работа, снимающая блокировку решения. |

### Подсказка pipeline (`pipeline::*`): по story points, только для `afk` { #pipeline-hint-pipeline-from-story-points-afk-only }

Отдельное пространство имён, независимое от `hitl`/`afk` и `status::*`. `/to-tickets` присваивает каждой `afk`-задаче оценку story points по Фибоначчи (Planning Poker: один основной проход и второй дешёвый совещательный, если оценка попала в серую зону) и выводит из неё одну из этих меток на гейте STOP-AND-ASK, где разработчик может переопределить метку, не меняя оценку. Задачи `hitl` метку `pipeline::*` не получают. Шкала и пороги берутся из необязательного поля `story_points` в `.harness/project.json` (схема: `.harness/project.schema.json`); без него `/to-tickets` использует значения по умолчанию: fast при `≤3`, full при `≥5`, серая зона `4`.

| Метка | Цвет | Значение |
| --- | --- | --- |
| `pipeline::fast` | бледно-голубой `#c5def5` | Оценка `≤ fast_threshold` и `Execution: afk`: короткий путь `/fast-implement` без гейтов. |
| `pipeline::full` | оранжево-красный `#d93f0b` | Оценка `≥ full_threshold`: pipeline `/implement` с гейтами. |

## Конечный автомат { #state-machine }

Задача без меток неявно находится в состоянии «нужен триаж»: отдельной метки для него нет.

1. Триаж анализирует задачу и определяет `type::*`. Затем он ставит `hitl`/`afk`. Если задача размером с эпик и её нужно декомпозировать, прежде чем с ней можно что-то делать, триаж вместо этого отправляет её в `status::specs` и направляет мейнтейнера к `/to-spec`.
2. `/to-spec` ставит `status::specs`, когда публикует новую задачу-эпик напрямую (пропуская маршрутизацию шага 1, если мейнтейнер начинает с `/to-spec`, а не с входящей задачи).
3. После описания задачи переведите её в `status::ready` (ничто не блокирует) или `status::blocked` (зависимость либо недостающие от вас сведения; в обоих случаях оставьте заметки триажа).
4. `status::blocked` → `status::ready`, когда блокер снят или вы ответили. Блокер снят, только если закрыта задача-предшественник, а она закрывается только после подтверждённого merge; push, публикация, принятый QA или открытый PR блокер не снимают.
5. `status::ready` → `status::in-progress`, когда задачу берёт сессия (агент или вы): `/implement` и `/fast-implement` делают это в pre-flight, до ветки задачи и до любой правки файлов. Метка заменяется, а не добавляется: задача несёт ровно одну метку `status::*`. На GitLab Free метка `key::value` остаётся обычной меткой (взаимоисключающие scoped-метки есть только в Premium), поэтому каждая замена явно снимает прежнюю метку с тем же префиксом `key::` (`--unlabel`), как `--remove-label` на GitHub.
6. Слита и закрыта → задача сохраняет `status::in-progress`; закрытое состояние служит её конечным `done`. На том же шаге `/to-pull-requests` переводит из `status::blocked` в `status::ready` каждую открытую задачу, у которой теперь закрыты все блокеры.
7. Отклонена на любом этапе → поставьте `resolution::wontfix`, снимите метку `status::*`, закройте.
8. Доска задач веб-консоли перемещает задачу командой `harness ticket-status <repo> --spec <spec> --ticket <ref> --to <column>`. Команда сама проверяет перемещение и заменяет метку, как на шаге 5. Разрешены: Backlog → Ready, только когда закрыты все блокеры (шаг 4); Ready → Backlog и Ready → In progress; In progress → Ready, только без активного batch. Перемещение в Backlog записывает `status::blocked`: это единственная метка Backlog, при которой у задачи остаётся ровно одна метка `status::*`. Любое другое перемещение и любое перемещение в Review / QA или Done команда отклоняет без записи: эти колонки следуют за batch, PR и закрытым состоянием.

Ставьте `task-report::required` по умолчанию, когда `/to-spec` или `/to-tickets` создают задачу, если не сказано пропустить.

## Локальный markdown-трекер { #local-markdown-tracker }

У задачи в локальном markdown-трекере (`.scratch/<feature>/issues/NN-*.md`) нет меток GitHub/GitLab: оси выше записываются в явные поля этого файла:

```markdown
**Category:** type::bug / type::feature / type::refactoring / type::chore / type::security / type::performance / type::hotfix
**Workflow:** status::specs / status::ready / status::in-progress / status::blocked / done
**Execution:** hitl / afk (omit while **Workflow:** is status::specs)
**Story Points:** Fibonacci score (afk tickets only; omit the line entirely for hitl tickets)
**Pipeline:** pipeline::fast / pipeline::full (afk tickets only, derived from Story Points; omit the line entirely for hitl tickets)
**Task report:** required (omit the line entirely if not required)
```

Этот блок полей задаёт словарь, на который ссылается строка `Workflow:` в [issue-tracker.md](issue-tracker.md). Собственная строка Wayfinder `Status: claimed/resolved` (тот же исходный документ) служит независимым маркером захвата файла; она сосуществует с этими полями, а не заменяет их.

Значения `status::*` совпадают со строками меток GitHub/GitLab, плюс конечное `done`, которое `/to-pull-requests` выставляет после подтверждения разработчиком merge ветки задачи. `/implement` и `/fast-implement` заканчивают работу на отправленной ветке задачи, затем предлагают `/to-pull-requests`. Удалённые задачи закрываются только после фактического merge изменения: GitHub автоматически закрывает `Closes #<ID>` для PR в default-ветку, а шаблон GitLab можно отключить или настроить, поэтому проверяйте любой результат. PR в integration-ветку закрывается явно после подтверждённого merge (см. `docs/agents/git-workflow.md`). Для локального трекера механизма sub-issue нет; декомпозированная задача лежит в каталоге `.scratch/<feature-slug>/issues/` функции (см. [issue-tracker.md](issue-tracker.md)): сам этот каталог и есть группировка, отдельный каталог эпика или поле для неё не нужны.

## Адаптация таксономии под проект { #adapting-this-taxonomy-per-project }

`engineering-suite` поставляет эту таксономию по умолчанию. Это проектное решение (многоосевые метки с пространствами имён), а не жёсткое требование. Переименование оси или добавление собственных контекстных меток проекта означает правку этого файла **и** `triage/SKILL.md`: скилл использует описанный здесь словарь как жёстко заданный текст, а не как данные, которые читаются из этого файла во время работы. После правки выполните `harness lock-project-skills`, чтобы настройка осталась зафиксированной как намеренное происхождение, а не как дрейф, который будущий `harness update --force` может молча перезаписать.
