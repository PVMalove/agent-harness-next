# Hooks и профили

Часть правил процесса можно записать словами, но слова не исполняются. Hooks превращают такие
правила в проверки, которые срабатывают до действия: агент не может «забыть» правило, потому что
инструмент возвращает отказ раньше, чем команда выполнится.

## Зачем

**Запрет опасных операций.** Прямой коммит или push в защищённую ветку, слияние pull request,
разрушительная операция с историей — всё это приводит к состоянию, которое нельзя откатить одной
командой. Hook проверяет команду до запуска и отказывает.

**Защита процесса.** Публикация PR без пройденного QA обесценивает проверку: PR выглядит готовым, а
на деле не проверялся. Hook не даёт открыть PR, пока прогон качества для текущего дерева не пройден.

**Защита метаданных.** Следы автоматизированного исполнителя в истории коммитов и в описании
изменения остаются навсегда и меняют авторство работы. Hook блокирует их до публикации.

## Три профиля

Профиль задаёт поведенческую строгость: сколько предупреждений, повторных проверок и отказов
получает работа.

- `minimal` — только критические guard-ы. Подходит для быстрых правок в личном проекте.
- `standard` — базовый режим по умолчанию: критические guard-ы, ограниченный прогон проверок и
  напоминания.
- `strict` — добавляет повторную проверку чувствительных путей и отказ на границах высокого риска.

Ни один профиль не ослабляет критические guard-ы, включая `minimal`. Строгость меняет количество
подсказок и повторных проверок, а не наличие запрета на опасное действие.

## Второй runtime

Hooks поставляются для обоих поддерживаемых runtime из одного набора скриптов, и критические guard-ы
у них равные. Второй runtime присылает правки файлов патчем, поэтому guard-ы подключаются группой,
покрывающей и патч, и обычную запись: решение не зависит от того, каким инструментом правили файл.

Если hooks этого runtime недоступны, критическую защиту дают проверки процесса runtime и
coordinator, а `harness health` сообщает об этом предупреждением — то есть отсутствие hooks видно, а
не маскируется.

## Политика как контракт

- Профиль читается только из `.harness/project.json`. Переменные окружения и параметры инструментов
  его не меняют.
- Агент не может изменить ни настройки hooks, ни ключ политики: эти правки блокируются во всех
  профилях. Политику меняет человек.
- Профиль можно повысить для отдельных путей и ролей эскалацией; понизить нельзя.
- Ответ hook — структурированный: идентификатор, профиль, решение `allow`/`warn`/`block`, код
  причины, готовая рекомендация и ссылка на доказательство. Критический hook при внутренней ошибке
  блокирует, поведенческий — разрешает и пишет диагностику.

При approval закрепляется digest политики. Поэтому смена профиля не проходит незамеченной: план
согласован при одной политике, а исполнение идёт при другой, и это видно до публикации.
