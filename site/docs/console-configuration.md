# Настройка проекта в консоли

Консоль позволяет подключить Git-репозиторий, изменить `project.json` и `orchestration.json`,
проверить результат и сохранить версию конфигурации. Перед записью она показывает изменения
и спрашивает подтверждение. Поля описаны в [Настройках](getting-started/settings/index.md).

Эта инструкция относится к терминальному интерфейсу. Номера клавиш и названия его действий
не описывают расположение элементов веб-консоли.

## Подключение проекта

1. На главном экране выберите «Открыть проект» (`1`) и укажите путь к локальному Git-репозиторию.
   Для нового каталога сначала выполните `git init`.
2. Нажмите «Проверить путь». Консоль определит `init`, `adopt` или `update`, установленный состав
   и конфликты. Локальная диагностика запустится автоматически.
3. Проверьте план установки. Смена состава заменяет набор управляемых capabilities.
   До подтверждения разберите конфликты и локальные изменения; этот экран не включает force.
4. Подтвердите показанную команду установки. Затем откройте «Настройка».
5. После настройки проверьте повторную диагностику. «Открыть проект» делает выбранный репозиторий
   целью остальных разделов консоли.

Отмена сохраняет прежнюю цель. Пока команда выполняется, переключение проекта недоступно.

### Диагностика при подключении

«Офлайн» проверяет локальные файлы и окружение. «Онлайн» отдельно проверяет авторизацию,
доступ к репозиторию и права GitHub/GitLab; локальный трекер не требует сетевых проверок.
«Исправить» после подтверждения применяет локальные health-исправления и повторяет диагностику.

`skipped` означает, что проверка не выполнялась. Проверка настроек sandbox по файлам
не доказывает фактический доступ worker. Подробнее о проверке доступа читайте в
[главе оркестрации](guides/orchestration/access.md).

## Обновление Harness

Откройте «Обновить Harness» (`2`), проверьте версию, drift и diff каждого изменённого файла.
Выберите режим до подтверждения команды.

| Режим | Что меняет |
| --- | --- |
| Обычный `update` | Обновляет файлы по штатным правилам, сообщает о локальных конфликтах |
| `--force-managed-files` | Перезаписывает управляемый снимок, сохраняет seed-файлы |
| Выбранные seed-файлы | Передаёт `--force-seed-file PATH` для каждого отмеченного файла |

«Проверить снова» перечитывает изменения. Если план изменился после просмотра, проверьте его заново.

### Адаптеры runtime в настройках

Просмотр установки и обновления показывает отсутствующие и устаревшие адаптеры.
Подтверждённый обычный `harness update` восстанавливает их в пределах выбранного состава.
Он не меняет транспорт и не добавляет `backend-orchestration` автоматически.

## Шаги и черновик

1. Откройте «Настройка конфигурации» (`8`) и выберите один или оба файла.
   Мастер загрузит текущие значения; для отсутствующего файла использует шаблон.
2. Пройди нужные поля. На каждом шаге есть назначение, текущий ответ и рекомендация с причиной.
   Строки вводи без кавычек, числа, списки и объекты вводи как JSON.
3. Для `provider_profiles`, `assignment_plans` и списков выберите редактирование через меню или JSON.
   Оба способа меняют один черновик. Переходы «Назад» и «Далее» сохраняют ответы.
4. Нажмите «Проверить итог». Просмотрите JSON, diff и диагностику схем и валидаторов.
   Из списка ошибок можно перейти к нужному полю.
5. Нажмите «Применить» и подтвердите цель. До этого рабочие файлы не меняются.

Если файл изменился снаружи, запись останавливается. «Загрузить внешние изменения» объединяет
новую версию с черновиком и перечисляет конфликтующие поля; в них побеждает ваш ответ.
Снова проверьте diff перед применением. Если закрыть мастер с несохранённым черновиком, консоль попросит подтверждение.

`approval_policy=auto` требует `trusted` и `worker_attestation_required=true`.
Заданный `access_policy` сам по себе не предоставляет runtime доступ.

Буфер обмена использует доступную системную утилиту; без неё остаётся внутренний буфер приложения.
`HARNESS_CONSOLE_SYSTEM_CLIPBOARD=0` отключает системный буфер. Вставка средствами терминала
обычно доступна через Ctrl+Shift+V.

## Версии и восстановление

«Сохранить версию» в главном меню настройки сохраняет рабочую конфигурацию.
Та же кнопка на итоговом экране сохраняет черновик без применения.
Снимок содержит оба файла, включая отсутствие файла, описание, дату, версию Harness и хеши.
Он хранится локально в `.harness/config_versions/` и переживает cleanup. Ledger и worktrees в него не входят.

Перед восстановлением выберите версию, прочитайте diff и подтвердите действие.
Консоль проверяет хеши и совместимость. Перед применением или откатом она сохраняет текущие файлы
отдельной версией. Если в выбранном снимке файла нет, восстановление удалит его.
Повреждённую или несовместимую версию применить нельзя.

Файловая блокировка и журнал защищают согласованную запись двух конфигов.
После прерывания мастер восстанавливает транзакцию; если файлы затем правили вручную,
автоматическое восстановление останавливается, сохраняя внешние изменения.

Не вводи секреты в команды, конфигурацию или описание версии. Распознаваемое значение секрета
блокирует создание снимка; ссылка на переменную, например `TOKEN=$CI_TOKEN`, допустима.
Проверка не распознаёт все секреты. Храни авторизацию в штатном хранилище CLI.

## Подсказки через CLI

ИИ выключен по умолчанию. «Проверить CLI» определяет наличие, нужные флаги и авторизацию
`codex` и `claude` без запроса к модели. Для запроса выберите доступный CLI и нажмите «Подсказать с ИИ».
Мастер использует действующую авторизацию CLI и не просит ключи.

Запрос содержит описание текущего поля, до четырёх вариантов, признаки стека, ОС и рекомендацию.
Команды, путь проекта и значения конфигурации не передаются. CLI работает во временном каталоге,
сохраняя штатную среду авторизации. Codex использует read-only sandbox и отключённые пользовательские
настройки и инструменты; Claude Code использует `-p --safe-mode --tools "" --strict-mcp-config`.
Сессия не сохраняется и не продолжается. Запрос ограничен 90 секундами и размером ответа.
Переход к другому шагу отменяет ожидающий результат.

Ответ попадает в черновик только отдельным действием. Проверки и подтверждение записи остаются.
При неподдерживаемой версии CLI, ошибке сети, авторизации или ответа мастер сохраняет обычные подсказки.

## Что не проверяется автоматически

Автоматические проверки не доказывают работу внешнего трекера, реального запроса к модели
или фактических разрешений worker в твоём окружении. Их нужно проверять отдельно.
Описание поведения консоли сверяется с [её исходниками](https://github.com/PVMalove/agent-harness-next/tree/master/harness/console).
