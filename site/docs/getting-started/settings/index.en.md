# Project settings

Project settings are two core contracts in `.harness/` plus the surfaces around them.
`project.json` describes the project itself: language, branches, QA gate commands, tracker, test zone,
hook policy, and memory. `orchestration.json` describes how the coordinator and the runtime run roles,
approval, access, and verification; it appears with the `backend-orchestration` capability. Around them
live the integrations inventory, generated hook policy, native runtime configs, secrets, and
environment.

## The two core contracts

Both files live in `.harness/`.

| Contract | Creation, ownership, and checks |
| --- | --- |
| [project.json](project.md) | Created from a template during `harness init`, `adopt`, or `update` if absent; maintained by the project afterward. Read by qa-gate, pr-composer, code-review, to-guide, test-author, and hooks. Health: `files.project_json`. |
| [orchestration.json](orchestration/index.md) | Appears with the `backend-orchestration` capability: an absent file is copied from `.harness/orchestration.example.json`; maintained by the project afterward. Read by the coordinator, `harness-runtime`, and the console setup wizard. Health: `files.orchestration_config`. |

The installer does not overwrite existing values: `project.json` is created once, and
`orchestration.json` only when it is absent. `harness update` refreshes the managed
`.harness/orchestration.example.json`, but not the project config; overwriting the project file
requires an explicit `--force-seed-file`.

## What else settings include

Besides the two contracts, a project has surfaces configured separately:

- `.harness/integrations.json` — the inventory of native configs: paths, sha256, runtimes,
  `secret_refs`, and the `verify` action; checked by `files.integrations`.
- `.harness/hook-policy.json` — generated by the installer and never edited by hand; `hooks.policy`
  reports drift and `harness update` fixes it. The format and the check are described in the
  [hooks installation guide](../../hooks/install-and-update.md).
- Native configs `.claude/settings.json`, `.claude/settings.local.json`, `.codex/hooks.json`,
  `.mcp.json`, `.kimi/mcp.json`, `opencode.json`, and `opencode.jsonc` are read by their runtimes.
  Harness records them in the inventory; hook installation merges managed entries while preserving
  other settings. Forcing a complete file replacement is a separate explicit action.
- Secrets — `secret_refs` and `access_policy.*.environment` contain names only. Values belong to
  CLI authentication, the environment, or an integration's native config; containers receive them
  from the environment of `harness-runtime serve`. IPC and console tokens are generated separately.
- Dependencies — Python 3.12+, `uv`, and Git; backend orchestration needs `harness-runtime`
  (building requires Rust 1.89+), and containers need Docker or Podman. Environment checks use
  the `environment.*` prefix; harness does not install the project's own dependencies.

These surfaces are described on the [Integrations](integrations.md),
[Secrets and tokens](secrets.md), and [Dependencies and environment](environment.md) pages.

## Where the schemas live

- `.harness/project.schema.json` — the `project.json` schema; the file itself holds `"$schema": "./project.schema.json"`.
- `.harness/orchestration/orchestration.schema.json` — the `orchestration.json` schema; the file holds
  `"$schema": "./orchestration/orchestration.schema.json"`.
- `.harness/orchestration.example.json` — the managed example of a complete configuration; `harness diff`
  shows its drift.

Editors use the schemas for hints and checks. The schema and the `harness health` validator remain the
source of truth, not the example.

## How to edit safely

1. Edit the file with the Edit or Write tool, not with shell redirection or a heredoc. That keeps the
   change visible in the diff and does not bypass review.
2. Keep the JSON valid: UTF-8, no comments, no trailing commas, unique keys.
3. Change one logical group of fields at a time and verify the result before the next edit.
4. After an edit, run `python3 harness/bin/harness.py health <repo>` (or `harness health <repo>` when
   the CLI is installed). The check changes nothing; on `fail` it prints the cause and the fix command.
5. For `orchestration.json`, also run `config validate` (see below).
6. If a running runtime reads the configuration, restart `harness-runtime serve`: the process keeps
   the configuration in memory.

## Validating the configuration

```bash {.ah-code-wrap}
python3 .harness/orchestration/coordinator.py --repo . config validate --json
python3 .harness/orchestration/coordinator.py --repo . config validate --canonical --json
python3 .harness/orchestration/coordinator.py --repo . config validate --fix --dry-run --json
```

| Command | What it does |
| --- | --- |
| `config validate --json` | Prints diagnostics: file, JSON pointer, code, allowed values, and the safe received value. Writes nothing. An invalid config exits with code 2. |
| `config validate --canonical --json` | Also rejects spelling that requires normalization, with the code `config-noncanonical`. |
| `config validate --fix --dry-run --json` | Shows the diff of safe enum normalization and does not write the file. |
| `config validate --fix --json` | Writes the normalization in a transaction with a backup copy. |

On load, the coordinator normalizes enum fields in memory only and warns about every correction; the
file does not change. IDs, models, paths, and commands are not normalized. A duplicate key, a secret,
and an ambiguous value are errors, not a reason to keep the last value. See the
[backend orchestration guide](../../backend-orchestration.md) for details.
