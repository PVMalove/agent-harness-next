# Code review

Ревью идёт по двум независимым осям, и его отчёты не объединяются. Код может соответствовать одной
оси и не соответствовать другой: аккуратный по стилю, но реализующий не то. Обе оси проверяются
субагентами параллельно от фиксированной точки — коммита, ветки, тега или merge-base.

## Standards

Ось проверяет соответствие задокументированным стандартам репозитория и baseline из двенадцати
«запахов» кода Фаулера — например, загадочное имя, дублирование, примитивная одержимость, повтор
ветвлений. Запах — это суждение, а не жёсткое нарушение, поэтому он не приравнивается к ошибке.
То, что ловит линтер, ось не пересказывает: линтер уже сказал это сам. При конфликте стандарт
репозитория важнее baseline.

## Spec

Ось проверяет соответствие исходному тикету или спецификации: что упущено, что сделано лишним
(расширение объёма) и что реализовано неверно. Если спецификацию найти не удалось, ось явно
пропускается, а не додумывает требования.

## Как это устроено

Вход — дифф от фиксированной точки и описание задачи. Два субагента получают независимые
инструкции, работают параллельно и возвращают отчёты в основную сессию; основная сессия не правит
чужие замечания молча, а решает по каждому. Язык отчёта берётся из поля `language` конфигурации
проекта, а не из языка комментариев в коде.

Пример фрагмента отчёта:

```text
Standards — Warning
- services/reports/csv.py: Primitive Obsession (суждение) — разделитель передаётся строкой в трёх местах.
Spec — Clean
- Все пункты тикета покрыты; лишнего поведения нет.
```

## Что считается блокером

- Невыполненный критерий приёмки.
- Изменение вне объявленного объёма задачи.
- Новое поведение без теста.
- Ослабленная проверка: отключённый тест, `except: pass` вокруг проверяемого действия, суженный
  до тривиального случай.

Замечание по Standards — предмет решения: его можно принять как долг, если оно не влияет на
поведение. Замечание по Spec решением не является: расхождение с задачей либо устраняется, либо
задача явно переформулируется.
