# /fast-implement

`/fast-implement` — однопроходный путь без coordinator, architect, независимого QA и approval-гейтов.
Реализацию пишет текущая сессия. Маршрут нужен для мелкой задачи, чьё направление не обсуждается.

## Когда использовать

- Тикет размечен `afk` и `pipeline::fast` — это мелкий объём, обычно до трёх story points.
- Задача укладывается в одну проверяемую границу и не требует независимой проверки отдельной ролью.
- Тикет `hitl` по этому маршруту не идёт никогда: для него есть `/to-guide`, где реализацию
  выполняет человек.

Если команда получила эпик вместо тикета, она берёт первый подходящий тикет фронтира: открытый, не
заблокированный, никем не занятый и размеченный `pipeline::fast` вместе с `afk`. Названный явно
тикет без метки `pipeline::fast` отправляется в `/implement`.

## Pre-flight

1. **Разрешить тикет.** Явный `hitl`-тикет останавливает работу с указанием на `/to-guide`; явный
   `afk`-тикет без `pipeline::fast` — с указанием на `/implement`.
2. **Проверить блокеры.** Открытый блокер останавливает работу, а тикет должен быть помечен
   `status::blocked`.
3. **Пометить в работе — до ветки и правок.** Заменить текущую `status::*` на `status::in-progress`:

   ```bash
   gh issue edit 102 --remove-label status::ready --remove-label status::blocked \
     --add-label status::in-progress
   ```

   Затем проверить, что `status::in-progress` — единственная метка состояния. Неудачная запись —
   остановка, а не повод продолжать без метки.
4. **Ветка.** Создать issue-ветку от integration-ветки тикета; имя должно соответствовать
   `branch_pattern` проекта и не совпадать с защищёнными ветками.

## Шаги

1. **Тест первым.** Новое поведение начинается с падающего теста по `/tdd` на согласованном шве.
2. **Реализация.** Минимальный код до зелёного теста, затем рефакторинг без изменения поведения.
3. **Ревью по согласию.** Предложить `/code-review`; при отказе зафиксировать отказ явно.
4. **Коммит и push.** После отдельного согласия сделать semantic commit и запушить issue-ветку,
   сообщив хеш и результат push.
5. **Предложить публикацию.** Назвать `/to-pull-requests` и остановиться: PR открывает человек.

## Чем отличается от /implement

| Аспект | `/fast-implement` | `/implement` |
| --- | --- | --- |
| Кто пишет код | текущая сессия | dispatched-роли под управлением coordinator |
| Гейты | нет | architect → developer → code-review → qa → publish |
| Approval | согласие человека на review, commit и push | approval на каждом гейте по политике |
| Независимый QA | нет, полный прогон в конце сессии | да, clean-room на закреплённом кандидате |
| Артефакты | commit в issue-ветке | candidate commit, brief, отчёты, ledger |
| Требует capability | нет | `backend-orchestration` |
