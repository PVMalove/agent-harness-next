# Рабочий поток

Harness ведёт работу от идеи до merge по пяти шагам. Не каждая задача проходит все пять: точка
входа определяет, какие шаги пропускаются совсем, а какие выполняются один раз для целого эпика.

## Пять шагов

| Шаг | Что происходит | Кто ведёт |
| --- | --- | --- |
| Проектирование | Снимается неопределённость, фиксируются решения и границы | `/grilling`, `/grill-with-docs`, `/wayfinder` |
| Спецификация | Обсуждение становится единым источником правды и публикуется в трекер | `/to-spec` |
| Тикеты | Спецификация режется на вертикальные слайсы со связями блокировки | `/to-tickets` |
| Реализация | Тест первым, реализация, независимое ревью, QA | `/implement`, `/fast-implement`, `/to-guide` |
| Публикация | PR в integration-ветку, merge руками человека, закрытие тикета | `/to-pull-requests` |

Merge всегда выполняет человек. Ни один шаг не открывает и не мержит PR сам.

## Точки входа

| Ситуация | Что происходит | Что пропускается |
| --- | --- | --- |
| Один тикет извне: баг-репорт или небольшая фича, объём укладывается в одну сессию | `/triage` доводит issue до состояния `status::ready` и режима `hitl`/`afk`, дальше один шаг реализации | Проектирование, спецификация, декомпозиция |
| Задача масштаба эпика: состав работ известен, нужна декомпозиция | Прорабатывается за одну сессию, затем `/to-spec` → `/to-tickets` → реализация по каждому тикету | Wayfinder |
| Крупный объём с неопределённым путём к цели | `/wayfinder` ведёт карту решений, пока не останется открытых вопросов, затем передаёт работу `/to-spec` | Ничего, но работа идёт сессиями |

Начальный шаг подсказывает `/ask-matt`: он описывает основной путь, входы для входящих issue и
трудных багов, и ветки вне этой схемы.

## Проработка идеи

`/grilling` — ядро этапа: агент моделирует план как дерево решений и задаёт вопросы по фронтиру,
то есть только те, чьи предпосылки уже закрыты. Каждый раунд начинается с краткой сводки того, что
устоялось. Когда фронтир пуст, агент показывает сводку решений и спрашивает подтверждение, после
чего работа переходит к `/to-spec`.

`/grill-me` — тонкая обёртка для проектирования с нуля, когда репозитория ещё нет в игре. После неё
остаётся сводка решений.

`/grill-with-docs` — та же оболочка для работы в существующем репозитории. Она предпочтительна,
потому что параллельно ведёт глоссарий и архитектурные решения.

`/domain-modeling` усиливает проектирование в существующем коде: сверяет термины с глоссарием,
уточняет размытые понятия, проверяет утверждения по коду и сразу записывает договорённости в
`CONTEXT.md`. Архитектурное решение предлагается только тогда, когда оно труднообратимо,
неочевидно без контекста и было реальным выбором между альтернативами.

## Спецификация

`/to-spec` не интервьюирует повторно: он синтезирует уже обсуждённое. Сначала исследуются словарь
домена и решения затрагиваемой области, намечаются швы (seams) — точки, где фича будет
тестироваться, и предлагается имя integration-ветки. Дальше спецификация записывается файлом и
публикуется в трекер; публикация не передаёт тело inline, а читает его из файла.

Что содержит спецификация:

- Problem Statement — в чём проблема;
- Solution — что меняется;
- User Stories — что нужно пользователю и зачем;
- Implementation Decisions — модули, интерфейсы и решения, без путей к коду;
- Testing Decisions — какие швы проверяются и на каком уровне;
- Out of Scope — что явно не входит в работу;
- Integration Branch — точное имя ветки, в которую пойдёт работа.

Раздел Out of Scope ограничивает объём: без явного запрета агент склонен добавить попутное
кэширование или правку инфраструктуры. После публикации integration-ветка создаётся от базовой
ветки проекта; существующую ветку никто не сбрасывает и не удаляет.

## Декомпозиция

`/to-tickets` превращает спецификацию в тикеты — вертикальные слайсы, каждый из которых проверяется
независимо и помещается в одно свежее контекстное окно. До явного одобрения разбивки ничего не
публикуется: агент показывает слайсы, рёбра блокировки и оценку, а затем уточняет их по замечаниям.

- Слайс — не слой. Тикет, который «добавляет слой», не проверяется отдельно.
- Блокировка ставится за зависимость по результату, а не за пересечение файлов.
- Оценка в story points по шкале Фибоначчи даёт метку маршрута: `pipeline::fast` для мелкого
  объёма, `pipeline::full` для значимого.
- Режим исполнения `hitl` или `afk` решает, кто реализует тикет: человек по руководству или агент.

Тикет получает метку состояния `status::ready`, а если он ждёт другой тикет того же пакета —
`status::blocked`. Блокировка снимается только подтверждённым merge и закрытием предшественника.

## Оркестрация Discovery Pipeline

Одобренные на проектировании пути фиксируются как часть договорённости, сохраняются в спецификации
и назначаются конкретным тикетам. Перед реализацией из этих путей, тестов и решений собирается
Context Package — детерминированный набор данных для ролей одного batch. Coordinator регистрирует
пакет в ledger и сверяет его свежесть по хешам источников перед каждым dispatch.

Подробнее об устройстве runtime и хранилища — в [обзоре архитектуры](../architecture/overview.md).
