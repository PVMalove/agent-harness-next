# block-direct-master

## 1. Name and localization
- **English name:** block-direct-master.sh (PreToolUse Hook)
- **Translation / Essence:**

```text
Blocking of direct commits and pushes to protected branches (master, main, base_branch, integration/*) according to the "Zero Direct Commits" rule.
```
## 2. Full description
The script is a pre-hook (PreToolUse) for the bash command execution tool. Its main task is to enforce the "Zero Direct Commits" rule (described in `docs/agents/git-workflow.md`) deterministically. The rule prohibits the agent from making changes (commits and pushes) directly to protected branches.

**How it works:**
1. `direct_commits.py` makes the decision on the fail-closed principle: the command is allowed only with code `0` and the word `allow` in its output. A missing Python, any other code, and a partial copy of the module give code `2`.
2. The command is parsed into tokens (`pr_commands.parse`), and every call of `git commit` and `git push` is found in it, including inside `bash -c`, `eval`, and after `sudo`, `env`, `xargs`. Global git options before the subcommand (`-C`, `-c`, `--git-dir`, `--work-tree`, `--no-pager`, and others) are taken into account. A mention of commit/push in the arguments of printing commands (`grep`, `rg`, `echo`, `cat`), in quotes, and in a heredoc body does not count as a call. A heredoc body is excluded from the analysis only when the shell structure is strictly parsed and the data goes to something other than an interpreter. A pipeline, a command substitution, and an unknown stdin interpreter (`bash <<EOF`, `| $SHELL`) keep the original text, so `git commit` inside such a heredoc is still blocked.
3. For each call, the script determines the working directory: an earlier `cd` in the same command; otherwise the `workdir` of the `exec_command` call from `tool_input`; otherwise `cwd` from the payload; otherwise the project root (`CLAUDE_PROJECT_DIR`). An explicit `workdir` takes precedence over `cwd`, because the second runtime runs the command in it, while the payload `cwd` stays the session directory; a relative `workdir` is resolved from the payload `cwd`. `git rev-parse` queries the branch from this directory with the same options `-C`, `--git-dir`, `--work-tree`, `--bare` as the call, so the check covers the branch of exactly the checkout that receives the commit.
   - `cd` (and also `pushd`, `builtin cd`) is taken into account only if the command is a simple chain that the strict lexer accepts (`pr_commands.strict_steps`): without `$`, backticks, parentheses, and comments. In a chain, `cd` changes the directory of later calls if it surely runs: not in a pipeline (`|`) and not in a list with `||`. A `cd` that is not first in an `&&` list (`x && cd p`) takes effect only until `;`. A list that runs in the background (`&`) does not change the directory.
   - If the command contains `cd` and the chain is not simple, the directory of the calls is considered undefined. For example, `cd <wt> && git commit -m "$(cat <<'EOF' …)"` is blocked; use `git -C <wt> commit -m "$(…)"` instead.
4. Protected branches: `master`, `main`, the project base branch (`base_branch` from `.harness/project.json` in the project root), and any branch with the prefix `integration/`. A commit or push from a checkout on a protected branch is blocked.
5. For `git push`, the script additionally checks the target ref of each refspec (for example, `git push origin HEAD:master` or `git push origin feature:integration/payments`). A push to `master`, `main`, or `base_branch` is blocked even when it runs from an issue branch. A push with `--all`, `--branches`, `--mirror`, or with `*` in a refspec is blocked too: it can update a protected branch.
6. Exception: creation of a new epic integration branch (the `/to-spec` step). For each target ref `integration/<name>`, the script uses `git ls-remote` to check whether it exists on the remote named in the command. A push that only creates `integration/*` refs that are absent on the remote is allowed even from a protected branch. A push to an existing `integration/<name>` is blocked; if the remote is unavailable and existence cannot be checked, the push is blocked with an explanation. A commit and other pushes in the same command are checked as usual.
7. Second exception: the first commit of the grilling documents to a new integration branch (also the `/to-spec` step). `git commit` on the branch `integration/<name>` is allowed only if all of these conditions hold:
   - the command consists of one simple `git commit` without a variable prefix, pipeline, `&&`, and `;`: another command in the same call could change the index after the check;
   - `git commit` has only message options (`-m`, `--message`, `-F`, `--file`) and `-q`, `--quiet`, `-s`, `--signoff`; paths, `-a`, `-i`, `--amend`, and other options cancel the exception;
   - the index is not empty and contains only grilling documentation paths: `CONTEXT.md`, `CONTEXT-MAP.md`, `**/CONTEXT.md`, `docs/adr/**`, `**/docs/adr/**`; a rename is checked by both paths (`git diff --cached --no-renames`);
   - `git ls-remote` confirms that the branch does not exist on `origin`.

   If the branch already exists on `origin` or the remote is unavailable, the commit is blocked with the usual protected-branch message.
8. Fail closed: a commit/push is blocked in text that cannot be parsed (an unclosed quote, `python -c` code, commands from shell stdin), and in a command whose program or shell text bash evaluates at run time (`$X`, `sh -c "$(…)"`), if `commit` or `push` can turn out to be a git subcommand. The hook blocks such a command in three cases: its arguments contain a separate word `commit` or `push` (`$C commit`); the text of the whole command contains `git … commit`; the command has a dynamic argument (`$SUB`), and a separate word `commit` stands in another command of the chain. A part of an option (`--commit-plan-file`) and a part of a file name (`commit-plan-618.json`) do not block the command. A call whose checkout cannot be determined is also blocked: `cd` to a path with a variable or substitution, to a nonexistent directory, `cd -`, `popd`, `cd` outside a simple chain, `GIT_DIR`/`GIT_WORK_TREE` in the command, `env -C`, a `-C`/`--git-dir`/`--work-tree` path in which git finds no repository (for example, `{}` from `xargs`). A `workdir` of a non-string type also blocks the command: the actual checkout is unknown.

Limitation: the word `git` in the arguments of a non-printing command counts as a possible call, so, for example, `gh pr view --json git --jq commit` is blocked on a protected branch.
## 3. Contracts
- **Input (Input/Brief):** The JSON object of the Bash tool call, passed through standard input (`stdin`). The fields `tool_input.command`, `tool_input.workdir` (an optional `exec_command` parameter of the second runtime), and `cwd` are used. The environment variable `CLAUDE_PROJECT_DIR` (default `.`) sets the project root: the default working directory and the location of `.harness/project.json`.
- **Output (Output/Report):** Returns exit code `0` if no violations are found (allows the command to run). On an attempt to commit/push to a protected branch, on an unparsed command with commit/push, on an undefined checkout, or on a non-string `workdir`, returns exit code `2` and prints the reason to the standard error stream (`stderr`), which stops the tool.
