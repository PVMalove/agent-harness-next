# block-direct-master

## 1. Название и локализация
- **Английское название:** block-direct-master.sh (PreToolUse Hook)
- **Русский перевод / Суть:**

```text
Блокировка прямых коммитов и пушей в защищённые ветки (master, main, base_branch, integration/*) по правилу "Zero Direct Commits".
```
## 2. Полное описание
Хук `PreToolUse(Bash)` запрещает агенту коммитить и пушить напрямую в защищённые ветки. Так он проверяет правило "Zero Direct Commits" из `docs/agents/git-workflow.md`, и результат не зависит от поведения модели.

**Как хук решает:**
1. Решение принимает `direct_commits.py` по принципу fail closed: команда проходит, только если модуль вернул код `0` и напечатал слово `allow`. Если Python нет, модуль вернул другой код или скопирован не полностью, хук возвращает код `2`.
2. `pr_commands.parse` разбирает команду на токены, и хук находит в ней каждый вызов `git commit` и `git push`, в том числе внутри `bash -c`, `eval` и после `sudo`, `env`, `xargs`. Хук учитывает глобальные опции git перед подкомандой (`-C`, `-c`, `--git-dir`, `--work-tree`, `--no-pager` и другие). Упоминание commit/push в аргументах печатающих команд (`grep`, `rg`, `echo`, `cat`), в кавычках и в теле heredoc вызовом не считается. Тело heredoc хук пропускает, только если структура shell строго разобрана и данные получает не интерпретатор. Если тело уходит в конвейер, в подстановку команды или в неизвестный интерпретатор stdin (`bash <<EOF`, `| $SHELL`), хук проверяет исходный текст, и `git commit` внутри такого heredoc блокируется.
3. Для каждого вызова хук определяет каталог запуска. Порядок такой: `cd` раньше в той же команде, затем `workdir` вызова `exec_command` из `tool_input`, затем `cwd` из payload, затем корень проекта (`CLAUDE_PROJECT_DIR`). Явный `workdir` важнее `cwd`: второй runtime выполняет команду в `workdir`, а `cwd` payload остаётся каталогом сессии. Относительный `workdir` хук разрешает от `cwd` payload. Ветку хук спрашивает через `git rev-parse` из этого каталога и с теми же опциями `-C`, `--git-dir`, `--work-tree`, `--bare`, что у вызова. Поэтому хук проверяет ветку того checkout, куда попадёт коммит.
   - Хук учитывает `cd` (а также `pushd` и `builtin cd`), только если команда представляет собой простую цепочку, которую принимает строгий лексер (`pr_commands.strict_steps`): без `$`, обратных кавычек, скобок и комментариев. В такой цепочке `cd` меняет каталог следующих вызовов, если точно выполнится: не в конвейере (`|`) и не в списке с `||`. Если `cd` стоит в списке `&&` не первым (`x && cd p`), он действует только до `;`. Список, запущенный в фоне (`&`), каталог не меняет.
   - Если в команде есть `cd`, а цепочка не простая, каталог вызовов хук считает неопределённым. Например, `cd <wt> && git commit -m "$(cat <<'EOF' …)"` блокируется. Вместо этого используйте `git -C <wt> commit -m "$(…)"`.
4. Защищённые ветки: `master`, `main`, базовая ветка проекта (`base_branch` из `.harness/project.json` в корне проекта) и любая ветка с префиксом `integration/`. Хук блокирует commit и push из checkout на защищённой ветке.
5. Для `git push` хук дополнительно проверяет целевой реф каждого рефспека, например `git push origin HEAD:master` или `git push origin feature:integration/payments`. Push в `master`, `main` или `base_branch` блокируется, даже если агент пушит из issue-ветки. Push с `--all`, `--branches`, `--mirror` или с `*` в рефспеке тоже блокируется: он может обновить защищённую ветку.
6. Первое исключение: создание новой интеграционной ветки эпика (шаг `/to-spec`). Для каждого целевого рефа `integration/<name>` хук через `git ls-remote` проверяет, есть ли он на remote из команды. Если push только создаёт `integration/*`, которых ещё нет на remote, хук пропускает его даже из защищённой ветки. Push в уже существующую `integration/<name>` блокируется. Если remote недоступен и проверить ветку нельзя, push блокируется с объяснением. Commit и другие push в той же команде хук проверяет как обычно.
7. Второе исключение: первый коммит документов прожарки в новую интеграционную ветку (тоже шаг `/to-spec`). Хук пропускает `git commit` на ветке `integration/<name>`, только если выполнены все условия:
   - команда состоит из одного простого `git commit` без префикса переменных, конвейера, `&&` и `;`, потому что другая команда в том же вызове могла бы изменить индекс после проверки;
   - у `git commit` есть только опции сообщения (`-m`, `--message`, `-F`, `--file`) и `-q`, `--quiet`, `-s`, `--signoff`; пути, `-a`, `-i`, `--amend` и другие опции отменяют исключение;
   - индекс не пуст и содержит только пути документации прожарки: `CONTEXT.md`, `CONTEXT-MAP.md`, `**/CONTEXT.md`, `docs/adr/**`, `**/docs/adr/**`; у переименования хук проверяет оба пути (`git diff --cached --no-renames`);
   - `git ls-remote` подтверждает, что ветки нет на `origin`.

   Если ветка уже есть на `origin` или remote недоступен, хук блокирует коммит обычным сообщением о защищённой ветке.
8. Fail closed. Хук блокирует commit или push в тексте, который не может разобрать: незакрытая кавычка, код `python -c`, команды из stdin оболочки. Блокируется и команда, программу или текст для оболочки которой bash вычислит только при запуске (`$X`, `sh -c "$(…)"`), если `commit` или `push` может оказаться подкомандой git. Это происходит в трёх случаях:
   - в аргументах команды есть отдельное слово `commit` или `push` (`$C commit`);
   - в тексте всей команды есть `git … commit`;
   - в команде есть динамический аргумент (`$SUB`), а отдельное слово `commit` стоит в другой команде цепочки.

   Часть опции (`--commit-plan-file`) и часть имени файла (`commit-plan-618.json`) команду не блокируют. Хук блокирует и вызов, checkout которого не определить: `cd` в путь с переменной или подстановкой, `cd` в несуществующий каталог, `cd -`, `popd`, `cd` вне простой цепочки, `GIT_DIR`/`GIT_WORK_TREE` в команде, `env -C`, путь `-C`/`--git-dir`/`--work-tree`, по которому git не находит репозиторий (например, `{}` из `xargs`). Если `workdir` не строка, хук тоже блокирует команду: checkout неизвестен.

Ограничение: слово `git` в аргументах непечатающей команды хук считает возможным вызовом. Поэтому, например, `gh pr view --json git --jq commit` на защищённой ветке блокируется.
## 3. Контракты
- **Вход (Input/Brief):** JSON вызова инструмента Bash через stdin. Хук читает поля `tool_input.command`, `tool_input.workdir` (необязательный параметр `exec_command` второго runtime) и `cwd`. Переменная окружения `CLAUDE_PROJECT_DIR` (по умолчанию `.`) задаёт корень проекта: каталог запуска по умолчанию и место `.harness/project.json`.
- **Выход (Output/Report):** код `0`, если нарушений нет, и команда выполняется. Код `2` и причина в `stderr`, если агент коммитит или пушит в защищённую ветку, если команду с commit/push не удалось разобрать, если checkout не определён или `workdir` не строка. Код `2` прерывает вызов инструмента.
