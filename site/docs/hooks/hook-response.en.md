# hook-response

## 1. Name and localization
- **English name:** hook_response.py (hook verdict envelope)
- **Translation / Essence:**

```text
Response envelope of managed hooks: a JSON verdict, a return code by decision, and the hooks policy profile of the project.
```
## 2. Full description
Every managed event hook (`block-dangerous-git`, `block-direct-master`, `block-pr-merge`, `block-public-attribution`, `require-qa-gate`, `protect-hook-policy`, `check-branch-name`, `check-worktree-branch-name`, `require-bounded-check`, `block-scratch-outside-docs-tasks`, `count-skill-usage`, `mark-qa-gate-passed`) at the start of the script restarts itself through `hook_response.py run <hook_id> <bash> <сценарий>`. The ChangeImpact advisory hooks (`impact-first-touch`, `targeted-check-reminder`, `sensitive-path-recheck`) are started through the envelope directly into the shared body: `hook_response.py run <hook_id> <python> change_impact_hooks.py <hook_id>`. The module reads the stdin of the call, starts the original script with the same stdin, passes its stdout and stderr through unchanged, and prints the verdict as the last line of stderr:

```json
{"hook_id":"block-pr-merge","profile":"standard","decision":"block","reason_code":"pr-merge","remedy":"…","evidence_ref":".claude/hooks/block-pr-merge.sh"}
```

- **Block reason.** The `reason_code` of a block is the code of the hook rule. A script with several rules (`protect-hook-policy`, and for an unparseable patch of `apply_patch` of the second runtime also `block-scratch-outside-docs-tasks` with the code `apply-patch-unparseable`) names the reason with the prefix `[reason_code] ` at the start of stderr (`EXTRA_REASONS`); an unregistered prefix is ignored.
- **Decision and return code.** `allow` and `warn` are code `0`, `block` is code `2`. The verdict goes to stderr, not to stdout: Claude Code parses stdout on code `0` as its own JSON protocol, and the values `allow`/`warn` are not defined in it.
- **Exit code of the original script.** `0` is `allow` with `reason_code` `ok`; `2` is a block with the `reason_code` of the rule of this hook; any other code, a start failure, termination by a signal, or a hang longer than the timeout is an internal error. The body timeout is 50 s (`INNER_TIMEOUT_SECONDS`, less than the 60 s timeout of the hook in the runtime): the process is interrupted, the envelope issues the `internal-error` verdict, which for a critical hook is `block` with code `2`, and for the rest is `warn`.
- **Criticality (ADR 0024).** Critical hooks (`block-public-attribution`, `block-direct-master`, `block-pr-merge`, `protect-hook-policy`, `check-branch-name`, `check-worktree-branch-name`, `block-dangerous-git`, `block-scratch-outside-docs-tasks`, `require-qa-gate`) block on an internal error (`block`, `internal-error`, code `2`), including when the envelope itself fails. The behavioral `require-bounded-check` and the accounting `count-skill-usage`, `mark-qa-gate-passed` allow with a warning on an internal error (`warn`, code `0`); accounting hooks do not block by design, so their code `2` also counts as an internal error.
- **ChangeImpact advisory hooks (ADR 0024, section 2a).** The class `ADVISORY_HOOKS`: [`impact-first-touch`](impact-first-touch.md), [`targeted-check-reminder`](targeted-check-reminder.md), and [`sensitive-path-recheck`](sensitive-path-recheck.md). The body always exits with code `0`. The warning is the first line of stderr `[reason_code] remedy` with the own code of the hook and, when present, the line `evidence_ref=<путь>`; stdout contains only the JSON of the runtime protocol. The envelope decides as follows: code `0` with the hook prefix is `warn` (stdout is passed through), code `0` without the prefix is `allow`. The prefix `[internal-error]`, any other code, a start failure, and a timeout give `warn` `internal-error` with code `0`, and the stdout of the body is discarded: a partial output would break the `Stop` protocol of the second runtime. The body timeout of an advisory hook is 10 s (`ADVISORY_TIMEOUT_SECONDS`), because the body sits on the hot path of every edit; the shared `INNER_TIMEOUT_SECONDS` and the branch of the critical hooks do not change. No profile gives an advisory hook `block` and code `2`.
- **Active profiles of advisory hooks.** The envelope applies the profile before the body starts (`ACTIVE_PROFILES`): `impact-first-touch` and `targeted-check-reminder` work in `standard` and `strict`, `sensitive-path-recheck` only in `strict`. In the other profiles the envelope answers `allow` with `reason_code` `ok`, the body is not started, and no state is written.
- **Profile.** It is taken only from the `hook_policy` key of the `.harness/project.json` file of the project that contains `.claude/hooks/hook_response.py`. Environment variables, including `HOOK_PROFILE`, and tool parameters are not read. A project without the file or without the key gets `standard`. The hook does not know the role and the paths of the command and cannot check the escalation conditions, so it applies the strictest escalation to all calls: the profile is the strictest of the base one and all `escalations[].profile` (a project with `minimal` and an escalation to `standard` for the `qa` role gets `standard`, and `require-bounded-check` blocks). This only tightens: `hook_policy.resolve_profile` gives a profile no higher for any call. A key that cannot be parsed or whose values are unknown, and a file that cannot be read or parsed, give `strict` — the shift is only toward the strict side.
- **What the profile changes.** `minimal` lowers the block of the behavioral hook (`require-bounded-check`) to a warning (`warn`, code `0`, the rule `reason_code` is preserved) and turns off advisory hooks. Critical hooks block in any profile. `standard` keeps all blocking decisions and enables `impact-first-touch` and `targeted-check-reminder`; a project without `hook_policy` behaves as `standard`. `strict` keeps the same decisions, also enables `sensitive-path-recheck`, and adds the fail-closed boundaries of the coordinator (below).
- **Strict boundary (coordinator).** Under `strict`, `dispatch propose` and `dispatch create` for code-review and QA, `qa run`, and `dispatch publish` refuse with code `2` and the error `strict_impact_unknown` if the diff of the candidate from the batch base (`--no-renames`, that is, also the previous path of a rename) changes a sensitive path, and the VerificationPlan does not prove the ImpactSet (ADR 0023) for it. The plan proves the impact when all its stages are `full` or no `impact.unknown` reason refers to a sensitive changed path and there is no reason without a path. The refusal lists up to 20 sensitive paths and names the boundary; the remedy is to enable `verification_plan_policy` in the orchestration config and create a new batch so that review and QA carry the plan, or for the human owner to change `hook_policy` in `.harness/project.json` and repeat propose. The refusal happens before any mutation: the brief is not written, the QA lease is not taken, the push is not performed, so a repeat gives the same decision. The source of the ImpactSet is only the VerificationPlan proposal or the brief: the boundary does not recompute the ImpactSet, so `strict` without `verification_plan_policy` refuses review and QA for any sensitive change. The policy role for escalations: `review` for code-review, `qa` for QA and `qa run`, `coordinator` for publish. The propose profile is taken from `hook_policy` in `.harness/project.json`; `qa run` and publish decide by the policy of the started dispatch — a snapshot of its pinned configuration, whose hash must match the `hook_policy_sha256` of the brief (a mismatch is an integrity refusal), so an edit of `project.json` after approval does not change the decision. A brief without `hook_policy_sha256` gets `standard`. For publish, the plan is the VerificationPlan of the brief of the accepted QA. `minimal` and `standard` behave as before on these boundaries. Strict does not check every tool call, does not run `make verify` and the full set from the hook, and does not block the recovery commands `ledger lock-status`, `qa clear-stale-lease`, `batch rewind`, `dispatch cancel`, and `ledger release-lock --force` (the last one still requires `--approved-by`, `--approved-at`, and `--reason`).
- **Decision R1 on the Rust part of the boundaries.** ADR 0024, section 2a, calls the fail-closed check a check of the coordinator and Rust, and section 3 gives the authoritative check to the Rust policy module for the operations that Rust executes. Today the Rust runtime executes neither `dispatch propose`, nor `qa run`, nor publish: Python executes these operations. Therefore, by decision R1, one Python function of the coordinator, `hook_policy.require_strict_boundary`, checks all three boundaries. A task that moves the execution of QA to Rust (ADR 0022) will add the Rust check of `qa run` by the saved `hook_policy_sha256` and the plan. The execution of QA in Python does not move with it: the policy decision stays in the Python zone. The scoped hook of the test-author subagent (`test-author-guard.py`) is wired in the agent description, answers with its own soft-refusal protocol, and does not pass through the envelope.
- **Registry.** The values `hook_id`, `profile`, `decision`, and `reason_code` are registered in `harness/orchestration/system_fields.v1.json` (the fields `hook.id`, `hook.profile`, `hook.decision`, `hook.reason_code`). `parse_hook_response` in `harness/orchestration/hook_policy.py` reads the verdict as the last non-empty line of the output and rejects an unregistered value with a contract error.
- **Without the envelope.** If Python or `hook_response.py` is unavailable, the script runs directly and decides on its own, as before: critical scripts without Python still block.
- **Second runtime.** The `.codex/hooks.json` adapter calls the same scripts, so its envelope, verdict, and profile are the same: the profile is taken from the `hook_policy` of the project, not from the runtime environment. A subset for `Bash` on `PreToolUse` (the critical guards and `require-bounded-check`) and `targeted-check-reminder` on `Stop` and `SubagentStop` are wired; hooks on `Write` and `Edit` (including `impact-first-touch`, `sensitive-path-recheck`, and the touch log of `targeted-check-reminder` before the `apply_patch` adapter), `EnterWorktree` and `Skill`, and `mark-qa-gate-passed` on `PostToolUse` are not wired (the second runtime calls `PostToolUse` also after a command with a non-zero exit code, and the payload has no exit code), and `harness health` shows them as missing in the `hooks.policy` check. The project hooks of this runtime work only after trust in the `.codex/` layer of the project and in each hook by hash. The merge of the settings files and the composition of the adapter are described in [install-and-update.md](install-and-update.md).
- **Restart marker.** The original script is started with the variable `HARNESS_HOOK_ENVELOPE=1`, so that it does not wrap itself a second time.

## 3. Contracts
- **Input (Input/Brief):** `run <hook_id> <команда...>`; `hook_id` must be registered. The JSON payload of the tool call comes through stdin.
- **Output (Output/Report):**
  - **Allow/warning:** code `0`, the last line of stderr is the verdict with `decision` `allow` or `warn`.
  - **Block:** code `2`, the last line of stderr is the verdict with `decision` `block`; the message of the original script stands before it.
  - **Unknown `hook_id` or an invalid call:** code `2` and a message in stderr without a verdict.
