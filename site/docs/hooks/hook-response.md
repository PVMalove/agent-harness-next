# hook-response

## 1. Название и локализация
- **Английское название:** hook_response.py (hook verdict envelope)
- **Русский перевод / Суть:**

```text
Конверт ответа управляемых hooks: JSON-вердикт, код возврата по решению и профиль политики hooks проекта.
```
## 2. Полное описание
Конверт `hook_response.py` даёт всем управляемым hooks один формат ответа: JSON-вердикт, код возврата по решению и профиль политики hooks проекта. Каждый управляемый hook (`block-dangerous-git`, `block-direct-master`, `block-pr-merge`, `block-public-attribution`, `require-qa-gate`, `protect-hook-policy`, `check-branch-name`, `check-worktree-branch-name`, `require-bounded-check`, `block-scratch-outside-docs-tasks`, `count-skill-usage`, `mark-qa-gate-passed`) в начале сценария подключает общий фрагмент `.claude/hooks/hook-envelope.sh` со своим `hook_id` (`. "$(dirname "$0")/hook-envelope.sh" <hook_id>`). Фрагмент перезапускает сценарий через `hook_response.py run <hook_id> <bash> <сценарий>`. Advisory-hooks ChangeImpact (`impact-first-touch`, `targeted-check-reminder`, `sensitive-path-recheck`) запускают через конверт сразу общее тело: `hook_response.py run <hook_id> <python> change_impact_hooks.py <hook_id>`. Конверт читает stdin вызова, запускает исходный сценарий с тем же stdin, передаёт его stdout и stderr без изменений и последней строкой stderr печатает вердикт:

```json
{"hook_id":"block-pr-merge","profile":"standard","decision":"block","reason_code":"pr-merge","remedy":"…","evidence_ref":".claude/hooks/block-pr-merge.sh"}
```

- **Причина блокировки.** `reason_code` блокировки равен коду правила hook. Если у сценария несколько правил, он называет причину префиксом `[reason_code] ` в начале stderr (`EXTRA_REASONS`). Так делают `protect-hook-policy` и, для неразбираемого патча `apply_patch` второго runtime, `block-scratch-outside-docs-tasks` с кодом `apply-patch-unparseable`. Незарегистрированный префикс конверт игнорирует.
- **Решение и код возврата.** `allow`, `warn` и `ask` дают код `0`, `block` даёт код `2`. Вердикт `ask` просит ручного подтверждения человека. Код `3` тела с зарегистрированной причиной (`ASK_REASONS`, сейчас только `project-json-shell-write` у `protect-hook-policy`) конверт превращает в `ask`, если задан `CLAUDE_PROJECT_DIR` (Claude Code), иначе в `block`. При `ask` в stdout идёт JSON `permissionDecision: "ask"` с причиной. Вердикт конверт пишет в stderr, а не в stdout: Claude Code при коде `0` разбирает stdout как собственный JSON-протокол, а значения `allow`/`warn` в нём не определены.
- **Код исходного сценария.** `0` даёт `allow` с `reason_code` `ok`; `2` даёт блокировку с `reason_code` правила этого hook. Любой другой код, сбой запуска, завершение по сигналу или зависание дольше тайм-аута считаются внутренней ошибкой. Тайм-аут тела равен 50 с (`INNER_TIMEOUT_SECONDS`), это меньше 60 с тайм-аута hook в runtime. Конверт прерывает процесс и выдаёт вердикт `internal-error`: для критичного hook это `block` с кодом `2`, для остальных `warn`.
- **Критичность (ADR 0024).** Критичные hooks (`block-public-attribution`, `block-direct-master`, `block-pr-merge`, `protect-hook-policy`, `check-branch-name`, `check-worktree-branch-name`, `block-dangerous-git`, `block-scratch-outside-docs-tasks`, `require-qa-gate`) при внутренней ошибке блокируют (`block`, `internal-error`, код `2`), в том числе при сбое самого конверта. Поведенческий `require-bounded-check` и учётные `count-skill-usage`, `mark-qa-gate-passed` при внутренней ошибке разрешают с предупреждением (`warn`, код `0`). Учётные hooks по замыслу не блокируют, поэтому их код `2` тоже считается внутренней ошибкой.
- **Advisory-hooks (ADR 0024, раздел 2a; ADR 0031).** Класс `ADVISORY_HOOKS` включает hooks ChangeImpact [`impact-first-touch`](impact-first-touch.md), [`targeted-check-reminder`](targeted-check-reminder.md), [`sensitive-path-recheck`](sensitive-path-recheck.md) и автозапуск runtime `runtime-autostart`. Тело всегда завершается кодом `0`. Предупреждение тело пишет первой строкой stderr `[reason_code] remedy` с собственным кодом hook и, если есть, строкой `evidence_ref=<путь>`; stdout содержит только JSON протокола runtime. Конверт решает так: код `0` с префиксом hook даёт `warn` (stdout передаётся), код `0` без префикса даёт `allow`. Префикс `[internal-error]`, любой другой код, сбой запуска и тайм-аут дают `warn` `internal-error` с кодом `0`, а stdout тела конверт отбрасывает: частичный вывод сломал бы протокол `Stop` второго runtime. Тайм-аут тела advisory-hook равен 10 с (`ADVISORY_TIMEOUT_SECONDS`), потому что тело стоит на горячем пути каждой правки. Исключение: `runtime-autostart` ждёт готовности `serve`, поэтому его тайм-аут равен `INNER_TIMEOUT_SECONDS` (`TIMEOUTS`). Общий `INNER_TIMEOUT_SECONDS` и ветка критичных hooks не меняются. Ни в одном профиле advisory-hook не получает `block` и код `2`.
- **Активные профили advisory-hooks.** Конверт применяет профиль до запуска тела (`ACTIVE_PROFILES`): `impact-first-touch` и `targeted-check-reminder` работают в `standard` и `strict`, `sensitive-path-recheck` только в `strict`, `runtime-autostart` во всех трёх профилях. В остальных профилях конверт отвечает `allow` с `reason_code` `ok`, тело не запускается и состояние не пишется.
- **Профиль.** Конверт берёт профиль только из ключа `hook_policy` файла `.harness/project.json` того проекта, в котором лежит `.claude/hooks/hook_response.py`. Переменные окружения, включая `HOOK_PROFILE`, и параметры инструмента конверт не читает. Проект без файла или без ключа получает `standard`. Hook не знает роль и пути команды и не может проверить условия эскалации. Поэтому он применяет самую строгую эскалацию ко всем вызовам: профиль равен самому строгому из базового и всех `escalations[].profile`. Например, проект с `minimal` и эскалацией до `standard` для роли `qa` получает `standard`, и `require-bounded-check` блокирует. Это правило только ужесточает: `hook_policy.resolve_profile` для любого вызова даёт профиль не выше. Ключ, который нельзя разобрать или значения которого неизвестны, и файл, который нельзя прочитать или разобрать, дают `strict`, то есть сдвиг только в строгую сторону.
- **Что меняет профиль.** `minimal` понижает блокировку поведенческого hook (`require-bounded-check`) до предупреждения (`warn`, код `0`, `reason_code` правила сохраняется) и выключает advisory-hooks ChangeImpact. Критичные hooks блокируют в любом профиле. `standard` сохраняет все блокирующие решения и включает `impact-first-touch` и `targeted-check-reminder`; проект без `hook_policy` ведёт себя как `standard`. `strict` сохраняет те же решения, включает ещё `sensitive-path-recheck` и добавляет fail-closed границы coordinator (ниже).
- **Граница strict (coordinator).** Под `strict` команды `dispatch propose` и `dispatch create` для code-review и QA, `qa run` и `dispatch publish` отказывают с кодом `2` и ошибкой `strict_impact_unknown` при двух условиях: diff кандидата от базы batch (`--no-renames`, то есть с прежним путём переименования) меняет чувствительный путь, а VerificationPlan не доказывает ImpactSet (ADR 0023) для этого пути. План доказывает влияние, когда все его стадии `full` или ни одна причина `impact.unknown` не относится к чувствительному изменённому пути и нет причины без пути. Отказ перечисляет до 20 чувствительных путей и называет границу. Исправить можно двумя способами: включить `verification_plan_policy` в конфиге orchestration и создать новый batch, чтобы review и QA несли план, либо человек-владелец меняет `hook_policy` в `.harness/project.json` и повторяет propose. Отказ происходит до любой мутации: brief не пишется, QA-lease не берётся, push не выполняется, поэтому повтор даёт то же решение. ImpactSet граница берёт только из VerificationPlan proposal или brief и сама его не пересчитывает. Поэтому `strict` без `verification_plan_policy` отказывает review и QA любому чувствительному изменению. Роль политики для эскалаций: `review` для code-review, `qa` для QA и `qa run`, `coordinator` для publish. Профиль propose граница берёт из `hook_policy` в `.harness/project.json`. `qa run` и publish решают по политике запущенного dispatch, то есть по снимку его пинованной конфигурации. Хеш этого снимка обязан совпасть с `hook_policy_sha256` brief, иначе граница отказывает с ошибкой целостности. Поэтому правка `project.json` после approval решение не меняет. Brief без `hook_policy_sha256` получает `standard`. У publish план берётся из VerificationPlan brief принятого QA. `minimal` и `standard` на этих границах ведут себя как раньше. Strict не проверяет каждый вызов инструмента, не запускает `make verify` и полный набор из hook и не блокирует команды восстановления `ledger lock-status`, `qa clear-stale-lease`, `batch rewind`, `dispatch cancel` и `ledger release-lock --force` (последняя по-прежнему требует `--approved-by`, `--approved-at` и `--reason`).
- **Решение R1 о Rust-части границ.** ADR 0024, раздел 2a, называет fail-closed проверку проверкой coordinator и Rust, а раздел 3 отдаёт авторитетную проверку модулю политики Rust для операций, которые исполняет Rust. Сейчас Rust runtime не исполняет ни `dispatch propose`, ни `qa run`, ни publish: эти операции исполняет Python. Поэтому по решению R1 все три границы проверяет одна Python-функция coordinator `hook_policy.require_strict_boundary`. Rust-проверку `qa run` по сохранённому `hook_policy_sha256` и плану добавит задача, которая переводит исполнение QA в Rust (ADR 0022). Исполнение QA в Python при этом не переносится, и решение политики остаётся зоной Python. Скоупный hook субагента test-author (`test-author-guard.py`) подключён в описании агента, отвечает собственным протоколом мягкого отказа и через конверт не проходит.
- **Реестр.** Значения `hook_id`, `profile`, `decision` и `reason_code` зарегистрированы в `harness/orchestration/system_fields.v1.json` (поля `hook.id`, `hook.profile`, `hook.decision`, `hook.reason_code`). `parse_hook_response` в `harness/orchestration/hook_policy.py` читает вердикт как последнюю непустую строку вывода и отклоняет незарегистрированное значение ошибкой контракта.
- **Без конверта.** Если Python, `hook-envelope.sh` или `hook_response.py` недоступны, сценарий выполняется напрямую и решает сам, как раньше. Критичные сценарии без Python по-прежнему блокируют.
- **Старый конверт и `runtime-autostart`.** Advisory-скрипт `runtime-autostart.sh` не передаёт управление конверту через `exec`, а ждёт его код. Конверт, который знает этот hook, всегда отвечает для него кодом `0`. Ненулевой код значит, что установленный `hook_response.py` старее скрипта и не регистрирует `runtime-autostart`. Тогда скрипт печатает в stderr `[runtime-autostart-failed] … выполните harness update <repo> --force-seed-file .claude/hooks/hook_response.py` и завершается кодом `0`, поэтому не блокирует `Bash` и не продолжает ход на `Stop`. Критичные hooks по-прежнему делают `exec` в конверт, и незарегистрированный `hook_id` критичного hook даёт код `2`.
- **Второй runtime.** Адаптер `.codex/hooks.json` вызывает те же сценарии, поэтому конверт, вердикт и профиль у него те же: профиль берётся из `hook_policy` проекта, а не из окружения runtime. Подключены:
    - на `PreToolUse` для `Bash`: критические guards и `require-bounded-check`;
    - на `PreToolUse` для `apply_patch|Write|Edit`: `protect-hook-policy` и `block-scratch-outside-docs-tasks`;
    - на `Stop` и `SubagentStop`: `targeted-check-reminder`.

    Не подключены остальные hooks на `Write` и `Edit` (`impact-first-touch`, `sensitive-path-recheck` и журнал касаний `targeted-check-reminder`, пока нет адаптера `apply_patch`), hooks на `EnterWorktree` и `Skill`, `runtime-autostart` и `mark-qa-gate-passed` на `PostToolUse`. Последний не подключён потому, что второй runtime вызывает `PostToolUse` и после команды с ненулевым кодом выхода, а кода выхода в payload нет. `harness health` в проверке `hooks.policy` показывает такие hooks как отсутствующие. Проектные hooks этого runtime работают только после доверия слою `.codex/` проекта и каждому hook по хэшу. Слияние файлов настроек и состав адаптера описаны в [install-and-update.md](install-and-update.md).
- **Маркер повторного запуска.** Исходный сценарий запускается с переменной `HARNESS_HOOK_ENVELOPE=1`, чтобы не обернуть себя второй раз.

## 3. Контракты
- **Вход (Input/Brief):** `run <hook_id> <команда...>`; `hook_id` обязан быть зарегистрирован. JSON-payload вызова инструмента приходит через stdin.
- **Выход (Output/Report):**
  - **Разрешение/предупреждение:** код `0`, последняя строка stderr содержит вердикт с `decision` `allow` или `warn`.
  - **Блокировка:** код `2`, последняя строка stderr содержит вердикт с `decision` `block`; перед ней стоит сообщение исходного сценария.
  - **Неизвестный `hook_id` или неверный вызов:** код `2` и сообщение в stderr без вердикта.
