# CLI и конфигурация

Команды имеют вид `harness <command> <repo> [флаги]`. `<repo>` задаёт путь к целевому проекту, это
не обязательно текущий каталог. Harness не становится зависимостью проекта: он работает с
репозиторием по пути и копирует в него проверяемый снимок.

## Команды

| Команда | Что делает | Пишет на диск |
| --- | --- | --- |
| `init` | Первая установка в проект без harness | да |
| `adopt` | Установка поверх проекта, где уже есть свои скиллы с теми же именами | да |
| `diff` | Сверяет проект с залоченным снимком | нет |
| `update` | Подтягивает новую версию capability | да |
| `registry` | Пересобирает реестр скиллов проекта | да |
| `lock-project-skills` | Фиксирует хеши скиллов, которыми владеет сам проект | да |
| `memory build/search/rebuild/sync/eval` | Локальный индекс памяти и указатели на разрешённые источники | `build`, `rebuild`, `sync`: да; `search`, `eval`: нет |
| `parsers status/install` | Парсеры графа проекта: состояние bundle и установка языков | `install`: да; `status`: нет |
| `health` | Диагностика установки и окружения | только с `--fix` |
| `ticket-status` | Переносит тикет спеки в колонку доски: заменяет его метку `status::*` на GitHub, GitLab или в локальном трекере, если переход разрешён | только для локального трекера `.scratch/` |
| `list` | Список установленных скиллов | нет |
| `cleanup` | План и удаление одноразовых данных `.harness` и брошенных ресурсов контейнеров | только с `--apply` |
| `worktree-remove` | Удаляет управляемый worktree, сохраняя ветку | да |
| `worktree-venv` | Связывает `.harness/.venv` worktree задачи с venv основного checkout, если `uv.lock` и `pyproject.toml` совпадают | да |
| `uninstall` | План и полное удаление harness из проекта | только с `--apply` |
| `console` | Интерактивная консоль: TUI; с `--web` поднимает сервер | через выбранные команды |
| `console-server` | Запускает сервер консоли без интерактивной оболочки | нет |

## Какую команду выбрать

| | `init` | `adopt` |
| --- | --- | --- |
| Когда | В репозитории нет harness вообще | Под именами выбранной capability уже лежат свои скиллы |
| Требование | Падает, если снимок уже установлен | Не требует пустоты: сохраняет проектные скиллы вне capability |
| Конфликт с каталогами скиллов | Падает без обходного флага | `--replace-conflicts` заменяет только конфликтующие имена |

| | `diff` | `update` |
| --- | --- | --- |
| Пишет на диск | нет, только отчёт | да |
| Код выхода | `0` чисто, `1` есть расхождение | `0` при успехе, иначе ошибка |
| Локальные правки | показывает как расхождение и не трогает | без флага отказывается; `--force-managed-files` перезаписывает снимок, `--force` перезаписывает снимок и seed-файлы |

Capability задаёт состав снимка. Сборки: `project-foundation`, `mattpocock-suite`,
`engineering-suite`, `backend-orchestration`. Без `--capability` ставится `project-foundation`.
`engineering-suite` расширяет `mattpocock-suite`, а `backend-orchestration` расширяет
`engineering-suite`.

## Конфигурация `.harness/project.json`

Контракт строгий: незнакомое поле считается ошибкой. Обязательны `language`, `base_branch`,
`branch_pattern` и `qa_gate_commands`, остальные поля необязательны. Каждое поле читает свой
потребитель.

| Поле | Назначение |
| --- | --- |
| `$schema` | Ссылка на схему конфигурации проекта |
| `language` | Язык вывода (`ru` или `en`): отчёты code-review и шаблон тела PR |
| `base_branch` | Ветка выпуска: от неё `/to-spec` создаёт integration-ветки эпиков; она же база для работы без эпика |
| `branch_pattern` | Регулярное выражение для имени issue-ветки |
| `qa_gate_commands` | Команды полного локального прогона качества |
| `shell` | Оболочка для `qa_gate_commands`: `bash` или `powershell` |
| `tracker` | Трекер проекта: `type` (`github`, `gitlab`, `local`), `host`, `project` |
| `ci_required_checks` | Имена CI-проверок, доказательство по которым принимается вместо локального QA |
| `test_paths` | Относительные glob-пути тестов: единственная зона записи test-author; без поля test-author выключен |
| `test_runner` | Команда изолированного запуска одного теста; вместе с `test_paths` нужна для test-author |
| `test_author` | Исполнитель короткого маршрута test-author: `runtime`, `model`, `effort` |
| `hook_policy` | Политика hooks: `profile` (`minimal`, `standard`, `strict`) и `escalations` |
| `story_points` | Шкала оценки и пороги маршрутизации `pipeline::fast` / `pipeline::full` |
| `memory` | Включение локальной памяти проекта |
| `memory_policy` | Разрешённые источники, redact-правила, порог и бюджет памяти |

Внутри `tracker` допустимы только `type`, `host` и `project`. Сертификаты, прокси и учётные данные
сюда не пишут: они остаются в личной конфигурации CLI трекера. Внутри `hook_policy` эскалации только
повышают профиль для путей и ролей; эскалацию слабее базового профиля валидатор отвергает.

## CI evidence

Поле `ci_required_checks` содержит уникальные непустые имена CI-проверок. Если все они прошли,
coordinator принимает доказательство от трекера вместо повторного полного локального QA. Пустое или
отсутствующее поле означает, что CI-доказательство не настроено и нужен локальный QA.

Записывайте в `ci_required_checks` полные проверки: `verify`, `rust` и другие задания, которые
`verify.yml` запускает для PR в `master`. Не записывайте туда `-light` имена. Задание `verify-light`
идёт только для PR в `integration/**`, и если пара требует полного QA, `collect-ci` отвечает на такую
проверку причиной `light_check`. Поле хранится в локальном `.harness/project.json`, который не
коммитится. Оператор задаёт его один раз, когда включает CI-доказательство, и описывает этот шаг в
тексте PR (ADR 0016, дополнение #937).

```bash
python3 .harness/orchestration/coordinator.py --repo . integration collect-ci \
  --pull-request 42 --record <record-id>
```

Команда собирает CI-доказательство для объединённого результата pull request. Она записывает только
завершённое доказательство: пройденное или проваленное. Если требуемый набор неполный, команда
ничего не пишет и сообщает `local_qa_required: true`. Тогда полный локальный прогон остаётся
обязательным: принять половину набора нельзя.

Следующий шаг по записи интеграции показывает команда:

```bash
python3 .harness/orchestration/coordinator.py --repo . integration next --ticket 42 --branch feature/issue-42-csv
```

## health

`harness health <repo>` без флагов ничего не меняет. Каждая проверка получает статус `ok`, `warn`,
`fail` или `skipped`. При `fail` команда печатает причину и команду исправления.

| Флаг | Что делает |
| --- | --- |
| без флагов | Файлы, каталоги, окружение и граф проекта |
| `--fix` | Создаёт недостающие каталоги `.harness` и пересобирает устаревший реестр скиллов; worktree не трогает |
| `--online` | Добавляет проверки трекера: авторизация CLI, доступность remote, права и метки (до 10 с на проверку); без флага все проверки `tracker.*` пропускаются |
| `--json` | Машиночитаемый отчёт для скриптов и дашбордов |

Группа «Оркестрация» появляется только при установленной `backend-orchestration`. Она показывает
authority (`runtime-store`) и версию схемы, незавершённые batch, dispatch без активности и
неучтённые worktree.

## Память проекта

`harness memory` работает офлайн и не делает сетевых вызовов.

```bash
python3 harness/bin/harness.py memory build /path/to/repository
python3 harness/bin/harness.py memory search /path/to/repository "правила ретраев"
python3 harness/bin/harness.py memory rebuild /path/to/repository
```

Поиск возвращает указатели на источник (заголовок, статус, путь и хеш), без текста документа.
Источник открывают, только если он нужен. Индекс производный: если его удалить, ничего не потеряется,
`rebuild` восстановит его с нуля. Без явного allowlist в `memory_policy` индекс остаётся пустым.

## Repo Map

Repo Map строит граф проекта с помощью парсеров tree-sitter. `parsers status` показывает состояние
bundle парсеров. `parsers install --language <язык>` скачивает закреплённые wheels и собирает bundle;
языки: `python`, `typescript`, `javascript`, `go`, `java`, `csharp`, флаг можно повторять. Без
парсеров граф проекта работает в упрощённом режиме, и проверки показывают это отдельной строкой.
Влияние изменений молча не сужается.

```bash
python3 harness/bin/harness.py parsers status /path/to/repository
python3 harness/bin/harness.py parsers install /path/to/repository --language python
```

## Coordinator

С `backend-orchestration` в проекте появляется `.harness/orchestration/coordinator.py`, CLI
оркестрации. Состояние оркестрации читают только через его команды; команды с пометкой read-only
ничего не меняют. Состояние хранит процесс `harness-runtime serve`: пока он не запущен, команды
оркестрации отказывают с `[runtime_unavailable]`.

| Группа | Назначение |
| --- | --- |
| `config` | Проверка и нормализация конфигурации оркестрации |
| `ledger` | Целостность аудиторской цепочки, блокировка, статус |
| `runtime` | Запрос к процессу runtime: рукопожатие и состояние |
| `batch` | Жизненный цикл batch: план, approval, отчёты, решения |
| `dispatch` | Запуск, наблюдение и остановка ролей |
| `qa` | Прогон QA и его доказательства |
| `integration` | Запись интеграции, CI-доказательство, следующий шаг |
| `risk` | Оценка риска изменения |
| `context-package` | Регистрация детерминированного пакета контекста |
| `report` | Приём отчётов ролей (`report submit`) и шаги политики отчёта (`report complete`) |
| `recovery` | Статус, перезагрузка, возобновление, исправление и прерывание остановленного batch |

Порядок гейтов и работа с batch описаны в руководстве [`/implement`](../guides/implement.md).

## Console

`harness console <repo>` открывает интерактивную консоль: задачи, оркестрация, отчёты и
восстановление. Консоль в статусе beta. Ей нужен `uv`, а первый запуск скачивает зависимости, поэтому
нужен доступ к сети. Если `uv` нет в `PATH`, команда показывает отчёт `harness health`.

`--web` запускает сервер консоли или находит работающий, печатает URL с токеном и открывает
браузер; с `--no-open` браузер не открывается. Веб-версия даёт тот же интерфейс, что и TUI, но в
браузере: тонкие эндпоинты и клиент на React/TS.
