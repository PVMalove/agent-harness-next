# Hooks

Hooks — детерминированные проверки, которые физически блокируют действие, а не оставляют
рекомендацию. Правило, записанное только в инструкции, можно не заметить; правило, записанное
hook-ом, возвращает отказ до выполнения команды.

Профиль задаётся только в конфигурации проекта, в ключе `hook_policy`. Переменные окружения и
параметры инструментов на выбор профиля не влияют.

## Профили

| Поведение | `minimal` | `standard` | `strict` |
| --- | --- | --- | --- |
| Критические guard-ы | да | да | да |
| Ограниченный прогон проверок | предупреждение | блокирует | блокирует |
| Уведомление об изменении влияния при первом касании рискованного пути | нет | предупреждение | предупреждение |
| Напоминание о неотчитанных точечных проверках | нет | да | да |
| Повторная проверка чувствительных путей при каждом касании | нет | нет | да |
| Отказ на границах высокого риска | нет | нет | да |

Без ключа `hook_policy` действует `standard`: блокирующий набор совпадает с привычным поведением,
поэтому существующий проект не меняет режим без явного решения. Эскалации только повышают профиль
для указанных путей или ролей — понижение валидатор отвергает.

## Критические guards

Эти проверки блокируют в любом профиле, включая `minimal`:

- **Защищённые ветки.** Прямой коммит или push в ветку выпуска и в `integration/*` запрещён: работа
  идёт в issue-ветке, защищённые ветки обновляет человек через merge.
- **Merge pull request.** Команда merge блокируется безусловно: слияние всегда выполняет человек.
- **Публичная атрибуция.** Запрещены следы автоматизированного исполнителя в сообщениях коммитов и
  заголовках и телах PR/MR; в тексте трекера блокируется только атрибуция.
- **Защита политики.** Запись в настройки hooks, каталоги hooks и изменение ключа `hook_policy`
  инструментом агента блокируются.

## Таблица hooks

| Hook | Событие | Что блокирует |
| --- | --- | --- |
| `protect-hook-policy.sh` | `PreToolUse` — Bash, Write, Edit | Правку настроек и каталогов hooks и изменение ключа политики |
| `block-direct-master.sh` | `PreToolUse(Bash)` | Коммит и push в защищённую ветку; разрешает только создание новой integration-ветки |
| `block-pr-merge.sh` | `PreToolUse(Bash)` | Любую команду merge PR/MR; при неразобранной команде отказ тоже срабатывает |
| `block-public-attribution.sh` | `PreToolUse(Bash)` | Запрещённые сведения в сообщениях коммитов, заголовках и телах PR/MR и в файлах, переданных как тело |
| `check-branch-name.sh` | `PreToolUse(Bash)` | Создание ветки, имя которой не соответствует `branch_pattern` |
| `check-worktree-branch-name.sh` | `PreToolUse(EnterWorktree)` | То же правило имени для worktree-инструмента |
| `block-scratch-outside-docs-tasks.sh` | `PreToolUse(Write, Edit)` | Временные артефакты вне разрешённых каталогов; заголовок PR и комментарии — только через файл в разрешённом месте |
| `require-qa-gate.sh` | `PreToolUse(Bash)` | Создание PR/MR, если QA не проходил или провалился для текущего дерева |
| `require-bounded-check.sh` | `PreToolUse(Bash)` | Полный прогон набора проверок без обёртки сводкой; точечный тест не блокируется |
| `block-dangerous-git.sh` | `PreToolUse(Bash)` | Разрушительные операции: `reset --hard`, `clean -f`, удаление ветки, `restore .` |
| `impact-first-touch.sh` | `PreToolUse(Write, Edit)` | Ничего: предупреждает о первом касании пути, влияние которого не вычисляется по графу |
| `sensitive-path-recheck.sh` | `PreToolUse(Write, Edit)` | Ничего: в `strict` сообщает о каждой правке чувствительного пути и пишет запись доказательства |
| `targeted-check-reminder.sh` | `PreToolUse(Write, Edit)`, `Stop`, `SubagentStop` | Ничего: в `standard` и `strict` напоминает отчитать точечные проверки, если файлы менялись после отчёта |
| `count-skill-usage.sh` | `PreToolUse(Skill)` | Ничего: считает частоту вызова скиллов |
| `mark-qa-gate-passed.sh` | `PostToolUse(Bash)` | Ничего: записывает маркер прохождения QA для прямого запуска команд |

Отдельно, в проект с включённой ролью test-author, ставится scoped guard тестовой зоны: он не даёт
менять тесты из-под реализующей роли. В стандартную установку он не входит.

## Политика и аудит

При approval закрепляется digest политики hooks. Поэтому смена профиля видна как изменение
контракта: проверенный план описывает одну политику, а исполнение идёт при другой, и это заметно до
публикации, а не после.

Профиль меняет человек правкой конфигурации проекта. Агент не может изменить ни настройки hooks, ни
сам ключ политики — это блокируется во всех профилях. Команды восстановления (`ledger lock-status`,
`qa clear-stale-lease`, `batch rewind`, `dispatch cancel`) не блокируются ни одним профилем: иначе из
отказа не было бы выхода.
