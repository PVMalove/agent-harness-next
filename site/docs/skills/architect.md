# Architect: архитектор

## Интерактивный скилл architect

Источник: [`SKILL.md`](https://github.com/PVMalove/agent-harness-next/blob/master/skills/first-party/engineering/architect/SKILL.md).
Скилл поставляется в `engineering-suite`, запускается вручную командой `/architect` и возвращает в
чате brief решения: текущую границу, варианты, рекомендацию, компромиссы, риски, критерии приёмки и
первые TDD-seams. Скилл изучает свидетельства и не меняет production code, тесты, конфигурацию и
файлы репозитория. Brief не разрешает реализацию, коммит, пуш или создание PR. Если разработчику
нужен постоянный ADR, принятое решение оформляют через `domain-modeling`.

Если память включена, скилл перед сравнением вариантов один раз выполняет
`harness memory search . "<решение, граница и модуль>"`. Статус поиска и статус источника он
трактует по [общему контракту](https://github.com/PVMalove/agent-harness-next/blob/master/harness/project/instructions/project-memory.md). Этот контракт задаёт и
установленный entry point для проекта без внешнего CLI. Возвращённые указатели дают кандидатов в
прецеденты. Источники со статусом `historical`, `unknown` и неподтверждённые требуют проверки, а
superseded исключаются. Скилл открывает источник, только если тот помогает различить варианты, и
проверяет его hash и применимость к текущим требованиям. Если память недоступна, скилл работает с
текущими свидетельствами репозитория.

## Роль оркестрации `architect`

Интерактивный скилл и роль координатора `architect` разные. Роль работает по своему манифесту и
Context Package. Скилл не расширяет её tool policy: роль не вызывает поиск по памяти напрямую и
сообщает координатору о недостающих свидетельствах. Дальше описан контракт роли.

Источник: [`harness/orchestration/roles/architect.md`](https://github.com/PVMalove/agent-harness-next/blob/master/harness/orchestration/roles/architect.md) и общий контракт [`_common.md`](https://github.com/PVMalove/agent-harness-next/blob/master/harness/orchestration/roles/_common.md).

### Архитектор

Используйте эту роль перед значимым решением о границе, особенно если решение трудно отменить. Роль только читает и не меняет production code, тесты, миграции или конфигурацию.

Задавайте форму изменения, а не только его поведение, и выбирайте идиому, при которой diff остаётся удобным для review. Шаблонный код, повторённый в каждом месте вызова, добавляет в Python уровень вложенности. Тогда `git diff` показывает каждую строку каждого затронутого блока как удалённую и добавленную заново. Механическое изменение может превысить лимит строк batch, а централизованный context manager или декоратор даёт ту же гарантию в пределах лимита. Если brief запрещает такую идиому, объясните в brief причину, чтобы developer эскалировал вопрос заранее, а не узнал о цене по ходу работы.

Результат: один краткий brief архитектурного решения. В нём границы, жизнеспособные варианты, выбранный вариант, компромиссы, риски, критерии приёмки и первые TDD-seams. Доказательство: целевые свидетельства из репозитория и требований, которых координатору хватает для решения. ADR нужен только для существенного необратимого компромисса. Completion report ссылается на этот brief и не пересказывает его.

Предложите план коммитов в поле отчёта `commit_plan` как упорядоченные записи `{id, summary, expected_paths, covers}`: одна запись на один коммит, который можно проверить отдельно. `covers` перечисляет номера пунктов Definition of Done (с единицы), которые реализует запись, и каждый пункт должен быть покрыт хотя бы один раз. Каждый путь в `expected_paths` лежит внутри `allowed_paths` brief. Если плану нужен путь за их пределами, это риск в `risks`, а не запись плана. `report submit` отклоняет план, который нарушает эти правила, и называет причину. По умолчанию координатор строит план из одной записи на пункт. Если предложенный план отличается от него, поставьте `risks.status: present` и опишите отличие в `risks.details`: тогда отчёт ждёт ручного accept. Accept, ручной или через `batch auto-decide` при `approval_policy: auto`, закрепляет план из отчёта без файла плана.

Если в Context Package нет ADR или карточки прецедента, которые нужны для решения, эскалируйте блокер с их названием. Не восстанавливайте их чтением всего репозитория.

Запускайте только проверки, которые различают архитектурные варианты. Архитектор не запускает полный набор проверок batch только ради базовой линии: это доказательство принадлежит developer и независимым QA-gates. Эскалируйте, если широкая базовая линия остаётся единственным способом проверить существенную предпосылку. Поэтому brief архитектора не утверждает команды проверки: укажите `checks_run` пустым списком, а каждую проверку для решения с её результатом опишите в `output`.

Если часть brief осталась невыполненной, перечислите каждый невыполненный пункт в `incomplete_items` по общему контракту. Его `target_role`: `architect` (суженный retry архитектора), `developer`, `code-review` или `qa`. Суженный retry архитектора решает только перенесённые пункты и повторяет план коммитов, только если пункт меняет этот план.

## 3. Контракты

- **Вход (Input/Brief):** неизменяемый brief координатора: тикет, явные allowed paths, критерии приёмки, запреты, issue-ветка, worktree и требуемые команды проверки.
- **Процесс (Process):** выбрать только доказательства, которые различают варианты; подготовить brief решения и план коммитов; эскалировать неустранимую неопределённость или необходимость широкой базовой проверки.
- **Выход (Output/Report):** brief решения, `commit_plan` и completion report со ссылкой на brief; `changed files: none`, `commit SHA: not applicable — read-only role`, пустой `checks_run`.
