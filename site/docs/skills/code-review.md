# Code Review: ревью кода

## 1. Название и локализация

- **Английское название:** `code-review`
- **Русский перевод:**

```text
Ревью кода
```

## 2. Полный перевод текста скила

<div class="ah-skill-text" markdown="1">

```yaml
name: code-review
description: Проверьте изменения после фиксированной точки (коммит, ветка, тег или merge-base) по двум осям. Standards: следует ли код документированным стандартам этого репозитория? Spec: делает ли код то, что требовал исходный issue или spec? Запускает обе проверки в параллельных подагентах и показывает их рядом. Используйте, когда пользователь хочет проверить ветку, PR, незавершённые изменения или просит «review since X».
```

Двухосевое ревью diff между `HEAD` и фиксированной точкой, которую указывает пользователь:

- **Standards**: следует ли код документированным стандартам кода этого репозитория?
- **Spec**: точно ли код реализует исходный issue или spec?

Обе оси работают как **параллельные подагенты**, чтобы не засорять контекст друг друга. Затем этот скилл сводит их результаты.

##### Граница runtime

Этот workflow не зависит от runtime. Язык вывода задаёт `language` из `.harness/project.json`; используйте уже настроенный вручную механизм ревью. Workflow не запускает adapter конкретного runtime, не выбирает провайдера или модель и не меняет проверяемую ветку.

Issue tracker вам уже должны были назвать. Если `docs/agents/issue-tracker.md` нет, попросите пользователя запустить `harness update`: команда создаёт этот файл из шаблонов harness. В GitLab каждая команда `glab` получает `-R <project-url>`. `<project-url>` и другие плейсхолдеры GitLab (`<host>`, `<project-id>`) определены в `docs/agents/issue-tracker.md` → GitLab → Conventions.

#### Процесс

##### 1. Зафиксируйте точку отсчёта

Фиксированная точка: то, что назвал пользователь. Это может быть SHA коммита, имя ветки, тег, `main`, `HEAD~5` и т. д. Если пользователь её не указал, спросите.

Если пользователь назвал PR или MR, фиксированная точка: его целевая ветка. Прочитайте целевую и исходную ветки. GitHub: `gh pr view <n> --json baseRefName,headRefName`; GitLab: `glab mr view <iid> -R <project-url> -F json` (`target_branch`, `source_branch`). Затем выполните `git fetch origin <target>` и возьмите `origin/<target>` как фиксированную точку. Текущий checkout должен стоять на исходной ветке. Если это не так, сообщите пользователю и не переключайте ветку (см. _Граница runtime_).

Один раз зафиксируйте команду diff: `git diff <fixed-point>...HEAD` (три точки, поэтому сравнение идёт с merge-base). Запишите и список коммитов: `git log <fixed-point>..HEAD --oneline`.

Прежде чем идти дальше, проверьте, что фиксированная точка разрешается (`git rev-parse <fixed-point>`) и diff не пуст. Неверная ссылка или пустой diff должны остановить работу здесь, а не внутри двух параллельных подагентов.

В gated-маршруте `/implement` review получает ещё закреплённые координатором Context Package и
candidate SHA. Review проверяет этот закреплённый кандидат, даже если integration base ушла вперёд:
обязательной проверки свежести base нет. Подготовка PR на сдвинувшейся base идёт через
`integration refresh`: команда делает rebase только issue-ветки batch на точный target SHA.
Delta-review бывает двух видов. Test-only delta-review идёт после Warning: новый кандидат, diff
затрагивает только тесты, в brief есть поле `delta_review_of`. Delta-review после fix-forward
назначает координатор, в brief есть секция `delta_review_scope`. Такой delta-review проверяет обе
оси только на дельте, а для остальной части кандидата опирается на отчёт прежнего review.
Координатор заменяет его полным review в пяти случаях: кандидат или новые коммиты совпадают с
risk trigger, которого прежний review не видел; новые коммиты меняют файл вне перенесённых пунктов;
у перенесённой rebase-копии не совпадает `git patch-id`; потерян коммит прежнего кандидата; новых
коммитов нет. Любой delta-review запускается отдельным независимым dispatch и никогда не заменяет
исходные доказательства на месте.

##### 2. Найдите источник спецификации

Ищите исходную спецификацию в таком порядке:

1. Ссылки на issue в сообщениях коммитов или в названном PR/MR (`#123`, `Closes #45`, `Related to #45` и т. п.). Получите issue по workflow из `docs/agents/issue-tracker.md`: GitHub `gh issue view <n> --comments`; GitLab `glab issue view <n> -R <project-url> --comments`. В GitLab `!67` означает merge request, а не issue: прочитайте его через `glab mr view 67 -R <project-url> --comments` (PR в GitHub: `gh pr view <n> --comments`) и возьмите тикет из footer `Closes #<ID>`/`Related to #<ID>`.
2. Путь, который пользователь передал аргументом.
3. Файл спецификации в `docs/`, `specs/` или `.scratch/`, который совпадает с именем ветки или функциональности.
4. Если ничего не нашлось, спросите пользователя, где спецификация. Если он ответит, что её нет, подагент **Spec** пропустит проверку и сообщит «спецификация недоступна».

##### 3. Найдите источники стандартов

Подходит всё в репозитории, что описывает правила написания кода, например `CODING_STANDARDS.md` или `CONTRIBUTING.md`.

Кроме того, что описывает репозиторий, ось Standards всегда несёт **базовый набор запахов** ниже. Это фиксированный набор запахов кода Фаулера (_Refactoring_, гл. 3), и он действует, даже если репозиторий ничего не описывает. Для него есть два правила:

- **Репозиторий важнее.** Документированный стандарт репозитория всегда побеждает. Если он одобряет то, что базовый набор пометил бы, не сообщайте этот запах.
- **Это всегда суждение.** Каждый запах подаётся как помеченная эвристика («возможный Feature Envy»), а не как жёсткое нарушение. Как и с любым стандартом здесь, пропускайте всё, что уже проверяют инструменты.

Каждый запах описан как _что это_ → _как исправить_; сравнивайте его с diff:

- **Mysterious Name**: имя функции, переменной или типа не говорит, что она делает или хранит. → переименуйте; если честного имени не находится, дизайн мутный.
- **Duplicated Code**: одна и та же форма логики встречается в нескольких hunk или файлах изменения. → вынесите общую форму и вызывайте её из обоих мест.
- **Feature Envy**: метод обращается к данным другого объекта чаще, чем к своим. → перенесите метод к данным, которым он завидует.
- **Data Clumps**: одни и те же несколько полей или параметров всё время ходят вместе (это тип, который хочет появиться). → объедините их в один тип и передавайте его.
- **Primitive Obsession**: примитив или строка заменяет понятие домена, которому нужен свой тип. → дайте понятию свой маленький тип.
- **Repeated Switches**: один и тот же каскад `switch`/`if` по одному типу повторяется в изменении. → замените его полиморфизмом или одной таблицей, общей для обоих мест.
- **Shotgun Surgery**: одно логическое изменение требует разрозненных правок во многих файлах diff. → соберите то, что меняется вместе, в один модуль.
- **Divergent Change**: один файл или модуль правят по нескольким несвязанным причинам. → разделите его так, чтобы каждый модуль менялся по одной причине.
- **Speculative Generality**: абстракции, параметры или hooks добавлены для потребностей, которых нет в спецификации. → удалите их и встройте обратно, пока не появится реальная потребность.
- **Message Chains**: длинная навигация `a.b().c().d()`, от которой вызывающий код не должен зависеть. → спрячьте обход за одним методом первого объекта.
- **Middle Man**: класс или функция в основном только передают вызов дальше. → уберите посредника и вызывайте настоящую цель напрямую.
- **Refused Bequest**: подкласс или реализация игнорирует или переопределяет большую часть унаследованного. → откажитесь от наследования и используйте композицию.

##### 4. Проверьте обе оси

Запустите подагентов `code-review-standards` и `code-review-spec` из `.claude/agents/` через механизм, который вручную настроен в coding application. Дождитесь обоих отчётов и верните их в эту основную сессию для сводки. Не заменяйте ни одну ось ревью внутри сессии.

**Prompt для `code-review-standards`** включает:

- полную команду diff и список коммитов;
- список файлов со стандартами из шага 3 **и базовый набор запахов из шага 3** целиком: у подагента нет другого доступа к нему.

**Prompt для `code-review-spec`** включает:

- команду diff и список коммитов;
- путь к спецификации или её полученное содержимое.

Если спецификации нет, пропустите подагента `code-review-spec` и отметьте это в итоговом отчёте.

##### 5. Сведите результаты

Покажите два отчёта под заголовками `## Standards` и `## Spec` дословно или с лёгкой чисткой. **Не** объединяйте findings и не меняйте их ранжирование: оси разделены намеренно (см. _Почему две оси_).

Закончите одной строкой: число findings по каждой оси и самая серьёзная проблема _внутри каждой оси_, если она есть. Не выбирайте одного победителя между осями: разделение осей существует как раз против такого переранжирования.

#### Почему две оси

Изменение может пройти одну ось и провалить другую:

- Код следует всем стандартам, но реализует не то → **Standards пройдена, Spec не пройдена.**
- Код делает ровно то, что просил issue, но нарушает соглашения проекта → **Spec пройдена, Standards не пройдена.**

Раздельные отчёты не дают одной оси скрыть другую.

##### Язык вывода

Прочитайте `language` из `.harness/project.json` (если файла или поля нет, по умолчанию `ru`). При `ru` пишите весь отчёт на русском, включая brief обоих подагентов и сводку, на каком бы языке ни был prompt. При `en` пишите на английском.

## 3. Контракты

- **Вход (Input/Brief):** фиксированная точка, diff, стандарты проекта и исходная спецификация.
- **Выход (Output/Report):** независимые отчёты `Standards` и `Spec`, затем краткая двухосевая сводка.
