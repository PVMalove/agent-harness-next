<div class="ah-skill-text" markdown="1">

### Пилотная базовая линия backend-оркестрации

Это руководство задаёт первую наблюдаемую базовую линию для необязательной capability `backend-orchestration`. Это протокол наблюдения для координатора. Он не запускает dispatch и не задаёт политику производительности.

#### Назначение

Соберите сопоставимые доказательства по реально завершённым batch, прежде чем решать, нужны ли проекту целевые показатели или изменения процесса. Весь период наблюдения ведите одну рабочую таблицу и одни правила подсчёта.

#### До первого запуска

1. Выберите период наблюдения и запишите метки времени его начала и конца.
2. Решите, откуда брать доказательства: записи batch, completion reports, журналы quality gate и трекер задач. Недоступные источники запишите до начала периода.
3. Для каждого batch в периоде запишите ID batch, ID тикета, issue-ветку, последовательность ролей и состояние завершения.
4. Объявите окно наблюдения после интеграции и правило проекта о серьёзности дефектов.
5. Подготовьте одну строку рабочей таблицы на batch и одну сводную строку на закрытый тикет. Не заполняйте отсутствующие измерения оценками.

#### Период наблюдения

Для каждого закрытого тикета в периоде применяйте одни и те же правила:

- каждый старт роли считайте стартом, а повтор считайте стартом нового dispatch;
- входные и выходные токены, которые наблюдает провайдер или runtime, относите к dispatch, который их потратил; самоотчёт роли не является token telemetry, а недоступные данные помечайте как отсутствующие;
- время работы quality gate записывайте отдельно от времени в очереди или ожидания;
- каждый дефект после интеграции свяжите с его batch и одинаково применяйте объявленные окно наблюдения и правило серьёзности;
- храните вместе с рабочей таблицей период измерения, ID batch и тикетов, источник, заметки об отсутствующих данных и правила подсчёта.

#### Запись каждого batch

Перед закрытием записи batch запишите:

- ID batch и тикета, запущенные роли, ID dispatch и были ли среди них повторы;
- число токенов каждого dispatch, только если есть telemetry провайдера или runtime, с её источником и заметкой об отсутствующих данных;
- метки времени старта и результата quality gate и время в очереди, если оно известно;
- метку времени интеграции и ID связанных дефектов, найденных в объявленном окне.

#### Измерение quality gate

Берите метки времени, которые выдаёт последовательная линия quality gate (serialized lane). Wall time считайте от старта gate до его результата, время в очереди ведите отдельным наблюдением. Если какой-то метки времени нет, запишите пробел и не восстанавливайте её по несвязанным событиям.

#### Запись дефектов после интеграции

В объявленном окне наблюдения записывайте каждый дефект, который можно связать с batch: ID batch, ID дефекта, метку времени обнаружения, серьёзность по правилу проекта и источник доказательства. Несвязанный дефект или дефект вне окна не считайте, пока не запишете, почему его включили.

#### Рабочая таблица базовой линии

| Измерение | Что наблюдать | Источник или заметка об отсутствующих данных |
| --- | --- | --- |
| Старты агента на закрытый тикет | Старты и повторы по каждому закрытому тикету | Записи batch и ID dispatch |
| Токены на batch | Входные и выходные токены каждого dispatch по данным провайдера или runtime | Telemetry или записи выполнения; иначе заметка об отсутствующих данных |
| Wall time quality gate | От старта gate до результата, очередь отдельно | Метки времени quality gate |
| Дефекты после интеграции | Связанные дефекты в объявленном окне по правилу серьёзности | Трекер задач и записи дефектов |

Базовая линия служит доказательством для будущих решений. Руководство не называет конкретного провайдера, модель, runtime или платформу и не задаёт жёсткой числовой цели.

</div>

## 3. Контракты

- **Вход (Input/Brief):** период наблюдения, закрытые batch/тикеты, completion reports, журналы quality gate, трекер и правило серьёзности дефектов.
- **Процесс (Process):** координатор собирает одинаковые наблюдения, не заменяет отсутствующие данные оценками и отделяет время в очереди от времени выполнения.
- **Выход (Output/Report):** рабочая таблица базовой линии с четырьмя измерениями и отмеченными пробелами данных.
