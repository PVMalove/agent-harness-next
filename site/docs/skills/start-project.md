# Start Project: начать проект

## 1. Название и локализация

- **Английское название:** `Start Project`
- **Русский перевод:**

```text
Начать проект
```

## 2. Полный перевод текста скилла

<div class="ah-skill-text" markdown="1">

```yaml
name: start-project
description: Начинает новый проект с идеи или создаёт, проверяет и обновляет его автономный агентный харнесс (agent harness). Используйте, когда пользователь хочет сформировать или инициализировать программный, контентный, исследовательский, операционный, личный или другой проект, решить, когда проекту нужен репозиторий, или установить либо пересмотреть харнесс проекта. Обычная работа внутри проекта, где харнесс уже есть, этот скилл не вызывает. Репозиторию, где уже много кода и соглашений, но ещё нет харнесса, лучше подходит более глубокий аудит `integrate-project`.
```

### Начать проект

Ведите проект от неоформленной идеи до переносимого проекта. Репозиторий, стек, трекер и харнесс
получаются из проектирования проекта, они не нужны заранее. Каждая фаза работает только на чтение, пока владелец
не подтвердит артефакт, который она предлагает записать надолго.

Найдите реальный путь этого скилла и проверьте, что публичный корень `agent-harness` на два уровня выше
содержит `skills/REGISTRY.md` и `harness/bin/harness.py`. Встроенные в него рабочие процессы служат библиотекой: по
реестру найдите и прочитайте только тот `SKILL.md`, который нужен текущей фазе. Корень найден, только если
есть оба файла. Иначе сообщите, что публичный пакет неполный, и не угадывайте другую установку.

#### Формирование (Shape)

1. Выясните, что есть у пользователя: идея, начальный каталог или существующий репозиторий. Прежде чем задавать
   вопросы, изучите существующие файлы. Если в репозитории уже много кода и соглашений, но харнесса ещё нет,
   этот случай разбирает отдельный аудит `integrate-project`, а не общий путь. Передайте работу ему и не
   выводите факты здесь поверхностно.
2. Определите основную работу проекта: программное обеспечение, контент, исследования и знания, операции,
   личное или другая явная область. Класс выбирает рабочие процессы, но не ограничивает, чем проект может стать.
3. Примите решения, от которых зависит следующий артефакт. Для неоформленной идеи прочитайте
   `skills/vendor/mattpocock/productivity/grilling/SKILL.md` и следуйте ему. `research`, `to-questionnaire`,
   `prototype` или `domain-modeling` берите, только если их описание в реестре подходит к текущей ветке решений.
   Процессы, которым нужен трекер, например `to-spec` и `wayfinder`, начинаются, когда уже есть репозиторий и
   его контракт с трекером.
4. Черновые размышления оставляйте в сессии. Когда известны цель, ожидаемый результат, повторяющаяся работа и
   следующий полезный артефакт, порекомендуйте ровно один вариант: продолжить разговор, написать brief, создать
   начальный репозиторий или собрать харнесс.

Формирование закончено, только когда владелец подтвердил рекомендацию или явно оставил работу в разговоре.
Подтверждение разрешает один этот артефакт, но не следующие заготовки (scaffolding).

#### Начало (Seed)

Когда владелец подтвердил seed, создайте названный Git-репозиторий или возьмите существующий и запишите только
подтверждённые brief и заметки о решениях. Структуру и инструкции существующего репозитория не меняйте.
Нерешённые вопросы о стеке, трекере и харнессе запишите как нерешённые. Не выбирайте ответ за владельца,
чтобы seed выглядел законченным.

Seed закончен, когда путь к репозиторию проверен, в долговечных файлах только подтверждённые факты,
`git status` просмотрен и владелец видит, какие решения ещё открыты. Для кода приложения, настройки трекера
и харнесса нужен свой подтверждённый следующий артефакт.

#### Сборка (Assemble)

Собирайте харнесс, только когда у проекта появилась стабильная работа, которую он будет поддерживать, или сразу,
если пользователь явно его просит.

1. Выведите из репозитория и разговора цель, тип проекта, этап, базовую ветку, трекер, повторяющиеся действия,
   команды, границы, политику доставки и Definition of Done. Неприменимые команды и трекер пометьте как `N/A`.
2. Выберите наименьшую целостную публичную capability:
   - `project-foundation` для общего проектного мышления, исследований, handoff, языка предметной области и
     инструкций для агентов;
   - `mattpocock-suite` для повторяющейся работы в программной инженерии;
   - никаких дополнительных пакетов только потому, что они доступны.
3. Если владелец просит `start-project` выбрать повторяющиеся рабочие процессы, разрешите подходящему
   установленному скиллу входа в личный каталог или каталог организации (catalog-entry skill) вернуть метаданные
   каталога. Передайте ему только факты о проекте и повторяющиеся действия и соблюдайте его границы доступа.
   Выбор из каталога не даёт доступа к посторонним личным знаниям, задачам, заметкам или секретам.
4. Покажите один манифест харнесса: факты о проекте, публичную capability, пакеты-наложения (overlay), пакеты
   только для проекта (project-only), интеграции, границы и файлы, которые изменятся. Разрешите конфликты
   одинаковых имён, происхождения и лицензий, затем получите подтверждение владельца для манифеста.
5. Для подтверждённого нового харнесса выполните команду найденного пакета. Примеры значений замените значениями
   из подтверждённого манифеста:

   ```bash
   python3 "<resolved-agent-harness-root>/harness/bin/harness.py" init "<repo>" \
     --project-type <type> \
     --capability <selected-capability> \
     --base-branch <branch>
   ```

   В Windows/PowerShell нет `python3` (используйте `python`), а перенос строки там `` ` ``, а не `\`.

   Заполните каждый неразрешённый `{{...}}` в `AGENTS.md`. Пакеты только для проекта положите в
   `.harness/skills`. Запустите `harness lock-project-skills`, чтобы закрепить их версионированный хэш, а после
   сборки всех пакетов запустите `harness registry`. Ссылки для обнаружения (discovery links) делайте
   относительными, никогда не ссылайтесь обратно на локальный каталог машины.

   Задайте `hook_policy` с профилем `standard` явно: назовите профиль в манифесте, а после `harness init`
   проверьте, что `.harness/project.json` содержит `"hook_policy": {"profile": "standard"}`, а `harness health`
   показывает `hooks.policy` с профилем `standard`. Не выбирайте `minimal` или `strict`, если владелец этого не просил.
6. Для существующего харнесса выполните `harness diff` перед `harness update`. `harness adopt
   --replace-conflicts` используйте только для явной миграции и только после проверки конфликтов одинаковых имён.
   `harness update` не записывает `hook_policy`. `hook_policy` существующего проекта оставьте его владельцу.
7. MCP-серверы, плагины, хуки и настройки runtime храните в их родных файлах проекта. Если такие файлы есть,
   внесите в инвентарь `.harness/integrations.json` их относительные пути, хэши, runtime, действие проверки и
   имена переменных окружения с секретами. Учётные данные никогда не копируйте в Git.

Сборка закончена, когда подтверждённый манифест представлен закоммиченными файлами проекта, у каждого пакета
есть происхождение источника и хэша, а неподтверждённых интеграций и рабочих процессов не добавлено.

#### Завершение (Finish)

Докажите каждый слой отдельно:

1. **Сохранено (Stored):** выбранные пакеты и lock-файлы лежат в каталоге `.harness/`.
2. **Подключено (Wired):** `.agents/skills` и `.claude/skills` указывают на один и тот же снимок проекта.
3. **Здорово (Healthy):** `harness health` проходит: маркеры шаблонов, имена, реестр, хэши публичных и
   overlay-пакетов, ссылки для обнаружения и инвентарь интеграций согласованы.
4. **Объявлено (Advertised):** новая сессия runtime показывает установленный скилл проекта. Если у runtime нет
   родного корня скиллов проекта, он может находить скиллы через `.harness/skills/REGISTRY.md` из `AGENTS.md`.
5. **Вызвано (Invoked):** эта сессия открывает выбранный скилл родным механизмом runtime.

Если текущая сессия не может заново просканировать скиллы (discovery), сообщите шаги 4 и 5 как точную проверку,
которая осталась для новой сессии. В конце назовите тип проекта, установленные capabilities, исключённые
поверхности, доказательства проверки и следующее полезное действие.

</div>

## 3. Контракты

- **Вход (Input/Brief):** идея, seed-каталог или репозиторий и ответы владельца.
- **Процесс (Process):** скилл по очереди проходит Shape, Seed, Assemble и Finish. На каждую долговечную запись нужно отдельное подтверждение владельца.
- **Выход (Output/Report):** проверенный репозиторий, манифест и подключённый харнесс проекта или точный следующий артефакт.
