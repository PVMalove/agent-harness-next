# Уровни тестов

Используем [пирамиду тестирования](https://vladislaveremeev.gitbook.io/qa_bible/vidy-metody-urovni-testirovaniya/piramida-urovni-testirovaniya-test-pyramid-testing-levels):
основная масса — быстрые unit-тесты, меньше проверок взаимодействия модулей,
минимум сквозных проверок критических путей.

- **Unit:** валидаторы, состояния, маршрутизация, argv, форматирование и фильтры.
  Здесь проверяются граничные варианты. Время, процессы и сеть подставляются явно.
- **Integration:** контракты Python/Rust, транзакции, блокировки, восстановление,
  coordinator/runtime/store и эффекты установки на временных данных.
- **E2E:** полный цикл оркестрации и восстановления, контейнерные smoke,
  отдельные проверки доставки установленного пакета и внешней CLI-обвязки.

Верхний уровень проверяет связь компонентов и критический результат, а не повторяет
всю матрицу ошибок unit-уровня. Каталог теста сам по себе не определяет его уровень.
Для консоли действуют отдельные [unit-only правила](console/README.md).

`make test` запускает все уровни. `make coverage` выполняет параллельный запуск
с line coverage пакета `harness` и минимальным общим порогом **70%**.
Rust проверяется отдельно через cargo fmt, clippy и test.

## Условия отдельных запусков

- Проверки настоящего parser bundle требуют `HARNESS_PARSER_BUNDLE_DIR` и выполняются
  в отдельной матрице Repo Map CI.
- Windows-специфичные проверки пропускаются на других ОС. Общий Python job Windows
  в workflow снова включён (#938): `verify-windows` идёт на полном пути CI, то есть не для PR в `integration/**`; отдельный Rust/runtime job `runtime-ipc-windows` его не заменяет.
- Векторный эксперимент требует `HARNESS_VECTOR_PROBE_ARTIFACTS`.
- Измерение производительности state требует `HARNESS_MEASURE_STATE_DIR`.

Пропуск означает отсутствие проверки в данном запуске, а не положительный результат.
