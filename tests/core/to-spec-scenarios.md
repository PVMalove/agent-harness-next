# Приёмочные сценарии `/to-spec`

Запускайте каждый сценарий в отдельном тестовом репозитории с `engineering-suite`. В Codex
выберите навык через `$to-spec`. Сохраните трассу команд и сравните список и хэши файлов
до и после каждого ответа. Исключите журналы среды выполнения. Проверяйте чтения по трассе,
поскольку `git status` не показывает, какие файлы открывал агент.

## Общие данные

- Целевой файл `docs/tasks/order-retries/order-retries.md`. Артефакт находится в соседнем
  `artifacts/discovery-context.md`. В обычном сценарии это две Markdown-строки в порядке
  `src/orders.py`, `tests/test_orders.py`. Файл `src/legacy.py` также существует.
- `src/orders.py` экспортирует `submit(order_id: str) -> str`. В тесте вызывается `submit`.
- Готовый итог `/grilling` фиксирует цель повторять временно неудачную отправку, сохраняя сигнатуру.
  Принято D1 `[1] Recommended` (две попытки), D2 `[2] Fast-Track` (только `TimeoutError`),
  D3 `[3] Full / Clean Architecture` (регрессия через публичную сигнатуру). У каждого решения
  перечислите остальные два варианта с причинами отказа. Приложите одобренный список файлов.
- В частичном итоге вместо готовых решений оставьте блокер D1 — идемпотентность повторной отправки.
  Явно запишите, что от выбора зависят контракт `submit` и проверка повторного вызова.
